docs/design/hq.md:131:- **Changes after a cursor (`hq wait`, [ADR 0019](../adr/0019-agent-state-changes-are-numbered.md), #166).** `hq wait` returns an agent that changed into `done`, `question`, `needs input` or `ended` after its `--since` (spec §4.1), and its processes, one call after another and beside the list and `hq ls`, must agree on whether a change came before or after the point a result stands for, with nothing watching between two calls and whatever the clocks do. Every change of an agent's state is an event with a number of the host's one counter (*Events and journals*), so each compares numbers. An agent's `state_seq` is the number of the event at which the reducer's state or open dialog last changed (`Reduced.Changed`, or for an agent `starting` since its launch, whose state no event has changed yet, the launch's event, `Reduced.Entered`; a report that changes neither moves it not, a new dialog while it needs input does), its `completion_seq` that of the event that ended its last completed turn (`Reduced.TurnEnded`: a turn end its hook reported as `done` or `question`, or the `TurnNotTaken` that decides the turn Claude owed after one kept `working` for background work does not come, as the operator decided on #166; not a stop blocked to deliver a message, a session's start, a resumed or restarted conversation, or a turn the user ended at the agent). An agent with no event behind its state has neither: an outdated one, whose journal hq does not read; one `starting` before its journal holds an event; one `ended` whose journal cannot be read; and one gone from tmux while waited on (`Agent.Gone`). A **cursor**, `next_since`, is the letter `c` and a number N such that the look that gave it saw every change numbered up to N: not the highest number it saw, since a look reads each agent's journal in turn under the lock, and an event another process appends for an agent it has read already, before it reads the next, is numbered at or below that next read's `Journal.Through` without being seen. So N is the lowest `Through` of the look's last reads (`agent.SeenThrough`), or the counter read before the look listed the home windows (`journal.Store.Through`) when that is all the look can vouch for: no journal read, one that could not be, or an agent whose window appeared while it looked, which `hq ls --json` and `hq wait` see by listing the windows once more (its window is made before its `Launched`, so every change of its is numbered above that counter). A look may show an agent at a change numbered above its N (evidence it appended for that agent after its last read of another), so `hq ls --json` looks again, three looks at most, until its N stands for every agent of the look (every row of `hq ls --json` without names); a list of agents that change at every look is printed from the third. A look finds the waited-on agents in such a state whose `state_seq` is above the cursor given and at most its own N, and prints its N as the next call's `--since`: consecutive calls return every change once and none twice, with any number of hq processes looking at once, and with no settle time, since a change a look sees is numbered at or below its N. A look that finds one does not return yet: the look after it, 250 ms later, returns what it finds, with its own N, and the agents the first found that it no longer does (one that moved on meanwhile still changed after `--since`), so agents that finish within a look of each other come back in one call (#116): a reported state is returned 250-500 ms after it is ingested. A change overtaken by a later one between two looks is not returned. Without `--since` the call starts each agent its first look showed from the state number that look showed for it, so an agent already in such a state is not returned, including one that look put there with an event it appended after it read another agent, which its N does not stand for yet, while a change another process numbers after that look (as `deliverWaiting` types) is; an agent that look did not show starts from the counter once the look is done. A cursor above the counter (a lost state directory) is refused, saying to take a new one from `hq ls --json`. `--since` also takes a moment (RFC 3339, as an older hq printed `next_since`) or a duration back from now, compared with the time of the event at which the agent entered its state (`Agent.Entered`), approximate by nature; the result carries a cursor all the same. `hq ls --json` prints its look's N; `hq read --json` the `Through` of its read of that one agent; `hq send --json` and `hq answer --json` the counter read just before they leave the message or the answer, so what the agent does with it is numbered above it. What a result could not have shown is every agent's change for `hq ls --json` and `hq wait` (of the agents waited on), but only the one agent's for `hq read`, `hq send` and `hq answer`: another agent's change before their cursor that no `hq wait` returned may be lost from there, so a watch takes its `--since` from `hq wait` and `hq ls --json` alone (3.12). An agent waited on that the last look saw and this one does not (killed), or sees `ended` with no number where it had one (its journal no longer read, its pane dead), is returned as `ended` at once, with no numbers, since no number can say it changed. What a look finds for a wait is one question of the wait's terms and of that look with its N (`waitTerms.resultAt`, #358): the terms are the agents named, or every agent but the outdated ones, `--since`, the agents the previous look waited on and the deadline, and the answer is the agents to return, these gone ones included, or none and whether the deadline has passed. `hq wait` holds the terms from one look to the next and asks each look, the MCP server's `wait` through it, and a look can be asked for terms no call holds, as each poll of a wait task asks it (3.12, ADR 0022), and a call and a poll take the look more after a hit alike (`waiting`, #363). `hq kill` kills an agent's home window and only then removes its files and journal (3.3), so a look can list the window and read the journal after it was removed (#239), and took the agent for one that never reported: `hq wait` returned it with `[session ended]` in place of its last message, and `hq ls` showed it so. A look notes an agent whose journal it found gone, holding nothing when it read it or removed while it looked (`Agent.JournalGone`), and when it found one lists the home windows once more and leaves out such an agent whose window has gone: for a kill this is certain, the window going before the journal, and the look shows what the next look shows, so `hq wait` returns the agent as killed with what the look before showed, and `hq ls`, the list and the other looks do not show it. An agent whose journal is gone while its window is still listed (before its `Launched` is appended, or a lost state directory) is shown as before. A `hq wait` whose first look falls between those steps of a kill answers that there is no such agent, as one whose first look comes after the kill does. A paged `hq read --offset N --since CURSOR` gives the page while the latest turn end's number (`Detail.ReplyNumber`) is at most the cursor, so a page is of the reply the cursor's read showed; with a moment it compares the turn end's time as before. `AGE` still counts from the time of the change: numbers order changes, times measure them.

docs/design/hq.md:303:**The wait task (#361, ADR 0022).** Under Claude Code (`mcpClient`'s `tasks`) a `wait` holds for 50 s (`waitHold`), as long as a `wait` lasted there before #359, so a change within them comes back in the same call and turn; one given a timeout of 50 s or less ends at it in its call, as before. A `wait` whose hold ends at or past its timeout, a look having taken long, returns no agents in its call, as at a timeout. Claude Code then asks for the task with `tasks/get` at that interval, with no model request, and starts the supervisor's next turn with its result once it has completed. A request without the declaration waits on in its call (above), its timeout cut to an hour; Claude Desktop's and the gateway's `hq mcp` serve no tasks, the first declaring none and the second passing none. **The id carries the wait, signed.** A wait task's id holds its terms: its kind (`w1`), the cursor of the call's last look, the moment of the handoff and the deadline, the call's start plus its timeout (empty for none, #363), each to the millisecond in base 36, a nonce that tells apart tasks of the same terms made at the same moment (two `wait`s in one message), the names, and the agents the call's last look waited on, each its name, `=` and its id (#363), between colons, the names and the agents between commas; then, after a colon, their signature (#362): the first 128 bits of their HMAC-SHA256 under the task key, in 22 characters of base64url: `w1:c42:mujrox8w::-k3qtLzR:a,b:a=3f2a9c1d4e5b,b=0c7d22e81f9a:7DkqY0b2xN4Lw9sPq1ZtVg`, short, since Claude Code prints it into the model's context with the handle and again with the result: a covered agent is its name and id alone, and one that look saw ended with no number is left out, since a look does not return it again (3.4, *Changes after a cursor*). The task key is 32 random bytes in hq's state directory, `$XDG_STATE_HOME/hq/task-key` (`0600`, `internal/taskid`), out of every sandbox's reach as the journals are, and the id never holds it. The first wait that goes on as a task makes it: written aside and hard-linked into place, so of `hq mcp`s that make it at once the first to link wins, none overwrites another's, and each signs with the one in place; it is never rewritten, and a file in its place that is not 32 bytes is refused, naming it. So no one builds an id from its terms alone, as the extension requires of an id (one a third party can neither enumerate nor guess): an id with any character changed, in its terms or in its signature, one signed in another state directory, and one hq cannot check because the key went with the state directory are unknown tasks (below), and asking for one reads the key and makes none. A wait whose hold passes when hq can neither read nor make the key fails in its call with that error, since no `hq mcp` could tell its task from one made up. So no `hq mcp` holds a wait, and any answers for any task, also one started for a session resumed after "Exit and stop tasks": each `tasks/get` is one look, taken as a call takes each look after its first (`agent.Looker.Loop`, `waiting`) and delivering what waits as each look of a wait does, asked for the wait's result for the id's terms (`waitTerms.resultAt`, 3.4). While it finds none and the deadline has not passed, the task is `working`. Once it finds agents it takes one look more, as a call does, so agents that change together come back together, and is `completed` with the `wait` tool's text for the last look, the agents of both and its `next_since`, and no `structuredContent`; once the deadline has passed with none it is `completed` with no agents and that look's `next_since`, not an error (#363). A covered agent the look no longer shows was killed since the call ended or between two polls: it is returned ended now, as a call returns one it covered (3.4), with its name and, when the trace of kills (3.3) already holds it, the repository and sandbox it worked in; the id carries no branch or last message, so its `last` is `[session ended]` where a call gives what it last showed (#363). tmux gone or a look that fails completes the task with that error as a tool error, the text the call would have ended with, which Claude Code shows the supervisor as "Task failed: ...". The cursor of the hold's last look stands for every change that look saw, so the task returns what a `wait` from the empty result's `next_since` would: nothing lost and nothing twice. Each `wait` that goes on is a task of its own; hq keeps no list of a conversation's tasks and ends none. **The poll interval** was measured (#361): Claude Code 2.1.332 asked every 5.01 s for minutes on end, with no model request, and hq answered each poll in 6-22 ms, about 14 ms of CPU, against the stub `sbx`; so a result comes at most 5 s after its change, little beside an agent's turn, for about 720 looks an hour, and a poll whose `sbx ls` takes all of its 5 s (`sbxPollTimeout`) ends before the next one comes.
