# Integration review: this project's surfaces

Read by the integration reviewer, who reads each ticket's diff against the release branch as it stands and once more over the whole release, and by `/release-ship` to classify a hotfix merged into the release branch. The review's questions, the *block* and *note* tags and where findings go are the skill's; this file holds the lists and the checks only the project knows. They grow from use: a hotfix path that cost a full Release QA is added afterwards.

## Shared surfaces

Files, keys, prompts, migrations or manifests more than one ticket may touch, and what *coherent* means for each: the condition two changes to the surface must satisfy together, beyond merging without conflict.

| Surface | Coherent means |
| --- | --- |
| The requirements spec, `docs/requirements/spec.md` | Every scenario, command and acceptance line agrees with every other: no behaviour is stated twice in two ways, the section and scenario numbers other documents cite still point at what they meant, and it says WHAT, never HOW (`docs/hq/agents.md`, *Rules*) |
| The design document, `docs/design/hq.md` | It describes the code as merged: each mechanic in one place, no two changes claiming the same section for different designs, and the § numbers the code, the tests and the docs cite still point at the right section |
| The glossary, `GLOSSARY.md` | One entry per term and one term per concept; no entry's term is another's *Avoid* word; the code, the docs and the issues of both changes use its terms |
| The packages for agent state, `internal/state`, `internal/agent` and `internal/journal` | One set of agent states and one attention order: a state or a transition added by one change is handled by the other change's code (the list, `hq wait`, the dashboard, the notifications), and what the hook reports and how hq keeps it (the event files, the journal, the agent's record) keep one form: a change to either raises the generation (ADR 0020), which the fingerprint test of `internal/version` holds |
| The screen rules, `internal/state` where it reads Claude's screen (`Sees`, `ScreenMayTell`) | Every rule a change adds, and every existing rule a change applies to a state it did not cover, is tested on a real capture of that state's screen (`internal/state/testdata`, with its row in the README there; `tools/capture/README.md`), and what one change reads off a screen the other does not read otherwise. A fix the reviewer suggests is held to the same: a suggestion to settle a state by the screen names the capture, or is given as the operator's decision. |
| The sandbox client, `internal/sbx` | One way to run and parse `sbx`: both changes go through the same calls, and what one changes in how a sandbox is named, created or found holds for the other's callers |
| The command line, `internal/cli` and `cmd/hq` | One usage text and one set of exit codes: every command in `hq help` exists and the other way round, a flag means the same in every command that takes it, and the codes are those `hq help` lists |
| The platform code and the dashboard, `internal/platform` and `internal/dash` | Both platforms behave the same after both changes: what one adds for one platform the other platform has, platform names stay in `internal/platform` (`go run ./tools/testgate platform`), and the dashboard's keys, views and columns do not collide |
| The MCP tool descriptions, `internal/cli/mcp.go` | Every tool's description matches what the tool does after both changes, and the descriptions do not contradict one another (in particular on `since`, `wait` and when to use `send` or `now`) |
| The test gates, `tools/testgate` | A threshold only goes up, in the pull request that moves the figure; two changes that each fit the margin must fit it together |

## Reasons of equivalence

A surviving mutant is accepted only when no test can kill it (`docs/hq/testing.md`, *Mutation tests*, *What passes*, which also names the differences that are not equivalence), and a reason that only sounds harmless lets a change of behaviour through. So for every reason of equivalence in the pull request's `## QA` (`gh pr view PR --json body` with PR its number), in every mutation block whatever its base, the reviewer tries to write the unit test that kills the mutant, in a worktree of its own that it never pushes: a test that passes on the original code and fails with the mutant put in by hand. The reason stands only when no input tells the mutant from the original. A test that tells them apart is a *block* finding, quoting the test: on the survivor's line when the pull request's diff holds it, in the review's body when it does not. The pull request's implementer adds the test before the merge.

## Reasons for a line not run

A changed line that no test runs (`not run` in a mutation block) is accepted only with a reason of one of the two kinds `docs/hq/testing.md`, *Mutation tests*, *What passes*, names: no test can run the line (a file that builds only on darwin, in a run on Linux), or a named test runs it in a process the gate cannot read, one ended by a signal before it writes down what it ran. So for every reason next to a `not run` line in the pull request's `## QA`, in every mutation block whatever its base, the reviewer checks it as a reason of equivalence: it tries to write a test that runs the line at any level, in a worktree of its own that it never pushes, and for a named test it checks that the test runs the line and that the process it runs in ends by a signal. The reason stands only when no such test can be written, or the named test does what the reason says. A reason of another kind ("an integration test covers it", a line hard to reach), or a test that runs the line, is a *block* finding, quoting the test when there is one: on the line when the pull request's diff holds it, in the review's body when it does not. The pull request's implementer adds the test before the merge.
