# hq - design

Version 1.0 (draft, in progress)

HOW hq is built. The WHAT is `docs/requirements/spec.md`; this document cites it by section (`§5`), scenario (`S4`) and acceptance (`§10`) and never restates it. Decisions that are hard to reverse live in `docs/adr/`.

## 1. Overview & design drivers

The architecturally significant requirements, in priority order. When two pull in different directions, the higher one wins.

1. **The givens** (§2, ADR 0001). State leaves a sandbox only through the mounted repository; sessions are tmux entities. Non-negotiable.
2. **The docked session is the real session** (§6.1, S3). The agent's own tmux pane is shown and used in the dashboard; nothing is mirrored or previewed. This makes the dashboard a composition of tmux panes rather than a single full-screen program that draws everything.
3. **No daemon** (§8, ADR 0002). Every command works with no dashboard running; only the dashboard observes state and notifies.
4. **Identical behaviour on both platforms** (§2, §8, S13): macOS with iTerm2, and WSL with Windows Terminal, both with plain tmux (ADR 0008). Platform-specific code sits behind one adapter.
5. **Timeliness and exactness** (§5, §10): state visible within 1 s, `ended` within 2 s, exactly one notification per attention event, none for the `question` and `done` of a supervised turn (and for a turn an API error ended the documented limitations: its notification comes about a minute late, none when a prompt comes first, and there may be none while a subagent runs, 3.5).
6. **Install footprint** (§8, §11): one command per platform, no service.
7. **Phase 2 headroom** (spec, Phase 2): the supervisor drives hq through the CLI's own commands (3.12); a flat row model, sorting and filtering kept separable.

## 2. Constraints & assumptions

Constraints are the spec's givens (§2) and constraints (§8); they are not repeated here. Assumptions below; if one proves false, the decisions that cite it are reopened.

- **A1 - Builders.** hq is built mostly by Claude Code agents working the repository's issues, under the owner's review. Technology is chosen for being agent-friendly and reviewable, not for a team's existing language skills.
- **A2 - Users.** The owner on macOS and a small team (2-6 people) on Windows/WSL. Each person runs their own hq; nothing is shared between machines.
- **A3 - Scale.** Per machine, typically 3-10 concurrent agents, rarely above 15, across 1-5 repositories. At this scale, polling tmux and the agents' event files several times a second is negligible, so incremental or event-driven machinery is not justified by load.

## 3. High-level architecture

### 3.1 Dashboard composition

The dashboard is one tmux window built from tmux's own parts ([ADR 0007](../adr/0007-dashboard-is-tmux-composition.md)):

```mermaid
flowchart TB
    subgraph W["tmux window: dashboard"]
        L["List pane (top)<br/>shell running the hq list program"]
        S["Docking slot (bottom)<br/>the docked agent's real pane, or the placeholder<br/>framed, titled name · branch · sandbox"]
        F["Status line (bottom edge)<br/>footer set by the list program"]
        P["Popup (on demand)<br/>centered dialog over the whole window"]
    end
    H1["Agent 42 home window<br/>its pane when not docked"]
    H2["Agent agent-17 home window"]
    H1 <-- "swap-pane (dock / undock)" --> S
    H2 <-. "swap-pane" .-> S
```

- **List pane.** A shell that runs the list program. The list program owns the list, the cursor, the keys of §6.2-6.5, and the footer text. On `q` it exits and hq takes every client off the `hq` session (3.11), so the terminal gets back what it had before `hq`; the shell stays in the list pane with a hint, seen only by a terminal attached without hq, and `hq` or `hq dash` starts the list there again.
- **Docking slot.** Holds exactly one pane: the docked agent's own pane, or the placeholder with the hint of S1/S6. Docking swaps the agent's pane in from its home window; the pane it replaces goes back to its own home. The agent's process, scrollback and cursor are never interrupted. Every home window is kept at the slot's size (tmux `resize-window`, when an agent's window is made and whenever the layout is applied, and again for the two windows a dock involves, in the same tmux call), so a swap never changes a pane's size and tmux sends the agent no resize: Claude redraws its whole screen on each resize and tmux keeps every cleared screen in the history (#130).
- **The slot follows the cursor.** The list program docks the cursor's row once the cursor has rested for 150 ms after the user's last move (`↑`/`↓`, a click on a row, a search letter); each move restarts the wait, so a held key (repeating every 30-90 ms by default on macOS and Windows) docks only where it stops. These docks leave the keys on the list; `⏎`, a search's `⏎` and a New agent dialog's agent dock with the keys. Only the user's moves dock: a refresh or re-sort moves the cursor with its agent, never to another, and the welcome of a new agent started elsewhere (`hq new`, `hq mcp`; spec S2) takes the cursor and the slot only when nothing is docked. A dock made elsewhere (a chord, `hq go`) moves the cursor to its agent (3.7); the list tells its own docks apart by the refresh that follows, so a refresh collected while its own dock was on the way does not pull the cursor back to the previous row. When the docked agent goes, the cursor takes its row's place without docking it, and the placeholder stays (S6).
- **Placeholder.** Not a shell: a hidden hq command that shows the hint, hides the cursor and takes no commands. Anything it is given (keys, a paste, a click, since it asks tmux for the mouse) is swallowed and puts the keys back on the list pane, so the list's keys keep working. Its pane is marked as hq's placeholder and kept when its program ends, so the home window it waits in never closes with its agent; `hq` starts it afresh when it is not running hq's program, which also replaces the shell an older hq left there, wherever it waits.
- **Frame and title.** The slot is framed on all four sides by the surround (`#16181D`, the design's colour). tmux cannot draw a box with corners inside a window (a border's ends always meet another border as a junction) and colours a border cell by whichever neighbouring pane it finds first from the active one, so the frame is tonal, not a line: two margin panes one column wide either side of the slot (role `spacer`, running the placeholder program with no hint, so a click there puts the keys back on the list) and the status line take the surround; every pane border is drawn in the surround's colour on the surround, so it is invisible whichever pane owns it. Pane statuses sit at the bottom (`pane-border-status bottom`): the list starts on the window's first row (no rule above the header), the border row between list and slot is the list pane's status, which shows the slot's title `▸ name · branch · sandbox` (or `▸ placeholder`) filled in the slot's colour exactly as wide as the slot, so title row and slot read as one area; the slot's own status row below it is the bottom margin. tmux draws a pane's status four columns narrower than the pane up to 3.5 and two from 3.6 on; on 3.6 and later the title's last two columns are given the surround's colour. The docked pane is four columns narrower than the terminal, which is what Claude sees. The terminal is titled `hq - agents`.
- **Where the keys are** (spec §6.1, #128). The side with the keys, the list or the docked session, is on the terminal's own background (tmux's `terminal` colour, not `default`, which in a pane's status row means the border's style; #117), the other on the surround. tmux draws a window's active pane in `window-active-style` and the others in `window-style`, and redraws them whenever the active pane changes, whatever changed it (Alt+l, a click, docking, a dialog's action), so the look follows the keys with no hq process involved. The dashboard window's own styles are the slot's: active the terminal's background, inactive the surround with the default text colour `#9CA3AF`, which dims what the session draws in the terminal's text colour; cells Claude draws in colours of its own keep them. Being the window's, they are taken by whichever agent's pane is docked and stay behind when it goes home: the pane itself carries no style, and its home window has none, so there it looks as tmux's defaults make it. The list pane has its own: active the terminal's background, inactive the surround, its text keeping the list program's colours. The margins are the surround either way, and so is the placeholder, which also has both styles of its own (the surround, text dimmed): it never holds the keys, and a click on it, which gives it the keys for the moment before it hands them back to the list, does not flash it. The title row is drawn from the list pane's `pane-border-format`, which loops over the window's panes (`#{P:}`) to take the slot pane's `pane_active`: the terminal's background and the title in the accent `#A78BFA` while the docked session is the active pane, the surround and the dim `#5C626C` otherwise, the placeholder (role `slot`) always the latter. tmux redraws pane statuses with the borders on every change of the active pane. Every `hq` sets these styles again, so a dashboard styled by an older hq is brought up to date in place, placeholders waiting in home windows included. Esc is not bound: Claude uses it (3.7).
- **Docked row's outline.** The design draws a rounded lavender box around the docked row within the row's own height. A terminal row is one line of cells, so a box needs a line above and a line below the row for its edges. Those lines could only come from the session below (the list's height is fixed, spec §6.1), from the list rows (6 at 24 lines, 3 below), or by pushing the rows apart around the docked one, which the design does not do; and they would move with the docked row as the list scrolls and re-sorts. Cell attributes do not draw it either: an overline takes each cell's text colour, so the top edge would change colour along the row (the state column), and overline and underline colours depend on the terminal and on tmux's terminal features. So the outline is the box's two sides: a lavender `│` in the margin column at each end of the row, reaching the edges the box does, taking no extra line and holding on any background, the cursor's included (#33, #102).
- **Footer.** tmux's status line, content set by the list program (key hints; the `/name` search while typing, `/ag · 1 match: agent-17`, §6.3). Cleared when the list program exits.
- **Dialogs.** tmux popups centered over the whole window, each running an hq dialog (§6.6). The list keeps refreshing underneath; the popup holds all keys and clicks while open.
- **Layout.** The list pane's height is re-applied on every resize: header + 6 rows + footer, 3 rows in a terminal below 24 rows (§6.1, S12); the slot takes the rest. The margins beside the slot are set back to one column each at the same time, since tmux shares a change of width among all panes of a row. The terminal's height is tmux's window height plus the session's status lines, which tmux takes from the terminal, so the classic 80x24 terminal (a 23-line window) shows 6 rows.
- **Agent home windows.** Every agent has a home window in the same tmux session, holding its pane while it is not docked. They are invisible to the user: the footer replaces tmux's window list, and the terminal shows only the dashboard window.
- **Finding the parts.** Like the home windows (3.3), the dashboard window and its panes are found by tmux options hq sets on them: the window is marked as the dashboard, each pane carries its role (list, slot or spacer, the margins beside the slot), and the list program records its process on the list pane while it runs, so `hq` knows whether to start it again. The session's look (colours, margins, titles, a status line that is only the footer) is set on the `hq` session and the dashboard window alone, never on the tmux server's global options, and reapplied on every `hq`.

Satisfies: §6.1, §6.4 (drawn by the list program), §6.6, S1, S3, S6, S8, S12; driver 2.

### 3.2 Platforms

Plain tmux on both platforms ([ADR 0008](../adr/0008-plain-tmux-on-both-platforms.md)). On macOS the dashboard is an ordinary `tmux attach` inside an iTerm2 window; on WSL, the same inside Windows Terminal. The terminal only hosts tmux; everything hq shows is drawn by tmux and the list program, so both platforms share one code path for the dashboard.

**Decision:** tmux 3.4 or newer on both platforms. Notifications come mostly from agents that are not docked, whose panes sit in hidden home windows, and tmux passes their sequences to the terminal only with `allow-passthrough all` (3.4; 3.3 passes only from the visible pane, 3.2a not at all). hq checks the version at install and at start and exits 3 with the remedy (`hq: tmux 3.2a is too old, 3.4 or newer needed (Ubuntu 24.04 ships it)`). WSL baseline: Ubuntu 24.04; macOS gets a current tmux from Homebrew.
Every tmux command hq runs, and the attach of the dashboard, carries `-u`: the list, the slot title and the popups draw lines and marks beyond ASCII, which tmux shows as `_` to a client whose locale (`LC_ALL`, `LC_CTYPE`, `LANG`) does not say UTF-8, as on a Linux shell with no locale set (#41). The terminals hq runs in (iTerm2, Windows Terminal) take UTF-8 whatever the locale says.

**Alternatives considered:** a fallback for older tmux (a bell from the hidden window): a second code path with weaker behaviour, no text, against spec §5 (kind and branch named).

Satisfies: §2, §5 (notifications from hidden panes), §8 (identical behaviour), §11 (prerequisites), S13; driver 4.

### 3.3 Agent registry

**Decision:** tmux is the registry. An agent exists exactly while its home window exists in the `hq` session; what hq knows at launch (name, repository path, sandbox, start time, the `new` marker) is stored on that window as tmux user options, and an `ending` marker while `hq sandbox restart` takes the agent down (sbx lists a stopping sandbox as running for the seconds the stop takes, S9). Every command and the list program read agents from tmux; there is no registry file.
**Rationale:** with no daemon (ADR 0002), the only always-current record of what runs is tmux itself; a separate file would duplicate it and go stale when a window dies outside hq.
**Consequences:** an agent that ended keeps its window, its dead pane kept readable, until it is killed (S7); removing the window frees the name (§4.2). Removing a window ends only the host side of `sbx run`, and Claude keeps running inside the sandbox, so killing an agent first ends its Claude session there (SIGTERM through `sbx exec`, found by the agent id it was launched with), waits a few seconds for it to exit, then removes the window (S6, S10). This holds whatever the pane's state: a pane also dies when only its host-side `sbx run` ends, and Claude then runs on in the sandbox, so an ended agent's session is signalled too, and since there is no pane to watch, the wait asks the sandbox (`pgrep` through `sbx exec`) until the process is gone. Only an agent with nothing left to end in its sandbox is left alone: `sbx ls` lists the sandbox as not running (or not at all) and the session went with it, as the list shows the agent ended (5.1) - its pane dead, or still running while its latest report is older than sbx's answer or the agent is already ended, as when its session's end is reported after sbx's answer: a session that ends as its sandbox stops reports its end, and that report is no sign that the sandbox ran after the answer (#191). Nothing runs there, and `sbx exec` would start the sandbox again. sbx is asked once per kill, before the agents' reports are read, as the list does (#87); the kill waits for that answer as the list does (at most a few seconds when sbx hangs), and when sbx fails or does not answer, every agent's session is signalled. The docked agent is known from where the panes are: its own pane, marked with its id, sits in the slot, and the placeholder waits in its home window; the list's other session state (the cursor) is a session option. Both survive `q` and detach as long as tmux runs (S1, S8, S9). An agent's pane carries what must travel with it when docked (its id, staying readable after it ends, passthrough). Staying readable takes two pane options: the dead pane is kept, and the pane has no alternate screen, because Claude draws in the alternate screen and tmux throws that screen away when Claude leaves it, taking the session with it. It also takes hq's session program, a hidden hq command each agent's pane runs `sbx run` through: when a session is cut off (its sandbox stopped, or `sbx run` ended from outside), `sbx run` resets the terminal (`ESC c`) as it exits, and tmux clears the screen, pushing the session into the history, so the dead pane would show only tmux's `Pane is dead` line. Once `sbx run` has ended, the session program draws the pane's latest lines again at the bottom of its screen, each run of blank lines as one, and exits with `sbx run`'s status. The lines come from the last screenful only, the pane's height up to the last line printed: Claude redraws its whole screen on every resize, as on every dock and undock, clearing the screen first (never the history), and tmux pushes each screen it clears into the history (`scroll-on-clear`), so the lines above the last screenful are Claude's earlier screens, each starting with the same banner and conversation, and taken from there they stacked in the dead pane. Those copies stay in the history: `scroll-on-clear` off would keep them out but lose the last screen when `sbx run` resets the terminal, and clearing the history would take with it what only the history holds, the parts of a long conversation that left the screen. Folding the blank runs keeps the conversation in view: Claude pads the rows above its prompt box, and a dead pane made smaller, as docking does, keeps its bottom lines. The line above tmux's `Pane is dead` line is left blank, since tmux marks it as wrapped and a resize would join the last line drawn to it. A screen that shows the latest lines already, as after most `/exit`s, is left as it is; the history keeps everything, the last screen twice and each screen a resize replaced. Removing a docked agent's window first sends its pane home, so the slot gets the placeholder back (S6). The sort must survive a tmux restart (§6.2), so they live in a small per-user preferences file. Agent state does not live here; it comes from the hooks (section 3.4).
- **Lost agents and `hq restore`** (spec §4.1, S9b, #140): a tmux server that goes (a host restart, `kill-server`) takes every window, so hq knows no agent of it, though each agent's conversation, journal and inbox are kept. tmux stays the registry; what restoring needs that only the window held is kept in the repository's `.git/hq/agents` as `ID.hq`, hq's record of the agent: its name, its sandbox, the tmux server it runs on (the `-L` socket name, `HQ_TMUX_SOCKET`, empty for the default server) and the generation of the hq that wrote it (`generation`, absent in a record written before), JSON, written by hq (never the hook) when it opens the agent's window (`hq new`, `hq restore`) and when `hq sandbox restart` relaunches it, through a temporary file renamed into place, and removed with the agent's other files (3.4). A **lost agent** is a record of this server in a repository hq knows (the primary workspace of each sandbox `sbx ls` lists, or REPO) whose id no window has; a record whose name a window now holds was replaced by that agent and is none, and of two of one name the first counts. The server in the record keeps another server's agents (another worktree's `scripts/local-dev.sh`, a tester) from ever looking lost: they report to the same directory. `hq restore` brings back no lost agent whose record carries another generation than the running hq's, or none (`not restored 42 in app: it was started by an older hq`): its files are its older hook's, which this hq does not read. For the others it reads the agent's journal as `hq sandbox restart` does (3.6), its hook's event files ingested first, and brings one back only when its sandbox is still one of its repository's (`sbx.OfRepository`), the directory Claude last worked in still exists (the worktree the journal gives, through the platform adapter), and its latest report carries a Claude session id; otherwise it reports the reason, `its journal is gone` for an agent whose journal holds no event. A bare `kill-server` leaves Claude running in the sandbox (only the host side of `sbx run` goes), and the resumed session would share its id and its journal, so the lost agents' sessions are first ended as `hq kill` ends an orphan (SIGTERM through `sbx exec`, `pgrep` until gone, only in a sandbox sbx lists as running, since `sbx exec` would start a stopped one). Each is then launched as `hq new` launches one (`launchAgent`), under its own name and id, `--resume <session id>`, no `new` marker, the running hq's generation, and the supervisor's word withdrawn, as a relaunch does; the row reads `starting` with what it last said until the resumed session reports, as after a restart. `hq sandbox restart` restores the lost agents of the sandboxes it restarts, after the start, with the same rule. A lost agent holds its name: `hq new` and the New agent dialog look for one of the name (after `sbx ls`, which they need anyway), and `hq kill` takes one when no window has the name, ending its session where it runs and removing its files.
- **The trace of kills** (spec §4.1 `hq killed`, #147): removing a window and its agent's files leaves nothing behind, so an agent gone from `hq ls` could not be told from one tmux or the user's own hand took away. Every kill goes through `removeAgents`, the one place that removes a home window and the agent's files; after the files go, it appends one JSON line per agent to `$XDG_CONFIG_HOME/hq/kills.log` (default `~/.config`, beside the preferences file): when (`at`), the agent's `name`, `id`, `repo` and `sandbox`, and who asked for it, `by` `cli` (with `command`, `kill` or `stop`), `dashboard` (the Kill dialog's popup, `hq __kill-dialog`) or `mcp` (with `client`, the one `hq mcp` serves, `app`, the name and version from the client's `initialize`, and `caller`, `HQ_AGENT` from `hq mcp`'s own environment, which only a client running inside an agent's session passes on). Each command sets who asks (`deps.killer`) before it kills. The file is the user's, out of every sandbox's reach, so no agent can write or erase a line (7.3); appends take an `flock` on `kills.log.lock`, and past 128 KiB the older half goes, rewritten through a temporary file renamed over it. A kill the trace cannot take ends every agent first, then fails naming them and the reason: the trace never keeps an agent alive. `hq killed [NAME]` prints it, oldest first. An agent that calls `kill` through sbx's gateway is not known: the gateway starts `hq mcp` on the host for the sandbox, outside the caller's session; telling it would take a mark from the caller's own hook (the PreToolUse hook that refuses a kill of itself, #142), which the sandbox could forge.
- **Generation and outdated agents** (spec §3, §5, #165, #194): `version.Generation` is one number compiled into hq, the form of what agents report and of how hq keeps it. Every agent hq starts or relaunches carries it on its home window, in the user option `inbox` (named for the hooks that deliver `hq send`'s messages, which it first marked, ADR 0012, and counted up through the hooks' generations since), and in its record. `agent.FromWindows` compares it for equality: an agent whose window carries another number, or none, is outdated, state `outdated`, with no report of its applied (the look reads no journal of it, ingests nothing, captures no screen of it and appends nothing), its age unknown, branch `-` and the last message `started by an older hq: kill it and start it again` (`a newer hq` when its number is the higher). It stays so whatever its pane does, until it is killed. It sorts before `needs input` and counts as needing the user (`NeedsYou`). `hq go`, docking and the kill (`endAgents`, which removes every file the agent's id names, those of its older hook included, into the trace of kills) treat it as any agent; `hq read`, `hq send`, `hq answer`, `hq code` and a `hq wait` that names it refuse it with `hq: 42 was started by an older hq: kill it and start it again` (exit 1) before they read anything of it, a `hq wait` on every agent leaves it out (`waitedOn`), and `hq sandbox restart` refuses while a sandbox it would restart holds one, before it marks or stops anything. This one rule replaces the thresholds hq read before (hooks that deliver messages, from `1`; that tell a supervised turn, from `2`; that take an answer, from `3`) and their refusals: an agent is current or outdated. The generation was `3` while the hook still wrote its state files, `4` since the journal replaced them (#199); it is `5` since the hook reports a turn an API error ended (StopFailure, #224).
**Alternatives considered:** a registry file in the user's home (duplicates tmux, goes stale). For lost agents: the record in the per-user configuration directory, out of the sandbox's reach (another file to keep in step with the repository's agents, and it would outlive a repository removed without hq); writing the record from the list's refresh for agents an older hq started (writes on every look; the user chose to leave such agents to a relaunch).
**Satisfies:** §4.1 (`ls`, `go`, `kill`, `stop`), §4.2 (name uniqueness and reuse), §6.2 (remembered sort), S1, S7, S8, S9; drivers 1, 3.

### 3.4 State channel

Hooks are injected when hq starts Claude and report the agent's events into the repository's `.git` ([ADR 0009](../adr/0009-hooks-injected-at-launch.md)); no repository setup.

```mermaid
flowchart LR
    subgraph SB["sbx sandbox (one per repository)"]
        C["Claude Code<br/>started with --settings:<br/>env HQ_AGENT, HQ_ID + hook set"]
        K["inline hook<br/>sh, git, cat, mv, cp, mkdir, rm, grep, awk, sleep, cksum"]
        C -- "lifecycle event + JSON payload" --> K
    end
    subgraph RP["mounted repository"]
        F["repo/.git/hq/agents/ID.*: the hook's working files, which the host never reads<br/>ID.last: what its rules read of the latest event it took for the state, and its cksum<br/>ID.ended: the same of the latest turn end<br/>ID.on: it kept an event that left the agent working<br/>ID.owe: tasks Claude owes a turn for<br/>ID.sup: the turn is a supervised turn<br/>ID.acted: a tool of its own ended in the turn<br/>ID.queued: a prompt Claude queued while it works<br/>ID.asked: the cksums of the dialogs it reported and of the holds that started<br/>and hq's: ID.next, the next prompt is the supervisor's; ID.hq, hq's record of the agent (3.3)"]
        I["repo/.git/hq/inbox/ID<br/>one file per message, JSON-encoded<br/>answer.CRC.LEN: the answer to the open question dialog"]
        E["repo/.git/hq/events/ID<br/>one file per event, COUNT.PID<br/>.n: the hook's count"]
    end
    subgraph ST["user's state directory"]
        J["$XDG_STATE_HOME/hq<br/>journals/ID: the agent's events, numbered<br/>journals/ID.reply: the latest reply<br/>journals/ID.ask: what the latest dialog asks<br/>journals/ID.read: what the last append read<br/>counter, lock"]
    end
    K -- "write tmp, rename" --> F
    K -- "write tmp, rename" --> E
    E -- "ingest under the lock, remove" --> J
    J -- "read, fold" --> LP["the look: hq list program / hq ls / hq wait ..."]
    LP -- "append what the screen, tmux, sbx show" --> J
    SEND["hq send"] -- "write tmp, rename" --> I
    I -- "rename out, copy into hook output" --> K
    MCP["hq mcp: new, send"] -- "ID.next before its prompt" --> F
    ANS["hq answer, mcp answer"] -- "write tmp, link" --> I
```

- **Identity.** A fresh id per agent, generated at `hq new`, stored on the home window (3.3) and passed to Claude as `HQ_ID`. Stable across `/clear`; never confused with an earlier agent that reused the name.
- **One copy of the script.** The hook script travels once, in the environment `--settings` sets (`HQ_HOOK`), and every hook runs `sh -c 'eval "$HQ_HOOK"' hq-hook KIND [SEQUENCE]`: seven hooks with a copy each made the settings far longer. The script sends its own errors nowhere, once at its start (`exec 2>/dev/null`) rather than on every command: nobody reads a hook's stderr.
- **Where the hook runs.** In an agent every hook runs inside its sandbox, under the sandbox's `sh`: dash, which compares `-nt` below a second (dash 0.5.12 in an sbx sandbox, checked for #286). In hq's tests and under `scripts/local-dev.sh --stub` it runs on the host, under the host's `sh`: on macOS bash 3.2, which compares `-nt` by whole seconds (#265). What a test that compares files' times does about it: `CODING_STANDARDS.md`.
- **Settings written out as the session starts.** The agent's window does not carry the settings: its command, which tmux bounds at 16 KiB (`command too long`; the same in tmux 3.4 to 3.7c), says `--settings hq-settings:NAME:ID`, and `hq __session`, which runs every agent's session (3.3), puts `state.Settings` for that name and id and the platform's notification sequence in its place before it runs `sbx run`. The settings are then an argument of `sbx run` only, bounded by the 32 KiB command line Windows takes for `sbx.exe` on WSL (the tests hold them to 24 KiB), and the hook script takes no room from the first prompt, which keeps nearly all of tmux's 16 KiB. Only the argument after the first `--settings` is a reference, so a prompt that reads like one stays as typed. `hq new` measures the window's command before tmux does and says by how much the prompt is too long, under the prompt in the New agent dialog (#40).

- **A turn an API error ended (#224).** When an API error ends a turn (an expired login, a rate limit, an overload, ...), Claude Code fires StopFailure in Stop's stead, with the error's kind (`error`, also its matcher) and its error line (`last_assistant_message`, optional; `error_details` optional), and ignores the hook's output and exit code; the event exists since Claude Code 2.1.78 (its changelog), far older than any version hq's rules were verified with, so what an older one does with the name in its settings does not arise. Verified with Claude Code 2.1.326 in sbx with its managed settings, on the operator's host (`internal/state/testdata`, setup N; `qa-artifacts` `issue-224/`): an expired login ended a turn after its second tool call, and the next prompt's turn at its first request, each with StopFailure (`authentication_failed`, `Login expired · Please run /login`, no `error_details`) and no Stop; Claude drew the error line in a reply card and `Once fixed, resend your message` faint in the box. Before #224 hq heard nothing of such an end, so the agent stayed `working`, a message for it waited for a Stop that never came, and `hq wait` did not return. The hook's `fail` takes nothing from the inbox (Claude would drop the output) and reports the end as a stop it does not keep: it writes `ID.ended` and `ID.last` and the event, and drops `ID.on`, `ID.acted` and `ID.queued`; `ID.owe` and `ID.sup` stay, the mark until the next prompt decides it or a session's start or end removes it (3.5), so the idle Notification can tell a supervised turn. Not verified: what Claude does with a prompt it queued during a turn an API error ends; the capture has none. The hook drops it as at any end it does not hand over, so should Claude run it, the agent shows `done` until that turn ends or opens a dialog. The reducer folds it as the latest turn end (`atFail`): `done`, whatever the kind (hq does not tell them apart) and whatever still runs (background work owed, a subagent's open dialog, spec §5 *Background work*), as after a turn the user ended, the last message its reply, which the journal keeps as a Stop's (`state.EndsTurn`), the time from it, and it is the completion number. A message waiting is entered as the agent's next prompt by the next look, as after any `done` (5.1): `WithoutHints` reads the faint line as an empty box. No screen rule: the hook reports both ends seen. `hq explain` names the event `turn end by an API error (KIND)`. Its notification comes at the idle Notification a minute later (3.5).
- **Events used.** Prompt submitted -> `working`; Stop -> `question` or `done`; StopFailure, which Claude Code fires in Stop's stead when an API error ended the turn -> `done`, its last message Claude's error line, whatever the error (below); a dialog opening (PermissionRequest: a question dialog such as AskUserQuestion, or a permission prompt) -> `needs input` at once; the end of that dialog's tool (PostToolUse or PostToolUseFailure) while it is open -> `working`; an MCP elicitation (Elicitation, below) -> `needs input` at once, and its form answered at the agent (ElicitationResult) -> `working`; Notification of kind permission prompt or agent needs input -> `needs input` when no dialog is open; Notification of kind `idle_prompt` -> no state, only the notification of a turn an API error ended (3.5); session end -> `ended` (also detected from tmux and sbx, section 5); SessionStart -> `done`, without a notification, except the new session's start (`startup`) of an agent launched with a first prompt, which stays `starting` from its launch until it reports that prompt (spec §5, S2, #191): Claude Code fires SessionStart before it takes a prompt given on its command line, and the launch's event says that one was given (`prompted`; a launch written before it has none, and is `done` at its start as before). A dialog of Claude's own at that start still gives `needs input` (3.4, below), seen because the look captures the screen of an agent waiting for its first prompt as of one at its prompt. A first prompt Claude never reports (a command of Claude Code's own, a prompt Claude drops) keeps the agent `starting` until its next report or `hq kill`, and a message sent to it waits, with no completed turn counted: no rule of the screen ends that wait, since a first prompt that is only late (a SessionStart hook of 3 s) looks the same (the operator's decision on #191; a rule settled on real captures is #220). A session resumed (`hq restore`, `hq sandbox restart`, which give no prompt of their own) or started over (`/clear`) is `done` at its start. Until the first event an agent is `starting`, and so is one whose latest event hq cannot read: the hook stores what Claude gave it, and a Claude cut off while it fed the hook an event (killed during its SessionEnd) gives a part of it or nothing; the branch and the latest Stop's last message still stand (#73). Verified with Claude Code 2.1.283 in sbx (#124): Claude fires SessionStart about 2 s after `sbx run` starts it, before any prompt, with `source` `startup`; with a PROMPT it runs the SessionStart hooks to their end before it fires UserPromptSubmit (a SessionStart hook made to take 3 s delayed UserPromptSubmit by 3 s), so SessionStart is always a session's first report and never overwrites a later one. Without it an agent started without a PROMPT stayed `starting` with its `new` marker until the user's first prompt, while Claude waited at its prompt. `--resume` fires it with `source` `resume` and the same session id; `/clear` fires SessionEnd (`reason` `clear`) and, at once, SessionStart with `source` `clear` and a new session id. hq's SessionStart hooks match `startup|clear` and `resume`: after each Claude waits at its prompt, so the agent is `done` (but `starting` while it waits for the first prompt hq launched it with, above), the last message `-` for a new agent and the latest Stop's otherwise (after `/clear` this also ends the moment of `ended` its SessionEnd gave, and the session id hq resumes at a restart is the new one). A compaction (`compact`), which may come in the middle of a turn, is not matched. A resumed session starts in the repository, not in the worktree its conversation left (verified: its SessionStart and later events carry the repository as `cwd`), so hq takes the branch, worktree and last message from the report before it, unless that is itself a resumed start (restarted again before any prompt, which keeps the one before), until the next report (the reducer, below). Verified with Claude Code 2.1.283 in sbx (#71): even with permissions bypassed, AskUserQuestion fires PreToolUse and PermissionRequest as its dialog appears, and answering it fires PostToolUse at once; Claude's own permission-prompt Notification ("Claude needs your permission") follows about 6 s after the dialog appeared and only while it is still open, so the hook drops it when the dialog is already reported. The hook takes a tool's end for the state only when it closes the open dialog (the same tool name), so tools ending while the agent works never restart `working` and it keeps its age, and another agent's tool (a background subagent's) does not close the dialog unless it is the same tool. A permission prompt that is granted returns to `working` when its tool has run. A question dialog's PermissionRequest (matcher `AskUserQuestion`) also runs a second hook, of kind `hold`, with a `timeout` of 86400 s, which writes nothing and holds for hq's answer (*Answers*, below). PreToolUse of hq's `kill`, `answer` and `send` runs a hook of kind `refuse`, which reports nothing and denies a call naming the agent itself (3.12, #142).
- **MCP elicitations (#100).** Verified with Claude Code 2.1.302 (#89, #100; payloads in `internal/state/testdata`): Claude runs the Elicitation hooks before it draws an MCP server's form and draws it as soon as they end with no decision, so hq's Elicitation hook only reports: it writes the event as the agent's state, as the PermissionRequest hook does for a dialog, prints the `needs input` notification (3.5) and no decision, and never holds, so the form is drawn at once (a hook that held would show the user the tool's card and `running Elicitation hooks…` in place of the form, #89). The agent is `needs input` at the Elicitation event, about 6 s before Claude's own Notification for it (`elicitation_dialog`, and `elicitation_url_dialog` for a URL-mode form), which hq's Notification hook no longer matches, so it adds nothing. The payload has `mcp_server_name`, `message`, `mode` (`form` with `requested_schema`; `url` with `url` and `elicitation_id`) and no `agent_id`, the agent's own and a background subagent's alike, with the main turn's `prompt_id`. Answered at the agent, accepted, declined or cancelled (Esc included), the form fires ElicitationResult (`action`, and `content` on accept) 7-61 ms after the answer; a URL-mode form fires it when accepted, though Claude Code then keeps a `waiting for completion` panel (`Reopen URL`, `Skip confirmation`) in place of the prompt box until the server confirms or the user skips or cancels it, past the turn's end (the `elicit` server sends no completion); hq shows the agent as its hooks say meanwhile, `working` and then the turn's end, and reads nothing of that panel. The hook writes it only while a form is open: the agent is `working`, with its turn's last message, as after a PostToolUse at a dialog, and the turn counts as acted on (no early Esc rewinds it, below). A form that another Elicitation hook answers (one in the user's own settings) is never drawn and fires no ElicitationResult: the end of a tool of that server (`mcp__SERVER__…`) closes it, and the screen's Claude at work (the dialog verdict, below) stays the fallback. Whose it is follows the rule of a subagent's dialog (below): no PreToolUse hook is added to tell them apart, which would fire on every tool call of every agent and not tell the agent from a subagent calling the same server. The form's schema is read on the host for `hq read` (3.12): its properties in their order, those of type `string`, `number`, `integer` or `boolean`, their options from `enum` (titled by `enumNames`) or `oneOf`'s `const` and `title`, and their default; a property hq cannot read in full (a list, a nested object) is left out and keywords it does not know are ignored, so a schema read in part still gives the message and the fields it could read. hq answers no elicitation: a hook can answer one only while it holds, and holding hides the form from whoever is at the agent; answering waits for Claude Code to draw the form while Elicitation hooks run, as it draws AskUserQuestion's dialog while PermissionRequest hooks run ([anthropics/claude-code#103115](https://github.com/anthropics/claude-code/issues/103115), #95).
- **Background work.** A turn that ends while background subagents still run is not the agent's end (spec §5, #38): Claude goes on by itself when they finish. Verified with Claude Code 2.1.291 (#38): the Stop of such a turn carries `background_tasks`, `[]` when nothing runs and otherwise one entry per running task (`{"id": ..., "type": "subagent", "status": "running", "description": ..., "agent_type": ...}`; a background shell command the same with `"type": "shell"` and its `command`, a running workflow with `"type": "workflow"` and its `name`, its agents not listed; a watch with `"type": "monitor"`, #62 below); the only status ever seen is `running`, a finished task is not in the list, and nothing else in the payload differs. The payload is one line of compact JSON. When background work ends, Claude wakes the agent with a UserPromptSubmit whose `prompt` starts with `<task-notification>`, then Stop; a wake-up can arrive in the middle of a turn, so the two are not paired, and a prompt the user sends while a subagent runs ends with a Stop that still lists it. With several subagents (three, finishing 25 s apart) Claude runs one wake-up turn per finished subagent, and each intermediate Stop lists the ones still running. The Agent tool has no foreground mode in a default session: asked to wait for a subagent, Claude still ends its turn with the subagent listed and is woken later (a foreground subagent, seen only with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, ends before the turn's single Stop with `[]`). No `idle_prompt` Notification came while a subagent ran. SubagentStart and SubagentStop fire too but are noisy (a SubagentStop with an empty `agent_type` follows every main Stop), and the Agent tool's input never says that a launch is in the background; the list at Stop makes counting unnecessary. So the hook decides at each Stop: when a task of `background_tasks` has the status `running` and is neither a shell command nor a watch (a `monitor` task) the agent itself started (an agent that left a dev server running would never be `done`, nor one that published an artifact; a subagent's command or watch, below, counts), and the turn did not end with a question, the Stop leaves the agent `working`. The hook walks the list in awk, reading each task's `type` and `status`; text inside a task's strings is only ever data. Such a Stop is reported and kept beside the hook's note of its latest report (`ID.on` marks it), and the note is left alone: the state's time is the user's prompt, so `AGE` keeps counting from there, and the hook prints no notification. Claude's wake-up while the note says working is kept too, for the same reason; any other prompt, Stop or session event is taken as before and removes `ID.on`. When the note does not say working at such a Stop (a Notification's `needs input`, a dialog whose end was never reported), the Stop is noted as well, and the reducer takes it for working, from then on; but never over a subagent's dialog (a PermissionRequest carrying `agent_id`, as a subagent's tool events do), which is still open: the agent needs input until it is answered, and its answer leaves it working at its prompt, `ID.on` still beside it. A question, the `[]` Stop of the closing turn, and a wake-up after `done` or `question` are ordinary reports: `question` with its notification, `done` with its notification, `working`. The reducer applies a kept event only where the hook can have meant it: a Stop beside a report that says working, or that is the report itself; a wake-up beside one that says working. Its time is the agent's latest report, which keys the evidence a look appends (below); the report's time stays the moment the state counts from. An agent whose latest report is such a Stop is `working` at its prompt: its screen looks exactly like a rewound turn's (below), so it is not read at all until the next report, and Esc there, which fires no hook and does not stop the subagents, changes nothing. A session that starts, resumes or ends removes `ID.on`, so the subagents of the session before are forgotten; one that outlives `/clear` wakes the new session (verified: SessionEnd `clear`, SessionStart `clear`, later UserPromptSubmit and a Stop with `[]`), which reads as any prompt and turn end. hq sets no timeout: if Claude never runs the closing turn the agent stays `working` until its next event or its end. **Work that finishes together.** Subagents that finish within a second or two of each other still get a wake-up turn each, and the list is already empty at the Stop of an earlier one (verified, three finishing together: Stop with one running, Stop `[]`, wake-up 20 ms later, Stop `[]`; the same when a subagent is stopped: Stop `[]`, then a wake-up with the status `killed`). Every wake-up names its task (`<task-id>`), also with a prompt of the user's queued at the same time (verified: two UserPromptSubmits, never one for both). So the hook keeps the ids of the tasks that run, less those Claude woke for, in `ID.owe`: those it saw running at a Stop, and those the agent started, taken from the PostToolUse of the tool that started them (verified: the Agent tool's response is `{"isAsync":true,"status":"async_launched","agentId":ID,...}`, the Workflow tool's `{"status":"async_launched","taskId":ID,...}`, a foreground subagent's `"status":"completed"`; a subagent's own tool events carry `agent_id` beside `hook_event_name`, and what a subagent starts is not the agent's), so background work is known before any Stop lists it, as when the user interrupts the turn that started it. The ids are kept one a line, rewritten at each Stop by the same awk, and a Stop with any id left is kept like one with a task running: `working`, no notification. That also covers a subagent the user has stopped, and subagents that end during a turn of the user's: the user's prompt keeps the ids. The reader tells the two apart by the kept Stop's own list (`Reduced.Owed`: nothing running). For an owed agent the wake-up comes at once or not at all, so its screen is read again: at rest (the prompt box, no `esc to interrupt`, no spinner, whatever the box holds; `state.Idle`) and unchanged for 2 s, the agent is `done` with its turn's message, since it was first seen at rest, appended and entered like a rewound turn (below; `AtRest`, then `TurnNotTaken`), without a notification, as no hook runs; one `hq ls` looks again after 2 s for it, as for a rewind. So a wake-up that never comes cannot leave an agent `working` with nothing running. An id that no longer runs is marked in the file once it has held back a turn end (`!ID`). A marked id holds back another only when Claude woke for one of the listed tasks since the last Stop (the wake-up leaves a `+` line, which the next Stop uses up): the wake-ups for tasks that ended together follow one another, so one that did not come by then is not coming, and it holds back one turn end. The user's next prompt drops the marked ones too; a wake-up that names no task drops them all, as nothing can be told paid, and so does a session's start or end. The task a wake-up pays is the one named first in it; an id further down is the subagent's report, only ever data. Costs of the bound, both needing two things at the same moment: when tasks end together and a wake-up for something not listed (the agent's own shell command ending) comes between their wake-ups, or another hook blocks a Stop so that Claude stops again with no wake-up in between, the marked id is dropped and the agent is `done`, notified, and `done` again at the wake-up that follows. The other way round (any wake-up keeping every marked id) would let one wake-up that never comes silence every closing turn until the user's next prompt, which is the worse fault. **A subagent's shell command (counted, #60).** A subagent that starts a shell command in the background and stops is reported finished, with an interim result, and the list then holds the `shell` task alone; when the command ends Claude wakes the subagent, which goes on and reports again under the same id (verified with Claude Code 2.1.291, #38: Stop with the subagent, PostToolUse of the subagent's Bash with `"backgroundTaskId":ID` and the subagent's `agent_id`, wake-up, Stop with the shell alone, 55 s later SubagentStart, wake-up, Stop `[]`; again on 2.1.295, #60: the subagent's console says `Agent "..." finished`, footer `1 shell still running`, the subagent with an empty circle on Claude's agents list, so no source, screen included, lists it as running). Neither sanctioned way for a subagent to wait keeps it running: a foreground `sleep` is blocked by Claude Code, which points to `run_in_background` or the Monitor tool, and the Monitor tool's until-loop is reported as a task of its own, a `monitor` (the console says `1 shell, 1 monitor`; first taken for a second `shell` task, set right in #62), the subagent ending its turn the same way; so this is the shape of every subagent waiting on anything slow, a CI run above all. The hook therefore counts such a command: the PostToolUse of a subagent's tool (it carries `agent_id`) whose response names a task, `backgroundTaskId` for Bash, `taskId` for the Monitor tool (read from Claude Code 2.1.296's tool definition; seen in a payload with 2.1.302, `testdata/post-tool-subagent-monitor.json`, #99), adds a line `~ID` to `ID.owe`; at a Stop a running `shell` or `monitor` task whose id has such a line counts as running work, and the line is kept, while a line whose task the Stop does not list running is dropped, so an id recorded for a command that ended before the next Stop cannot hold the agent `working` by itself. Claude wakes the subagent for the command, not the agent, so no turn is owed for it: the subagent, woken, is listed as `subagent` until it reports, and the rules above take it from there. A `shell` task with no such line, the agent's own, stays uncounted (and so does a `monitor` task, since #62 below). The reader (`Reduced.Owed`) reads the same lines, so an agent whose subagent's command runs is not owed a turn and its screen at rest is not read. The user's prompt keeps the lines, a wake-up that names no task and a session's start or end drop them, as they do the other ids. The price, chosen by the project lead: a subagent that leaves a dev server running and reports looks exactly like one waiting on its command (the wake-up's note is the same interim one, and a subagent's final report cannot be told from it), and its agent stays `working`, with the subagent's last message in `LAST`, until the server ends; this was built in #38 and reverted for that reason. A `done` with a notification while the work goes on, recurring at every wait for CI, is the worse fault, and a server a subagent left behind is a cleanup bug better seen than hidden. A command a subagent only watches was seen to end without the subagent being woken again (#60): its line goes when its task leaves the list, as any other. **The agent's own watch (not counted, #62).** The task types seen so far are `subagent`, `shell`, `workflow` and `monitor`. A `monitor` task is a watch: the Monitor tool's until-loop, or the watch Claude Code arms by itself when the agent publishes an artifact with the Artifact tool (verified with hq 0.5.0, 13.10.2026: the Stop after the agent's final report carried `"background_tasks":[{"id":"sjbxxhmjo","type":"monitor","status":"running","description":"live updates for artifact https://claude.ai/artifact/<id> (auto-armed on publish)"}]`, nothing else; the Artifact tool's PostToolUse says nothing of `async_launched`; the agent's own `/tasks` lists it under *Background - System tasks*, "auto-replying to comments"). Such a watch runs until the session ends or the user stops it, and wakes the agent only when somebody comments on the artifact, so with the rule above every turn of that session ended `working`, with the final report in `LAST`, `hq wait` never returning and no notification: nothing in hq could end it, as `Reduced.Owed` was false. So a `monitor` task joins `shell` in the rule: a running task counts as owed when its type is neither `shell` nor `monitor`; a `shell` or `monitor` task counts only when `ID.owe` holds its `~ID`, a subagent's (the `K=tool` branch is unchanged: nothing is recorded for the artifact watch, and a subagent's Monitor keeps recording its `taskId`), and `payload.busy` mirrors it. Considered and not chosen: a positive list (`subagent` and `workflow` count, anything else only with `~ID`), which matches the spec's wording but would make a new task type of Claude Code's that is real work end `done` early, the worse fault; unknown types keep counting. **The agent's own tasks (shown, #78).** What the rule above does not count is shown beside the state, never changing it (spec §5 *Own tasks*): a `shell` or `monitor` task the latest Stop lists `running`, whose id has no `~ID` line in `ID.owe`, is one of the agent's own tasks, shown by the task's `command` (a shell) or `description` (a watch) from the same payload; one whose id has a `=ID` line (the agent's own Monitor watch, below) is a watch, by its description, whatever type the Stop gives it. `payload.ownTasks` and `payload.busy` read the same list and the same `~ID` lines, one the inverse of the other for `shell` and `monitor`, so a change to one is a change to both; the `=ID` lines change only how an own task is shown, never whether it is one. `state.Reduced.OwnTasks` gives them only while the report is `done` or `question` from that Stop as the latest event: a Stop the hook kept leaves the report `working`, and a prompt, a dialog, a SessionStart or a SessionEnd has no turn end of its own. The row model keeps them only while its state is still that report's, the same state since the same moment (`agent.keepOwnTasks`), so a turn end read off the screen (`TurnEnded`, an Esc), a dialog of Claude's own, an ended agent and a report of the session before show none, and the JSON field and the LAST prefix always agree. The artifact watch is left out by its description ending `(auto-armed on publish)` (the payload above), the only thing in the payload that tells it from a watch of the agent's own; the description is looked at whatever the task's type, as Claude Code 2.1.302 lists a Monitor tool's watch as a `shell` (below) and may list the artifact watch so too. Should Claude Code describe it otherwise, it shows as an own task: fail-safe, since no state depends on the list, and preferred to dropping every `monitor` task, which would hide the watches the agent keeps itself. The list is that turn end's, refreshed by the turn Claude takes when a task ends: a task stopped by hand without a turn stays listed until the next turn end (spec §5). **The agent's own Monitor watch (marked, #99).** A watch the agent keeps with the Monitor tool is not a `monitor` task in Claude Code 2.1.302 (QA of #97, `testdata/stop-own-monitor.json`): its Stop lists it as `"type":"shell"`, with a `b`-prefixed id as a Bash command's, the Monitor's `description` and its `command`, while Claude's footer counts it as `1 monitor`; a subagent's watch is listed the same way (`testdata/stop-subagent-monitor.json`). Only the tool's PostToolUse tells them apart: `"tool_name":"Monitor"` with `"tool_response":{"taskId":ID,...}` (`testdata/post-tool-own-monitor.json`), where Bash has `backgroundTaskId`. So the hook's `K=tool` branch, for a Monitor tool's end with no `agent_id`, adds a line `=ID` to `ID.owe`. It is told by the tool's name, not by `taskId` alone: the Workflow tool's response carries a `taskId` too, with `async_launched`, and stays owed work, recorded as a plain id as before. The mark is never work: `busy` in the awk and `payload.busy` do not read it, the Stop's rewrite does not take it for an id owed a turn, and the checks that ask whether anything is owed a turn (the supervised mark, 3.5) look for a line that is not `=ID` (`grep '^[^=]'`, where an empty file was enough before), so a turn end that leaves only the agent's own watch running is the agent's end and notifies as before, supervised or not. It lives as `~ID` does: the Stop that rewrites the list keeps it while that Stop lists its task running as the agent's own and drops it at the first that does not; the user's prompt keeps it, and a wake-up that names no task and a session's start or end drop it with the rest. The reader (`payload.ownTasks`) then shows that task as a `monitor`, by its description: `1 monitor · ` in LAST, `own task: monitor  <description>` in `hq read`, `"type":"monitor"` in `own_tasks`. The `monitor` type is still what the artifact watch has (#62), and a `monitor` task is shown by its description should Claude report one; the artifact watch is left out by its description whether marked or not. The mark costs the hook about 200 bytes: its script was 7805 bytes then, under the budget a unit test holds it to (3.12 for that budget now). **A turn the user interrupted.** Such a turn is `done` from its screen (below); the hooks know nothing of that, and Claude's wake-up, kept beside the report, leaves the report's time, the interrupted prompt's. The reducer sees the turn end the journal holds since that prompt (`TurnEnded` of an earlier report), so the agent works since the wake-up: the time of the wake-up's report, which the first look to see it appends (`WokeUp`, with that time), for the reports after it (a kept Stop, a later wake-up of the same work) and for every other process. If no hq looked during the closing turn, the time stays the interrupted prompt's. The same event dates an agent woken late after the 2 s rule above made it `done`. The id of a started task is appended to `ID.owe` while a wake-up may be rewriting the file (read, then rename): an id lost that way is learned at the turn's Stop as before, unless the user interrupts that turn.
- **Turns the user ends.** Some turns end at the user's hand with no hook at all: cancelling a dialog with Esc, interrupting a turn at work with Esc, and refusing a permission prompt (Esc or No) fire no PostToolUse, PostToolUseFailure or Stop, and Claude's `idle_prompt` Notification comes 60 s after a Stop, never after these (verified with Claude Code 2.1.283 in sbx, #71, #72). Claude then waits at its prompt. While a turn is at work Claude's footer offers `esc to interrupt`, so a working agent is never read as ended, whatever its output holds. The moment hq first saw it and the last message are appended to its journal (`TurnEnded`, based on the report it overrules), so `AGE` counts from then in `hq ls` and the list alike, and the agent stays `done` whatever its screen shows of the turn until the next hook report: the next prompt appears on the screen a moment before its hook reports, and the agent does not flash back to the state the turn end overruled (its screen is still read for a dialog of Claude's own, below). It sends no notification: no hook runs, and the user is at the agent (spec §5). The lines matched are Claude Code 2.1.283's, recorded as test fixtures; a Claude that draws them otherwise leaves the agent as its hooks said, never a false `done`. The 500 ms keep a screen that lags behind the hooks from overruling them.
- **The screen with subagents running.** Claude Code 2.1.291 draws Claude's agents list below its footer while subagents run: `● main`, then a line for each subagent (`◯ general-purpose  Run the tests   7s · ↓ 26.5k tokens`, its time counting), so the prompt box is found above Claude's agents list, however long (recorded as test fixtures); `hq send` needs it to type a message into the box of an agent working only on subagents (it sits at its prompt: the box at rest and empty, Claude's faint suggestion aside). The turn Claude wakes itself for shows no `❯` line, only `● Agent "..." finished`, so a line of a turn the user ended earlier can still stand above the box with nothing of the user's below it: while an agent works on a turn Claude woke itself for (the wake-up kept beside the latest report, or taken as the report after `done`, a question or a dialog), such a line is its turn's end only as the last thing Claude said: with a bullet line (`● `) below it, the wake-up's notice or a reply, it is an earlier turn's (`state.EndedLast`; a screen recorded as a test fixture).
- **Rewound turns.** An Esc early in a turn, before Claude has committed anything (about 2-3.5 s into a turn without tools), rewinds it instead: the prompt leaves the transcript and goes back into the input box, and Claude prints no line and runs no hook, so the screen looks like Claude waiting at its prompt after the previous turn (verified with Claude Code 2.1.283 in sbx, #99). No single screen tells this from a turn at work: the footer drops `esc to interrupt` while the user types into the box and in a narrow pane (50 columns), and Claude shows no spinner while its reply streams. What does tell is that a turn at work keeps changing its screen (the spinner redraws several times a second, the reply grows; in the samples taken, a working agent's screen never stayed the same for more than about half a second), while a rewound one stays still. So a `working` agent's screen is at rest when it shows the prompt box at the bottom, a footer without `esc to interrupt`, no spinner line (a glyph and a word ending in `…`, as `✶ Brewing…`) since the last prompt, and in the box nothing or the prompt the hooks reported (`UserPromptSubmit`'s `prompt`, whitespace aside), which is what the rewind puts back; text the user typed during the turn, or a `/` menu that hides the turn, is neither. The first look that sees it at rest appends the moment and a fingerprint of the screen (`AtRest`), based like `TurnEnded` on the report; a later look, from any process, that sees the same screen at rest 2 s or more after it makes the agent `done` with `Interrupted`, since that first moment, and appends that decision (`Rewound`). A screen that changed in between starts over. The list looks every 250 ms, so it shows the end within about 2 s; `hq ls`, which looks once, looks again after 2 s when an agent's screen is at rest with its prompt back in the box, so a single `hq ls` shows it too (with an empty box, as after the user cleared it or while a narrow pane streams, it does not wait, and the next look decides). A rewind right after a turn the user ended leaves that turn's `Interrupted` or declined line above the box, which alone would read as this turn's end; so when the box holds the reported prompt and the last prompt shown sent above it is another, the line is taken for the earlier turn's and the rule above decides (an interrupt that puts its prompt back in the box leaves it sent above too; with the box emptied the two cannot be told apart, and the agent shows `done` at once, with the earlier line's message).
- **A turn Claude has acted on (#77).** Only an early Esc rewinds a turn, before Claude has committed anything, so once a tool of the agent's own has ended in the turn a screen at rest is no rewind. It is not a safe sign of a turn's end either: in the sbx template (fullscreen, the `clean-view` mod, no `esc to interrupt`) a working agent was read at rest, unchanged for 2 s, 8 s into a silent foreground Bash command that a run of earlier commands had preceded, and shown `done` with `Interrupted` for the 2.5 minutes until its next hook report. The screen hq read then was not captured, and in captures of the same command (Claude Code 2.1.301, a fresh session, an agent of hq's at 80x24, a cold page cache) the spinner showed on every frame. So the hook marks the turn when a PostToolUse or PostToolUseFailure without an `agent_id` comes in: `ID.acted` beside its note, which leaves the note and the agent's time alone, and which the next prompt, Stop or session event removes (a wake-up kept while the agent works goes on with the same turn and leaves it, and so does a prompt Claude queues, below); the mark holds the turn's `prompt_id`. While the mark is there, or after a dialog of its hooks' that the screen saw answered (*The dialog verdict*, which before ended no turn at rest at all), a screen at rest ends the turn only when it shows a tool the user cut short, the one Esc of such a turn that prints no line in the sbx template: the turn's card is the last thing Claude drew at the left edge above the box, collapsed to its summary and marked `×` (`│ ▸ 2 komendy · × · 5,1 s │`), and it stays so for 2 s like a rewind. A tool at work keeps its card open with the spinner below it, a command that failed marks the open card `×` while the turn goes on with its spinner, and a turn that ended by itself has its reply below the card; an Esc while Claude thinks or writes after a tool prints `⎿  Interrupted`, which the rule for turns the user ends reads. Before the turn's first tool has ended (a silent first command, or a turn spent on a foreground subagent, whose tools carry `agent_id`) there is no mark, and the rule for rewound turns stands.
- **A prompt Claude queues (#82).** A prompt typed while the agent works is queued by Claude, and Claude Code runs UserPromptSubmit when it queues the prompt, not when it takes it (verified with Claude Code 2.1.301 in the sbx template, #82, against the transcript's `queue-operation` lines: the hook 6-9 ms before the `enqueue`, none at the `dequeue`). Claude takes it in one of two ways. At the next end of a tool of the agent's own it takes it into the turn at work (`remove`, a `queued_command` attachment, one Stop). When no such tool ends before the turn's Stop, it takes it right after that Stop as a turn of its own, after any slash command queued before it (`/clear`: SessionEnd `reason` `clear`, SessionStart `source` `clear`, then the prompt), and no hook reports that turn until its first tool ends or its Stop. Prompts queued together are taken together, as one turn. Before this the agent showed `done`, with the message of the turn before, for the whole of that turn. Every event of a turn carries its `prompt_id`, the queued prompt's UserPromptSubmit too, which carries the id of the turn at work, while a prompt that starts a turn gets an id of its own, and the queued prompt's turn runs under a third id that first shows on its tool events and its Stop. So the hook takes a prompt for queued when its note says working and the prompt's `prompt_id` is the note's or `ID.acted`'s (a turn taken from the queue is known by its first tool's end). It reports the prompt as before, keeps a copy as `ID.queued`, and leaves `ID.acted` alone: the turn at work goes on. A tool of the agent's own that ends drops `ID.queued`. A Stop the hook blocks to deliver messages goes on with the same turn, and Claude takes nothing into it (verified: the queued prompt was dequeued after the second Stop), so the hand-over waits for the next Stop. A Stop with the same `prompt_id` as `ID.queued` hands over: it is reported and noted as the latest turn end (`ID.ended`), removes `ID.on` and `ID.acted`, and makes the note the queued prompt's; the reducer has the agent work on it from the Stop. The agent is then `working`, the prompt that turn runs on, and no notification fires. `ID.queued` stays, its id now `ID.ended`'s, so that a SessionEnd `clear` right after leaves every file alone, and the SessionStart `clear` after that reports the queued prompt again with the new session's id (for `hq sandbox restart`, 3.6), dated from that start, a few milliseconds later. Any other prompt, Stop or session event drops it. A Stop with another `prompt_id` is an ordinary report. **Esc with a prompt queued (#88).** The user interrupts the turn at work with Esc, which fires no Stop, and Claude runs the queued prompt at once as a turn of its own (the dequeue 60 ms after the Esc), under a `prompt_id` of its own, with no hook until its first tool ends or its Stop; the latest report was the queued prompt as reported when it was queued, so hq showed `done` with `Interrupted` from the Esc (the screen's line, seen against that report) to that Stop, and `hq wait` returned at the Esc. Two things hand over then. The screen: Claude Code 2.1.302 in the sbx template draws the prompt it took in one of two ways (`state.TookQueued`, fixtures `screen-fs-queued-*`). With the interrupted turn's reply streaming, the queued line above the box goes and no `❯` line is drawn: only `⎿  Interrupted` and, below it, Claude at work on the queued prompt (its spinner, then its reply or card), with no prompt of the user's between; a wake-up turn looks the same and the hooks tell it (`Reduced.Woken`). With the interrupted turn still thinking (2.1.301 in the issue's run too), the prompt is drawn sent, as `❯` and its text right below the `Interrupted` line, with Claude at work below it. While a prompt is still queued it is drawn as a `❯` line right above the box, with `ctrl+x ctrl+s to send now` under it and nothing of Claude's below, so neither way reads it as taken, and the line above it counts for nothing. So the look, seeing that while the journal holds the prompt queued (its `prompt_id` not the latest Stop's) beside a report that says working, appends that Claude took it (`TookQueued`), which hands the state over to it: `working` on the queued prompt since then, in every process, and a turn end seen for the report before falls away; hq touches none of the hook's working files for it (#199): the hook hands over by itself at the turn's first tool, below, and its notes decide nothing on the host. A look in the moment between the Esc and the dequeue sees the line alone and appends a turn end; the next look that sees Claude at work on the queued prompt hands over all the same, and the turn end, based on the report before, falls away. The hook: the end of a tool of the agent's own whose `prompt_id` is not `ID.queued`'s (the note's too), with the copy pending and no wake-up kept in `ID.on`, is the first event of that turn, and hands over the same way (less `ID.ended`), dated then, for a look that never saw the screen; `ID.acted` is then that turn's. A wake-up kept while the turn at work went on (`Reduced.Woken`) looks the same on the screen and carries a `prompt_id` of its own, so neither side hands over while one is kept: the agent stays on the turn at work's report until the queued turn's Stop. No PreToolUse hook is added for it: it would run on every tool call of every agent, and the screen shows the hand-over within one look. A queued turn with no tools is handed over by the screen alone; unseen, it stays `working` on the earlier report until its Stop, which is right in state. Esc twice (the queued turn interrupted at once) leaves two `Interrupted` lines and Claude idle: `done`, `Interrupted`, whether or not a look saw the first. Not covered: a `/clear` queued before the prompt and then Esc (the SessionEnd and SessionStart of the `/clear` are ordinary reports, as `ID.queued` is not taken at a Stop). a prompt queued in a turn taken from the queue before any tool of that turn has ended, whose id no hook has reported yet, is taken for a turn of its own, and that turn's end is `done` as before. Esc on a turn taken from the queue before any tool of it has ended (Claude puts its prompt back in the box), then the box emptied and `/clear` at the idle agent, finds `ID.queued` still there, as no hook fires for any of it: the agent reads `working` on the stale prompt again until its screen at rest ends that as a rewind (`done`, `Interrupted`; 10 s after the `/clear` in a run, the status line's animation keeping the screen from staying still for 2 s, #79). The race where a prompt is queued between Claude taking what was queued at a tool's end and that tool's PostToolUse hook (about 70 ms) is not covered either.
- **Claude's own dialogs.** Claude Code draws some dialogs of its own in place of its prompt box, outside any turn, and no hook reports them: at a session's start ("Make auto mode your default permission mode?", trusting the folder; Claude Code 2.1.285, #29) and after a turn, opened by a slash command (`/effort` asks "Change effort level?" when the conversation is cached for the current level; `/model` shows its picker; Claude Code 2.1.300, #66). Until the user answers one, Claude takes no prompt. So the look also looks at the screen of every agent waiting at its prompt (`done` or `question`, by its hooks or by a turn end hq saw, or `working` only on background work, where nothing else on its screen is read; #70), in the same tmux call as the others, once its report is 500 ms old (`state.OwnDialog`): with no prompt box on the screen, below the last rule (a line of `─`, or of `▔`, which Claude Code 2.1.300 draws above a dialog after a turn and which may carry text such as `● high · /effort`), a title, a text and two or more options on consecutive lines, one marked `❯`, their numbers and a scroll arrow aside. While it shows one, the agent is `needs input`, with the title as its last message, and `hq read` gives the title, the options and the text (`asks`). The moment hq first saw that dialog is appended to the journal (`OwnDialog`, based on the report, with a fingerprint of the dialog's title and text, so moving the cursor, scrolling its options or resizing the pane keeps it), so `AGE` counts from then in every process and `hq wait` returns the agent once, numbered by that event (Changes after a cursor). A look that finds the agent at its prompt again appends that it is gone (`OwnDialogGone`), so a dialog opened again during the same report counts from when it is seen; the agent is then as its hooks or its turn end say, with their moment, so answering a dialog returns the agent in the state its hooks or its turn end say, numbered by the event that closed the dialog, once. Closing such a dialog fires no hook, so a message left meanwhile goes with the agent's next prompt, and `hq send` says that instead of "when it stops". No notification is sent for it: notifications come from Claude's hooks (ADR 0010). `hq answer` picks its options with keys (below, ADR 0014). When the capture fails, a dialog the journal holds open for the agent's current report stands, since its moment, as a turn end hq saw does, so the row does not drop back to `done` for one look; what it asks is not kept, so `asks` is null until the next look sees it. The cost is one screen capture per look for every agent at its prompt, all in the one call (about 2 ms for 20 screens with tmux 3.6). Claude's agents list, which Claude Code draws below its footer while subagents run (`● main`, then a row for each subagent), is no dialog, with the cursor on it too: in 2.1.326 a `↓` from the box puts a `❯` on one of its rows, and the mode line reads `↑/↓ to select` or `enter to view · x to stop`. The rows of Claude's agents list, the one with the cursor on it included, count as that list, not as the footer, so the box above them is found (below it at most four footer lines: a notice, the status line, the mode line and the Tools mod's line). `Enter` on a subagent's row of Claude's agents list opens that subagent's view in the pane: its transcript, and a box of its own whose upper rule carries the subagent's description, the one it was started with (`──── Run the tests ─`). That box is not the agent's: no dialog is read there, and the readers of the agent's own turn (at rest, idle, ended by the user) find no box there, as before, since nothing above it is the agent's. Verified with Claude Code 2.1.326 in the sbx image's managed settings, at 100x30, 80x24 and 40x30, with and without the notice line (#225, `screen-agents-*`); the picker of `/model` opened over Claude's agents list is still read as a dialog, and hides that list. The rule is built on captures of the real dialogs (`internal/state/testdata/screen-own-*.txt`), and no other captured screen matches it but an MCP elicitation, which Claude Code 2.1.301 draws the same way and the hooks report (below).
- **The dialog verdict (#70).** Whether an agent is at a dialog, whose, since when and what it asks is decided in one place, the agent's dialog verdict (`agent.Dialog`): the hooks' (a PermissionRequest, or a Notification with no dialog open), a subagent's, Claude's own (above), or none. A subagent's dialog is told by its event: its PermissionRequest carries `agent_id`, as its tool events do; its MCP elicitation carries none, the same payload as the agent's own, its Elicitation event and Claude's Notification alike (verified with Claude Code 2.1.301 and 2.1.302, a background subagent calling an MCP tool that elicits, #70, #89), so a dialog the hooks report while the agent waits at its prompt on background work (beside the turn end the hook keeps) is a subagent's, as the agent has no turn then. Limit: a subagent's elicitation while the agent still works on its own turn cannot be told from the agent's own and counts as the agent's, so the screen may close it when it shows the agent at work. `hq read` hands it the report's detail and shows the asks it gets back (the detail's for the hooks' and a subagent's, the screen's for Claude's own); `hq send` words its answer from it. The rule: **the hooks open `needs input`; the screen may close it on clear evidence; an unclear screen keeps it.** Claude's own dialogs aside, the screen never opens one. A dialog the hooks reported closes when the screen shows Claude at work (`state.AtWork`: the footer offers `esc to interrupt`, or the spinner shows above the box since the user's last prompt with any label, `^[·✢✳✶✻✽*] .*…`, which a finished turn's `✻ Worked for 7s` and a main agent's `✻ Waiting for 1 background agent to finish` do not match; the spinner is the last line Claude starts at the left edge above the box, as only indented lines follow it (a tip, the todo list, the effort), so a line of a reply that reads like one, indented under its bullet or in a card, is not): the user answered it and Claude works on, as after an MCP elicitation, whose answer no hook reports, or a long tool approved in a permission prompt, whose PostToolUse comes only when it ends. The agent is then `working`, since the dialog's report, with the latest Stop's message as its last (`state.Reduced.LastStop`), as after a PostToolUse; `hq wait` does not return it. The moment hq first saw it is appended to the journal (`AtWork`, based on the report), so a later look at a screen that tells nothing keeps the agent working, and from then on its screen is read as any working agent's, with one exception: a screen at rest is no rewind for it (only an early Esc rewinds a turn, before Claude has acted on it, and a dialog means it has), so the bare box, which a reply streaming shows too, closes nothing by this path either (a tool the user cut short still ends the turn, as for any turn Claude has acted on, below); the lines Claude prints for a turn the user ended still end it, and its hooks' Stop does. Anything else keeps `needs input`: the dialog itself, a narrow pane (its footer drops the hint), and the bare prompt box, which a reply streaming shows too (Claude Code 2.1.301 draws no spinner then), so the box closes nothing. The lines Claude prints for a turn the user ended (`Interrupted`, `User declined to answer questions`) still close it as above; AskUserQuestion's "Chat about this" prints the same line and then writes a reply in the same turn, which is Claude at work below the line: the dialog answered, `working` until the turn's Stop (#88; before, `done` with the line's message while the reply was written). A subagent's dialog closes by its hooks only, whatever the screen shows: Claude draws it in the main pane exactly as the agent's own, and its answer leaves the main agent waiting on its subagents at the bare box. When the hooks reported a dialog, it is theirs, even when the screen reads as one of Claude's own: the screen is not read for a dialog of Claude's own while a hook's dialog is open. Verified with Claude Code 2.1.301 in an sbx sandbox with a template's managed settings (fullscreen renderer, a status line, mods drawing tool calls in cards, a PermissionRequest hook that approves every request): no working screen there shows `esc to interrupt`, and a tool at work labels the spinner with its description (`· elicit: ask_color… (5s · ↓ 86 tokens)`), which the spinner's earlier pattern (`\S+…`) missed and so took for a screen at rest; widening it changed no reading of the earlier captures. The captures are test fixtures (`internal/state/testdata/screen-fs-*.txt`); no permission prompt could be drawn there.
- **The first append wins.** Several hq processes look at the same agents at once (the list's looks, `hq ls` in a script, a chord), and each may be the first to see a moment the hooks do not date: a turn the user ended (`TurnEnded`), a screen first at rest (`AtRest`), a dialog of Claude's own first seen (`OwnDialog`), Claude at work after a dialog the hooks reported (`AtWork`; it keeps its moment as the others do, though the agent's time stays the dialog's report), the pane's death (`PaneDied`), sbx's answer that the sandbox does not run (`NotRunning`). Each appends what it saw to the agent's journal under the journal's lock, unless the journal already holds it (`journal.Standing`, the hook's last report and the evidence that stands, which a long-running look keeps as it folds), each event based on the hook's last report there; of racing processes the first event stands and the store sets the others aside as duplicates, or as overtaken when a later report of the hook came first (`journal.Standing.SetAside`, which the store, its fake and the look share), so every process folds the same journal and shows the same moment (an integration test races eight appenders). Nothing is kept on the home window.
- **Changes after a cursor (`hq wait`, [ADR 0019](../adr/0019-agent-state-changes-are-numbered.md), #166).** `hq wait` returns an agent that changed into `done`, `question`, `needs input` or `ended` after its `--since` (spec §4.1), and its processes, one call after another and beside the list and `hq ls`, must agree on whether a change came before or after the point a result stands for, with nothing watching between two calls and whatever the clocks do. Every change of an agent's state is an event with a number of the host's one counter (*Events and journals*), so each compares numbers. An agent's `state_seq` is the number of the event at which the reducer's state or open dialog last changed (`Reduced.Changed`, or for an agent `starting` since its launch, whose state no event has changed yet, the launch's event, `Reduced.Entered`; a report that changes neither moves it not, a new dialog while it needs input does), its `completion_seq` that of the event that ended its last completed turn (`Reduced.TurnEnded`: a turn end its hook reported as `done` or `question`, or the `TurnNotTaken` that decides the turn Claude owed after one kept `working` for background work does not come, as the operator decided on #166; not a stop blocked to deliver a message, a session's start, a resumed or restarted conversation, or a turn the user ended at the agent). An agent with no event behind its state has neither: an outdated one, whose journal hq does not read; one `starting` before its journal holds an event; one `ended` whose journal cannot be read; and one gone from tmux while waited on (`Agent.Gone`). A **cursor**, `next_since`, is the letter `c` and a number N such that the look that gave it saw every change numbered up to N: not the highest number it saw, since a look reads each agent's journal in turn under the lock, and an event another process appends for an agent it has read already, before it reads the next, is numbered at or below that next read's `Journal.Through` without being seen. So N is the lowest `Through` of the look's last reads (`agent.SeenThrough`), or the counter read before the look listed the home windows (`journal.Store.Through`) when that is all the look can vouch for: no journal read, one that could not be, or an agent whose window appeared while it looked, which `hq ls --json` and `hq wait` see by listing the windows once more (its window is made before its `Launched`, so every change of its is numbered above that counter). A look may show an agent at a change numbered above its N (evidence it appended for that agent after its last read of another), so `hq ls --json` looks again, three looks at most, until its N stands for every row it shows; a list of agents that change at every look is printed from the third. A look finds the waited-on agents in such a state whose `state_seq` is above the cursor given and at most its own N, and prints its N as the next call's `--since`: consecutive calls return every change once and none twice, with any number of hq processes looking at once, and with no settle time, since a change a look sees is numbered at or below its N. A look that finds one does not return yet: the look after it, 250 ms later, returns what it finds, with its own N, and the agents the first found that it no longer does (one that moved on meanwhile still changed after `--since`), so agents that finish within a look of each other come back in one call (#116): a reported state is returned 250-500 ms after it is ingested. A change overtaken by a later one between two looks is not returned. Without `--since` the call starts each agent its first look showed from the state number that look showed for it, so an agent already in such a state is not returned, including one that look put there with an event it appended after it read another agent, which its N does not stand for yet, while a change another process numbers after that look (as `deliverWaiting` types) is; an agent that look did not show starts from the counter once the look is done. A cursor above the counter (a lost state directory) is refused, saying to take a new one from `hq ls --json`. `--since` also takes a moment (RFC 3339, as an older hq printed `next_since`) or a duration back from now, compared with the time of the event at which the agent entered its state (`Agent.Entered`), approximate by nature; the result carries a cursor all the same. `hq ls --json` prints its look's N; `hq read --json` the `Through` of its read of that one agent; `hq send --json` and `hq answer --json` the counter read just before they leave the message or the answer, so what the agent does with it is numbered above it. What a result could not have shown is every agent's change for `hq ls --json` and `hq wait` (of the agents waited on), but only the one agent's for `hq read`, `hq send` and `hq answer`: another agent's change before their cursor that no `hq wait` returned may be lost from there, so a watch takes its `--since` from `hq wait` and `hq ls --json` alone (3.12). An agent waited on that the last look saw and this one does not (killed), or sees `ended` with no number where it had one (its journal no longer read, its pane dead), is returned as `ended` at once, with no numbers, since no number can say it changed. `hq kill` kills an agent's home window and only then removes its files and journal (3.3), so a look can list the window and read the journal after it was removed (#239), and took the agent for one that never reported: `hq wait` returned it with `[session ended]` in place of its last message, and `hq ls` showed it so. A look notes an agent whose journal it found gone, holding nothing when it read it or removed while it looked (`Agent.JournalGone`), and when it found one lists the home windows once more and leaves out such an agent whose window has gone: for a kill this is certain, the window going before the journal, and the look shows what the next look shows, so `hq wait` returns the agent as killed with what the look before showed, and `hq ls`, the list and the other looks do not show it. An agent whose journal is gone while its window is still listed (before its `Launched` is appended, or a lost state directory) is shown as before. A `hq wait` whose first look falls between those steps of a kill answers that there is no such agent, as one whose first look comes after the kill does. A paged `hq read --offset N --since CURSOR` gives the page while the latest turn end's number (`Detail.ReplyNumber`) is at most the cursor, so a page is of the reply the cursor's read showed; with a moment it compares the turn end's time as before. `AGE` still counts from the time of the change: numbers order changes, times measure them.
- **Branch.** Hooks run in Claude's current directory, which moves into the worktree Claude creates (`CLAUDE_PROJECT_DIR` stays at the repository). The hook asks git there for the checked-out branch and writes it as a header line (`branch NAME`) before the payload: git answers inside the sandbox, where the path is valid on both platforms, so the host never maps sandbox paths to find a branch. Empty before the first event and on a detached HEAD. The payload's `cwd` is kept as the worktree path (for `hq code`, M4).
- **Interpretation on the host.** The hook stores the raw payload after the branch line; hq derives the state, the time it was entered, the one-line last message and takes the branch. `question` vs `done`: the last assistant message ends with `?`, the rule proven by a `notify.sh` hook in one of the team's application repositories.
- **Last message.** `last_assistant_message` of Stop; while `needs input`, what the dialog asks (the first question of AskUserQuestion; for a permission prompt the tool and its description or command; an MCP elicitation's message, or its server when it has none), or the Notification's own message when it came without a dialog. The journal keeps the latest turn end's reply (`journals/ID.reply`), so a `working` or `ended` agent still shows its previous reply, and `hq read` dates it by its turn end. An `ended` agent's `AGE` counts from when its session ended, never from its last report or its start: the session-end report's time when there is one (`/exit`); otherwise when its pane died, which tmux keeps for a dead pane (`#{pane_dead_time}`, whole seconds; a killed or crashed Claude, a launch that failed); otherwise when hq first saw it `ended` (a sandbox stopped while the pane lives on, a restart's `ending` marker, or a tmux too old to date a dead pane), which the first look to see it appends to the journal (`PaneDied` without tmux's date, `NotRunning`, `TakenDown`), so every later look, from any process, shows the same `AGE`, and a relaunch or a report after it starts over: an end from before the agent's latest launch or report is not its end (#104). Ended rows are then ordered newest end first (spec §6.2).
- **Messages (`hq send`, [ADR 0012](../adr/0012-hq-send-messages-cross-into-the-sandbox.md)).** The host leaves each message as one file in the agent's inbox, `.git/hq/inbox/ID`, named by the time it was sent in nanoseconds (zero-padded, so names sort in the order sent), a random part, `.sup` when the supervisor sent it (3.5), and `.now` for `--now`; written as a dot file and renamed into place, it holds the text already encoded as the inside of a JSON string (after the escapes and control characters but newlines and tabs are stripped; at most 8 KiB), so the hook copies bytes and needs no encoder. Whoever renames a message out of the inbox first delivers it, the hook into a directory of its own (`.taken.PID`) or `hq send` (`.taken-*`), so each is delivered once without a lock (an integration test races both). The hook delivers everything waiting, oldest first, each prefixed `Message from the user (hq send): ` and separated by a blank line: on Stop as `{"decision":"block","reason":...}`, so Claude goes on and stops again (with `stop_hook_active`, and blocked again only if another message came in meanwhile); the blocked Stop writes no report and prints no notification, so the agent stays `working` and the stop after it notifies once. On UserPromptSubmit as `additionalContext`, riding along with the prompt. On PostToolUse only when one of the messages has `.now`, as `additionalContext` with the tool's result; not on a subagent's tool (its payload carries `agent_id`, and Claude hands that result to the subagent), nor on PostToolUseFailure. While a dialog is open no Stop or tool end of it comes, so a message waits for its end. For an agent that waits at its prompt (`done`, `question`), `hq send` reads its screen as for rewound turns: once the prompt box is at rest and empty on two captures 150 ms apart that show the same screen, it takes the messages out of the inbox and types them in as one bracketed paste through a tmux buffer of the pane's own (`set-buffer` in parts of 4 KiB, `paste-buffer -p -d`), then Enter 300 ms later, so their lines stay one prompt and no key in them acts. A slash command is the exception (#173): Claude Code 2.1.325 shows a paste of more than 3 lines or more than 800 characters (newlines included, characters, not bytes or columns, which the captures, all ASCII, do not show and `state.Collapses` extrapolates: the one place the limits and the version are named) collapsed, `[Pasted text #N +K lines]` or `[Pasted text #N]`, with the hint `paste again to expand` in place of the footer, and a prompt that begins with a collapsed paste reaches the model as pasted text, never as a command; text typed in one burst over the limit is collapsed the same way. Typed text before a paste keeps the prompt a command: so a message that starts with `/` and would collapse has its command word typed (`send-keys -l` in parts of at most 200 bytes, `Tmux.Type`, which Claude takes as typed) and the rest pasted after it, and Claude runs the command with the rest, the first line's included, as its arguments, verified against the transcript's `<command-name>` and `<command-args>`, also for a first line of 1,000 characters. A shorter command, and any message that does not start with `/`, is pasted whole as before. Several messages waiting are typed in as prompts (`prompts`): a run of messages without a command is one prompt, joined by a blank line, and each command is a prompt of its own, since joined behind text it would be text and joined before text the text would be its arguments. Only the first prompt is typed in: Claude Code 2.1.325 queues a command entered while it works and runs it after the turn, but takes a prompt entered behind it into the running turn (a `queued_command` attachment at the next tool's end), ahead of the command. The others go back into the inbox under `held/` (`state.Hold`, all or none), once the first prompt is typed in (a failure to type it puts every message back for the hooks, in the order sent, as before, under its name and with the moment it was sent, so the next look at the agent at its prompt types them again; a command word typed before a paste that fails is taken out of the box with `C-u`), keeping the moments they were sent, where the hook, which takes only the files named `[0-9]*` of the inbox itself, does not see them; `state.Take`, `Pending` and `Oldest` see both, in the order sent, so the next look at the agent back at its prompt types the next prompt in. A message sent meanwhile, left to the hooks, may reach the agent before the held ones. The screen readers hold on these screens (fixtures `screen-styled-paste-*`, `screen-styled-command-*`): a collapsed paste is something in the box, and the hint below it is no footer that offers Esc. Where hq leaves a message that starts with `/` to the hooks (`queued:`, with and without `--now`, and a message the hooks took), its line adds that the command arrives as text and does not run, the queued lines with an "if", since a look may still type the message in. With anything in the box, or no box, for 4 s (a capture every 150 ms), it leaves them for the next prompt's hook. It then captures every 150 ms, up to 3 s, until the box no longer holds what it typed (`state.BoxText`), so that consecutive sends follow one another: the next one meets what Claude does with the prompt, not the prompt still in the box. Claude Code 2.1.304 (#125) takes a slash command out of the box a few tenths of a second after Enter, and `/model NAME` then shows a panel in place of the box (a `▔` edge, no rules) for about 2 s, so the screen is not at rest for about 2.5 s; a send that decided from one capture right after another send met either and left its message for a prompt that never came, since a slash command fires no hook. A message left waiting so for an agent at its prompt is typed in by hq itself wherever it looks at the agents (`hq ls`, `hq read`, each look of `hq wait`, and the list, which runs one round at a time beside its looks): once the oldest message has waited 6 s (its name gives the moment it was sent; `hq send` has delivered or given up by then), on one look of two captures, as `hq send` does but without waiting for the box. A look takes every message waiting, as `hq send` does, so one that types in an older message takes a newer one a running `hq send` has just left with it, and a message left for a `starting` agent (which `hq send` waits for up to 30 s) may be typed in by a look; each is still delivered once, and that `hq send` says it was taken. It reads the screen with its styles (`capture-pane -e`), because Claude draws hints in the empty box faint: a session that has just started shows a placeholder there (`Try "create a util logging.py that..."`, seen with Claude Code 2.1.283 in QA, recorded as a fixture), which read as text would keep a new agent from ever getting a message typed in; faint text on the input line is not counted, while what the user types never is faint. A `starting` agent (its session not started, or, launched with a first prompt, that prompt not taken yet, 3.4) is waited for up to 30 s, then left to its hooks, which deliver the message with the first prompt; while that prompt is never reported, the message waits. Verified with Claude Code 2.1.283 in sbx (#135): a blocked Stop continues the turn, and Claude shows the reason in the session as `Stop hook error: <reason>` (recorded as a screen fixture); both `additionalContext`s reach Claude; a multi-line bracketed paste and Enter submit one prompt; a background subagent's PostToolUse carries `agent_id`. An agent started by an hq of another generation has hooks this hq cannot read, so it is outdated (*Generation and outdated agents* above) and `hq send` refuses it with the remedy, as every command but those that open or kill it.
- **Answers (`hq answer`, [ADR 0013](../adr/0013-question-dialogs-are-answered-through-their-own-hook.md)).** A question dialog (AskUserQuestion) is answered through its own PermissionRequest hook, verified with Claude Code 2.1.302 (#89, #90). Beside the hook that reports the dialog, its PermissionRequest runs the hook of kind `hold`, matched to `AskUserQuestion`, with `timeout` 86400 (honoured, #89; at the timeout Claude sends SIGTERM and the dialog stays open). It writes no event and no note but one line: as it starts it adds `h CRC LEN` to `ID.asked`, the list where the reporting hook adds the `cksum` and length of each dialog's report after its note and before its event (#209). It waits until the hook's note of its latest report is the dialog's, of the same POSIX `cksum` and length as its own copy of the payload (the reporting hook may write it a moment after the `hold` hook starts; it waits up to 10 s, and no longer once `ID.asked` holds as many reports of its dialog as holds of it, its own counted: then the report came and is the note, or came and went), then looks every 0.2 s for the answer's file in the agent's inbox, `answer.CRC.LEN`, named for that report by its `cksum` and length, which hq computes the same way from the dialog's event file, kept whole for a question dialog beside the journal (`journals/ID.ask`, `state.Asked`, `state.Questions`). It takes the file by renaming it and prints it as its decision, so whoever renames it first has it: the hook, or `hq answer` taking it back (`state.WithdrawAnswer`). It ends with no output once the note is no longer the dialog's report (the dialog answered at the terminal, whose PostToolUse the reporting hook writes; a prompt, a Stop, a session's end; the agent removed), never taking an answer after that, at its first look when it starts only after the dialog was reported and answered (on a busy machine; before #209 it then held its 10 s; the count keeps the same questions asked again in the turn, a report of the same bytes, waiting for their own report, whatever ended the earlier holds): Claude does not stop it when the dialog closes, only at the session's end (#89, case 2d). A subagent's dialog (its payload carries `agent_id`) is not held for. A name per report keeps the answer to one dialog from being taken by another dialog's hook, even an answer left a moment too late for its own (unless the two reports are the same bytes: the same questions asked again in the same turn). The decision is written whole on the host (`state.Questions.Decision`): an allow whose `updatedInput` is the dialog's tool input, copied as Claude gave it, with `answers` added, keyed by the question's text: an option's label for a single choice, a list of labels for a multi-select question, which Claude joins with `, `, or free text, stripped and capped at 8 KiB as a message is; a cancel is a deny with `interrupt: true`, which leaves `User declined to answer questions` and ends the turn with no Stop, as Esc does (#89, case 5). The file is written aside and hard-linked into place, so the hook never reads half of it and a second answer to the same dialog is refused while one waits (`state.ErrAnswerWaiting`); answers left for other dialogs, which no hook takes any more, go when a new one is left. `hq answer` refuses first what it does not answer (an outdated agent, 3.3, before anything of it is read; the dialog verdict; the report's detail, which tells a question dialog from a permission prompt or a Notification), reads the questions again from the journal and refuses when they are no longer the dialog's, validates the whole answer, leaves the file, waits up to 3 s for the hook to take it and takes it back otherwise, then waits up to 5 s for the dialog to close: the end of AskUserQuestion, whose `tool_input.answers`, which the ingest keeps with the dialog (`state.Asked.Answers`), (one string per question) it compares with what it sent, as strings, since a label holding `, ` cannot be told from two labels (#89); or the look no longer at that dialog, as after a cancel, which only the screen shows. The dialog's id is six hex characters of FNV-1a over the moment of the dialog's report in nanoseconds (`state.DialogID`), the moment the open dialog is keyed on; `hq ls --json`, `hq read` and the supervisor's `list` and `read` give it as `dialog` while the agent needs input. **Prerequisite in the sbx template:** its own PermissionRequest hooks do not answer AskUserQuestion; they print nothing for it. Claude takes a bare `allow` for AskUserQuestion as the first result and ignores later ones (#89, case 3), so in a sandbox whose template has such a hook (the agents' template had an auto-approve hook that answered every request, until it was changed to stay silent for AskUserQuestion during #89 and #90) the agent ignores hq's answer. A sandbox keeps the template it was created with, so it is recreated after the template changes; a sandbox created before its template changed still has such a hook (#128: reported as a Claude Code 2.1.304 change, reproduced on 2.1.304 only with the template's former hook, answered with its current one). So before it leaves an answer or a cancel, `hq answer` looks at the sandbox's template: it prints the managed settings (`/etc/claude-code/managed-settings.json`, then `managed-settings.d/*.json`) with `sbx exec`, takes the command hooks of PermissionRequest whose matcher takes `AskUserQuestion` (none, `*`, the name, or a pattern matching it whole; `state.AskHooks`), Claude anchors a matcher's pattern (`Ask` does not take AskUserQuestion, verified with 2.1.304), and runs each once with `sbx exec`, the dialog's payload on its standard input, for at most 10 s (`timeout`, coreutils; without it, unbounded), in `sbx exec`'s directory and environment, not the session's: a hook that answers by those could pass the look. A hook that prints a decision (`state.Decides`) is named in the refusal, at once and with the cause, in place of an answer left, taken by the hook that holds and ignored by Claude, a 5 s wait, and a retry told the hook no longer holds. Such a dialog is answered at the agent only: Claude took the template's bare allow when the dialog opened, so fixing the template afterwards does not help it (seen with Claude Code 2.1.304, #128); a sandbox recreated from the fixed template does. A sandbox hq cannot look into, or a hook that fails, is passed: the answer goes on as before, and one not closed within 5 s names the likely cause, another PermissionRequest hook answering first (the repository's settings, a plugin, or the template where hq could not run its hooks). The stub `sbx` maps an argument `/etc/claude-code` of `exec` under its sandbox's own root, so the host's managed settings never count in tests. The look costs one `sbx exec`, and one more per such hook, on each answer to a question dialog. Verified with Claude Code 2.1.302 in #90, in the plain setup with a stand-in for an auto-approve hook that stays silent for AskUserQuestion: the reporting hook, which prints the dialog's notification, does not keep Claude from taking the held answer. The hold costs the hook about 390 bytes, which took its script to 8,325 bytes beside the elicitation's report (#100): over the 8 KiB it had been kept within, so its budget was 9 KiB then, still well within the 24 KiB of the settings (3.12 for it now).
- **Answers to Claude's own dialogs (`hq answer`, [ADR 0014](../adr/0014-dialogs-of-claudes-own-are-answered-with-keys.md), #120).** A dialog of Claude's own fires no hook, so `hq answer` picks its option with keys in the agent's pane, `tmux send-keys` of `Down`, `Up` or `Enter` by their names, one per call (`Tmux.Press`). The dialog verdict carries the fingerprint the journal holds of it (`OwnDialog`), from the look's screen or, when the capture failed, from the journal alone; `hq answer` checks the request against the dialog's id as for a question dialog, then captures the pane afresh (`state.ViewOwnDialog`: what the dialog asks, the option its `❯` is on, and whether its list scrolls) and goes on only when the fresh dialog has the same fingerprint (`agent.Dialog.Shows`). It refuses a list that scrolls (a `↑` or `↓` before an option, a `…` line below them: the picker of `/model`), text, several options and `--cancel` (`state.OwnView.Pick`), and a screen that shows another dialog, or none (answered at the agent first, with its state). It then presses `Down` or `Up` toward the option, one key at a time, and captures every 100 ms until the `❯` has moved, at most 2 s per key; the dialog changed meanwhile, or the `❯` not moved, it stops with nothing picked. On the option it presses `Enter`, then looks at the agent every 100 ms, up to 5 s, until it is at no dialog or another one (the look appends that the dialog is gone once the screen shows the box). `--json`'s `next_since` is the cursor read before the first key (the counter, "Changes after a cursor"), so the event that closes the dialog is numbered above it and a `hq wait` from it returns the agent once, in the state it is back in. No hook is involved; an outdated agent is refused all the same (3.3). Claude Code 2.1.304 (#120) redraws the `❯` within 0.1 s of a key and wraps round at the ends; hq moves only toward the option, and gives up after as many keys as the dialog has options. The question whether to trust the folder is out of reach: Claude Code 2.1.304 asks it before any hook runs, so the agent is `starting`, which the look does not read for a dialog. The fake Claude's `/effort LEVEL` asks as Claude Code 2.1.304 does, only when a turn has run since the start or the last change (otherwise it sets the level at once), and its dialog takes keys the same way: it turns its terminal non-canonical while the dialog is open, so each arrow reaches it as it is pressed.
- **Long replies (#64).** The hook writes the whole Stop payload, `last_assistant_message` included, so a long reply made a large state file, now a large event file: an 82,000-character reply made 86 KB, which the 64 KiB cap of 7.3 once refused as "not a state file", leaving the agent `starting` for good with no reply, no `hq wait`, no notification and messages that never left the inbox. The cap is now 16 MiB, a bound against planted files rather than a limit on what an agent says; the hook is unchanged, so running agents need no relaunch. Three consequences: (1) **parsed once**: the ingest reads each event file once, and keeps the latest turn end's reply beside the agent's journal (`ID.reply`), so a look reads only the events appended since the one before (5.1), never a long reply again, and `hq read` takes the reply from there in full; (2) **paged reply**: `hq read` (and the MCP `read`) gives the reply in pages of 32 KiB (`reply_size`, `next_offset`, `--offset N --since SINCE`), each page cut where a UTF-8 character begins; a page is tied to the read that gave its offset through that read's `next_since`, its cursor: a reply whose turn end is numbered above it is another reply, and the page is refused, saying so, rather than joining two replies (a moment, as an older hq printed `next_since`, compares the turn end's time with it plus 250 ms, as before); (3) **never silent**: a regular event file over the cap is still the agent's report: a Stop over it makes the agent `done` (the only report of that size an agent gives is a turn's end), and `LAST` and the reply say `[report too large to read: N MiB]`; `.stop` over it gives that as the last message and the reply. Rejected: capping the reply in the hook (every running agent would need a relaunch, and the reply would be lost), and reading the head and tail of an oversized file (a partial JSON parse is the defensive parsing 7.3 avoids).
- **No task list (rejected, #133).** `hq read` was to show the tasks Claude tracks for itself. Claude Code 2.1.283 offers its task tools (TaskCreate, TaskUpdate) only to older models by default (Opus 4.7 and before, Sonnet 4, Haiku 4.5), so the agents' model keeps no task list, and turning them on (`CLAUDE_CODE_ENABLE_TODO_TOOLS`) would change Claude's defaults, which hq does not do. So hq neither enables the tools nor reads a list.
- **Events and journals ([ADR 0018](../adr/0018-agent-state-is-a-pure-function-of-one-event-journal.md), #165).** Beside its working files above, which decide nothing on the host, the hook writes each event a rule reads as a file of its own, the sandbox stream: in `.git/hq/events/ID/`, the branch line and the payload, copied under a temporary name and renamed into place, named by the count it keeps in that directory (`.n`, written aside and renamed), its kind (the case of the script that wrote it: `prompt`, `stop`, `answer`, `dialog`, `input`, `result`, `start`, `resume`, `end`) and its process id, `%09d.KIND.PID`, so the names sort in the order it wrote them, never by the sandbox's clock, and say which case wrote each (`state.Facts.Hook`). It writes one with every report it takes for the state or keeps (just after its note, so the hook that holds on a question dialog, which looks every 0.2 s, sees the dialog's report as soon as it can; and that hook stops waiting for the report once the note is newer than its own copy and not the report, as when the dialog was answered at the terminal before it first looked), and for the end of a tool only when it tells something new: the first of the agent's own in the turn (`ID.acted` did not hold the turn), one of the agent's own that drops a queued prompt (`ID.queued` was there) or hands one over, one that closes a dialog or starts background work; a subagent's only for the last two. A turn of 200 tool calls leaves one file for them. A delivery of messages (a stop it blocks, the next prompt, after a tool's end) is an event file of its own, `delivery KIND` and then the name each message was left under in the inbox, written before the event of whatever the agent does next; the end of the tool a delivery comes with is written before it. Every look (`hq ls`, `hq read`, `hq wait`, `hq send`, the list, the chords, and the lookups of `hq go`, `hq code` and the dialogs) first ingests an agent's event files into its journal (`journal.Store`): with files there, it takes the one lock of the state directory (`$XDG_STATE_HOME/hq/lock`, by default `~/.local/state`, an `flock`), finishes or undoes an ingest a dead process left (`journals/ID.ingest`: the journal's size before and after, and the files; an append of hq's own events that takes the lock first undoes one cut off before its append was whole, and leaves a whole one for the next ingest, which alone removes the event files), lists the files again, reads each as hq reads what the sandbox writes (7.3), numbers them from the one counter (`counter`, written before the append, so a death in between leaves unused numbers, never one used twice), keeps the reply of the latest turn end among them in `journals/ID.reply`, appends them in one write, one JSON line each, and removes them. An event holds only what the rules read (`state.Facts`): the branch, the session and turn ids, whether a subagent reported it, the tool, for a turn end whether its reply ends with `?` and its tasks by id, type and status, the background work a tool started as the hook's list names it, the task a wake-up names, the prompt (not a wake-up's), what a dialog asks, the messages of a delivery. Its time is the host's time of its file. A failed ingest fails no look: the files wait for the next one. What hq sees and does is appended to the same journal as events of its own (#195), each carrying its basis, the number of the last event of the hook in the journal when it was taken, and timed by the appending process's clock; an event that dates the state from an earlier moment says so (`From`). From the screen, what a look sees first that no hook reports: a turn the user ended, with its line (`TurnEnded`); a screen first seen at rest (`AtRest`), or at rest at a tool the user cut short (`ToolCut`), with its fingerprint; the decision RestDelay later, the screen unchanged, that the turn was rewound (`Rewound`) or that the turn Claude owed does not come (`TurnNotTaken`), written by the look that decides and dated from the screen first seen at rest; a dialog of Claude's own seen (`OwnDialog`, with its fingerprint and its title) and gone (`OwnDialogGone`); Claude at work after a dialog its hooks reported (`AtWork`); Claude at work on a prompt it took from its queue (`TookQueued`); Claude's wake-up after a turn the user ended, dated from its report (`WokeUp`). From tmux, the pane's death, dated by tmux (`PaneDied`; an end known only from it is dated by it). From sbx, the sandbox not running, with the moment sbx was asked (`NotRunning`), only from an answer that ends the agent: an sbx too old, one that failed or did not answer gives no answer, and no event. From hq, written before it acts so whatever the agent then reports comes after it: the agent launched (`Launched`, `new` or `restore`, with its repository and tmux server, before its session is released) and relaunched (`Relaunched`), a restart taking it down (`TakenDown`, before the sandbox stops), a delivery of the messages typed in as its prompt (`delivery` of source `hq`, naming only the messages of the prompt typed, each by the name it was first left under in the inbox, which `state.Take`, `state.Hold` and the put-back after a failed typing keep, the put-back less `.now`, so the hooks deliver it with the next prompt as before, appended once they are taken and before they are typed; a held message gets its delivery when a later look types it in), an answer given (`Answer`, whose dialog in `whose`: to a question dialog before it is left for its hook, to a dialog of Claude's own before Enter), and `Withdrawn` for a delivery, an answer or a launch that did not reach the agent. A look reads each agent's journal once it has ingested it and appends what it saw only when the journal does not hold that evidence yet (`journal.Evidence.Holds`: the latest event standing of the same kind, since the agent was last launched and, for any other kind, since Claude last took a queued prompt, which hands the report over with no event of the hook, is the same evidence), so a screen that stays the same adds nothing, and to a journal that is not there (never begun, or removed) only while the agent's home window stands (*Lifetime*, `journal.Store.AppendEvidence`). Under the lock the store sets an event aside, keeping it in the journal with its reason: `duplicate`, the same evidence another hq process appended first, and `overtaken`, evidence of the screen or of sbx whose basis a later report of the hook overtook before it was appended. What hq does is never set aside. The journal decides the state (#198): every look ingests the hook's new event files, appends what the screen, tmux and sbx show that the journal does not hold yet (`state.Fold.Sees`, `Stopped`, `WakeUp`), and folds (`state.Fold`, which a long-running program keeps per agent, `agent.Folds`, folding only the events appended since its last look, `journal.Store.ReadFrom`); nothing on the host reads the hook's working files or a home window for a state. It follows each hook event through the case of the script that wrote it, keeping what the hook knows from its working files (its latest report, its latest turn end, a kept event, `ID.owe`, `ID.acted`, `ID.queued`) and the report before a resumed session from the events alone, and reads the hook's state off that; with no I/O and no clock, the moment for `AGE` passed in. Then it reads the events of hq's own beside that report, as the look reads the screen, the pane and sbx's answer (#197), each event set aside changing nothing: a report from before the agent's latest launch or relaunch is its previous session's, which gives the last message, branch, worktree and prompt but not the state (the agent is starting since the launch); the agent has ended at its session's end report, dated by it, else at the first of its pane's death (dated by tmux, after the moment the state counted from), sbx's answer that its sandbox is not running (only once a report of the session came, none newer than the moment sbx was asked, and only from an answer with that moment) and a restart taking it down, each dated by its event and never before the latest report, keeping the line of a turn the user ended for that report as its last message; while its session runs, the evidence of the screen, each keyed by the hook's report it was seen at (the latest report the hook took, or the event kept beside it when later) and the first seen for a report standing, overrules the hook: Claude's wake-up after a turn the user ended dates the work since it (`WokeUp`, or the wake-up kept beside the report); a turn end the screen showed makes the agent done since it was seen with its line (`TurnEnded`), or since its screen was first seen at rest with `Interrupted` (`Rewound`) or with its own message (`TurnNotTaken`), entered at the deciding event; else Claude at work closes a dialog of its hooks', its own and not a subagent's (`AtWork`); an agent then waiting at its prompt is at a dialog of Claude's own since it was first seen, its title the last message, until it is gone (`OwnDialog`, `OwnDialogGone`). Claude taking a queued prompt hands the state over to it (`TookQueued`). A screen first seen at rest decides nothing: no state changes with the time passed in alone. Its result also gives the event the agent last entered its state at (the report its state comes from, today's rule), the event its state or its dialog last changed at, the turn end of the last completed turn (one reported as done or question: not a turn end that leaves the agent working, a stop blocked to deliver messages or a session's start) and the events the state and the dialog verdict rest on; the dialog verdict says whose the dialog is (the hooks', a subagent's, Claude's own), the event that opened it and, once closed, the one that closed it. A turn the user ended at the agent, with its line or rewound, is not a completed turn and leaves it as it was; the screen's decision that a turn Claude owed for background work does not come is the end of one, since it completes a turn whose end the hook reported. The fixture journals (`internal/state/testdata/journals`) are steps of hq launching, relaunching or taking down an agent, the hook payloads run through the hook and the ingest, and a look (`agent.Look`, on the journal's store) at the screen fixtures the agent's pane shows, its pane dead or alive and sbx's answer, with what the look gave after each step (the old look, before the reducer, when they were first built); on every one the reducer gives the same after every step (the state, the moment it counts from, the last message, the own tasks and the dialog verdict), and an integration test rebuilds them and fails on a difference.
- **Waiting for the answer (`hq send --wait`, spec §4.1, §5.1, #170).** `hq send` returns the name its message was left under (`state.Post`), and with `--wait` it then looks at the agents as `hq wait` does, through the same loop (`watchLooks`: a look every 250 ms, sbx asked in the background after the first, the look's cursor), reading after each look the agent's events numbered above the cursor it took before leaving the message (`journal.Store.ReadFrom`, from where its last read ended). The message is **taken** once a delivery event names it, the hook's or the one hq appends before it types a prompt in, with no `Withdrawn` of that delivery after it (the typing failed and the message went back); names are compared less `.now`, which a message put back loses (`state.SameMessage`); a message held behind an earlier prompt is named by no delivery until a later look types it in (`takingOf`). The call returns on what `hq wait` returns, not on `completion_seq` (which a turn the user ended, a dialog, an end and a queued prompt leave or move otherwise): the agent in `done`, `question`, `needs input` or `ended` with a `state_seq` at most the look's cursor and above the delivery's number, which a delivery never moves itself (the reducer skips it); for a message hq typed in also above the first prompt Claude reported after the delivery that is not its own wake-up for background work (`Wake`), so the end of a turn Claude woke itself for before the typed prompt is not taken for the answer; with no such prompt only `needs input` or `ended` returns (a slash command that opened a dialog of Claude Code's own) (`settled`). Not yet taken, an agent that needs input or has ended returns at once, the message waiting, kept (its inbox still holds messages) or gone (killed: the agent is gone from tmux, `Agent.Gone`). It prints the look's cursor, so `hq wait NAME --since` from it never returns the same change. While the agent waits at its prompt with the message not taken, the call types it in itself as soon as the box is empty and at rest (`typeIn`, no wait for the box), not after `deliverWaiting`'s 6 s, which would leave a box busy for 4.5 s (as after `/model`) stalled; the others' messages go to `deliverWaiting` as in `hq wait`. A typing that fails there fails the call as it fails `hq send`, not as stalled: exit code 3 with tmux's words, the messages back in the inbox and the delivery withdrawn. The bound, 5 s fixed (`stallBound`), runs only while the agent is at its prompt (`atPrompt`): from when the send began to deliver while the message waits, and from the delivery's time once hq typed it in and Claude reported no prompt; a look with the agent elsewhere pauses it, and it starts again from that look (`stallClock`). When it has passed, at exactly 5 s held included (`lasted >= stallBound`), with the message waiting in the inbox the call fails as stalled, and so it does with the message no longer in the inbox and no delivery of it in the journal (another process took it and its delivery is not in the journal yet, or the journal cannot be read: where it went is not known); typed in, the box read once more with the rules hq has (`state.BoxText`, no new screen rule) decides: text in it is a prompt not sent (stalled), an empty or gone box is a slash command that started no turn (returned normally) or, for any other message, one that left the box with no turn (stalled). A stall is `ExitStalled` (4), its line names where the message is and says to read the agent before sending again; nothing is typed again or taken back. `--timeout` counts from the start of the call and also cuts the wait for a `starting` agent (30 s) and for the box (4 s). The first lookup (`findAgent`) fails on an sbx too old with exit code 3; the looks after it tolerate it, as `hq wait`'s. The supervisor's `send` passes `wait` and `timeout` as `--wait --timeout`, the timeout at most the client's `maxWait`, as `wait`'s (3.12), and the hook that refuses a call naming the calling agent knows both keys (`sendInput`).

- **Explaining a state (`hq explain`, spec §4.1, #202).** `runExplain` takes a look as `hq ls` does, the second one RestDelay later included (`lookDecided`), so the journal holds what the state now rests on, but types in no waiting message; an agent tmux lost is found as `hq kill` finds it (`lostAgent`), refused when its record carries another generation, and its event files ingested. It reads the agent's journal once and folds it event by event (`state.Fold.With`, then `Result`), which gives the state after each event and, after the last, the state, its age and the events the state and the dialog verdict rest on (`Reduced.RestsOn`, `DialogVerdict.RestsOn`, `Opened`, `Closed`); without `--all` it shows those, with `--all` every event, one set aside marked with its reason. An event is told in words from its kind and the facts that hold no text (`eventWhat`, the reason apart in `asideWhy`), and `--json` carries the facts of `state.Facts` but `Prompt` and `Text`, the conversation's text, `Branch`, `Cwd` and `Session`, which would name the user's work or session, and `Screen`, a fingerprint of a screen's text; the journal's reply and ask, kept for `hq read`, are never read. A unit test runs it over every fixture journal, plain and `--json`, with and without `--all`, and holds that its output is the same, character for character, when every text of the journal is blank, and holds none of those texts. It is a command only: `hq mcp` has no tool for it (its list of tools is pinned by a test) and the dashboard no key.
- **Location.** The main repository's `.git/hq/`, found from any of Claude's worktrees through git's common directory. Never tracked, no ignore rule. The journals, the counter and the lock are in the user's state directory, out of every sandbox's reach, the directories `0700` and the files `0600`.
- **Lifetime.** An agent's files live as long as the agent: when hq removes it (`hq kill`, `hq stop`, the Kill dialog, `k` on an ended row), it deletes that agent's files in `.git/hq/agents` (the hook's working files, `ID.next`, its record `ID.hq`, and the `ID`, `ID.stop` and `ID.prev` a hook of an earlier generation wrote), its inbox with any message or answer still waiting, its event files and its journal after its window, when its session has ended and nothing reads them any more. Only the removed agent's files go, by id: agents of other tmux servers (another worktree's `scripts/local-dev.sh`, a tester) report to the same directory, and hq cannot tell whether an unknown id is gone or lives elsewhere, so it never prunes other files beside the repository. The one exception is a journal left over by an agent whose repository was removed without hq (spec #165, *Leftovers*): its launch event names its repository and its tmux server (`repo`, `tmux`), and `hq restore` and every kill remove it (`sweepJournals`) once that server is the running hq's, no window there has its id and its repository holds no record of it; a journal that names another server, or no launch, stays, and so does every journal while tmux cannot list its windows. A killed Claude writes its session-end report on SIGTERM, so the files go only after its process is gone, whether its pane lived or not. A session that outlives the kill's wait may write its file once more; that file stays. No look writes a removed agent's journal back (#263): a look of another hq process that listed the window before the kill killed it can append its evidence (the dead pane's death, sbx's answer, what the screen showed, a wake-up) after the journal was removed, whether it read the journal before the removal or found it gone, and the store's append would begin the journal again, holding no launch, which nothing removes. So a look appends to a journal that is not there only when tmux says, asked under the store's lock with the append, that the agent's home window still stands: the kill kills the window before it removes the journal (the fact #239 rests on), so with the window gone it is a kill and nothing is written, and with the window standing the kill's removal, which takes the same lock, comes after the append and removes it too. An agent whose window stands while its journal is not there (before its `Launched` is appended, or after a lost state directory) gets its evidence as before. When tmux cannot list the windows at that moment, nothing is written, since a kill under way would leave that journal for good; the next look, tmux answering, writes it, and until then an agent whose ended state rests on that `PaneDied` shows `starting`. tmux is asked while the look holds the store's lock, only for a journal that is not there: a tmux that does not answer holds the lock as long as it already holds every look, which lists the windows first. hq's own events (`Launched`, a delivery, an answer) are appended as before.

Satisfies: §4.1 (`hq wait`, `hq send`), §5 (states, age, last message, no setup), §5.1 (messages), §8 (no repository files), S2, S4, S5, S11; drivers 1, 3.

### 3.5 Notifications

The agent's injected hook sends the notification ([ADR 0010](../adr/0010-hooks-send-notifications.md)): on Stop it returns `Question: <branch>` or `Done: <branch>` (the `?` rule in `awk`), on a dialog opening (an MCP elicitation's form included, #100) and on a Notification that comes with no dialog open `Needs input: <branch>`, as a `terminalSequence` that Claude writes to its pane and tmux passes to the terminal. hq bakes the platform's notification sequence into the hook at launch (3.10), and every agent window gets `allow-passthrough all` when it is made (3.2; it is a pane option, so it is set per window rather than on the session). tmux drops a bare OSC 9, and Claude accepts from a hook only OSC and BEL, not tmux's passthrough wrapper; Claude wraps the sequence itself when `TMUX` is set, which sbx does not pass into the sandbox, so the injected settings set it (verified with Claude 2.1.283). The branch is the one the hook reports with each event, or the directory's name when HEAD is detached; it loses control characters, `\` and `"` so it cannot break the JSON or add a sequence of its own, and neither it nor the message is ever used as a format. Only Stop, a dialog opening, the attention Notifications and the `idle_prompt` Notification (below) carry the sequence; the prompt, tool-end and session-end hooks print none (the prompt and tool-end hooks print only messages, 3.4), a Stop blocked to deliver messages prints none either, and the Notification Claude sends seconds after a dialog it already reported is dropped, so a dialog notifies once. A turn the user ends with Esc runs no hook and notifies nothing (3.4). No hq process sends a notification: the agent's hooks decide whether and when one goes out, by the rules above and those of the two paragraphs below, which give the exceptions and the limitations. tmux passes the sequence only to a terminal attached to the `hq` session, and `q` detaches it (3.11), so after `q` notifications stop until `hq` (ADR 0007, 0010).

**A turn an API error ended (spec §5, #224).** Claude ignores what the hook prints for StopFailure (3.4), so the `fail` hook cannot notify. The notification comes with the Notification of kind `idle_prompt`, which Claude Code sends 60 s after a turn's end with no prompt since (verified with 2.1.326 after StopFailure and after Stop, setup N of the fixtures): a hook of its own, `idle`, with the sequence, prints `Done: <branch>` only while the hook's note is that StopFailure, so no prompt has come since and an ordinary Stop, which notified, prints nothing more; and not while `ID.sup` exists, which `fail` keeps, so a supervised turn notifies nobody. It then makes that Notification its note, which every rule reads as it reads the StopFailure (neither is working or a dialog), so it notifies once; it writes no event, and the host never learns of it. The cost: the notification is a minute late, a prompt within that minute leaves the end with none, and so may a subagent still running, since Claude sent no `idle_prompt` while one ran (2.1.291, 3.4 *Background work*), the closing turn's end notifying instead; the spec states these as documented limitations. Alternatives considered: no notification for such an end (the user may not be watching an agent they prompted themselves); a notification from hq on the host (no hq process takes part in a notification: ADR 0002, 0010). The `idle` case took the script to 10,561 bytes, which raised its budget (3.12).

**Supervised turns (spec §5, #46).** The hook sends the notification (ADR 0010), so it is the hook that must know, at a Stop, whether every prompt of the turn came from the supervisor. Two things tell it, both written by hq on the host into the directories the hook already works in. A message's file name says who sent it: `send` of `hq mcp` adds `.sup` to it (before `.now`), `hq send` from a shell does not (3.4). And a prompt hq gives an agent for the supervisor is announced: before `new` of `hq mcp` releases an agent that has a PROMPT, and before its `send` types into an agent's prompt box a prompt made only of the supervisor's messages, hq writes an empty `ID.next` beside the hook's working files, its word that the agent's next prompt is the supervisor's. The hook keeps what it learns in `ID.sup`, which exists while the turn is a supervised turn:

- A prompt that is not Claude's wake-up takes `ID.next` by renaming it, so the word counts once, and a prompt that finds none is the user's. With it the hook writes `ID.sup`, unless something of the user's may be under way. That is: a message of theirs goes along with the prompt; or, with no `ID.sup` there already, a turn is owed for background work (`ID.owe` holds an id, one that has held back a turn end included, read before the prompt drops those) or the hook's note says working (a turn of the user's at work, should their prompt and hq's cross, or one they interrupted, which no hook reports). Work of both notifies (spec §5). With `ID.sup` there already, everything under way is the supervisor's, and it stays. Without the word the hook removes `ID.sup`: a prompt of the user's makes the turn theirs, also in the middle of a supervised turn.
- Delivering messages (at a Stop, with a prompt, after a tool) removes `ID.sup` when one of them is the user's. The supervisor's own change nothing: its message into a turn the user started leaves the turn the user's, and into its own turn leaves that supervised.
- A Stop that is the agent's end prints no notification while `ID.sup` exists, and then removes it unless a turn is still owed (`ID.owe`, as after a question with subagents running): the mark does not outlast what the supervisor sent. A dialog and a Notification print theirs whatever it says, and neither they nor the dialog's answer touch it: dialogs stay the user's, and answering one does not make the turn theirs.
- Claude's wake-up changes nothing, so the closing turns are of the turn that started the work, a supervised turn the user interrupted included (no Stop removed its mark).
- A session's start, resume or end removes `ID.sup`, so what wakes a new session notifies. It leaves `ID.next`: a new session reports its start before its first prompt (3.4).

Nothing else reads `ID.sup`: the row, `hq ls`, `hq read` and `hq wait` cannot tell a supervised turn (spec §5). The commands learn that they run for the supervisor from the MCP server, which calls them in process (3.12); typed in a shell they leave no mark, so only `hq mcp` counts, and every MCP client is the supervisor. `ID.next` must never fall to a prompt the user sends later. `send` therefore waits until the hook has taken it, looking every 50 ms, and takes it back itself after 3 s (Claude reports a prompt as it is sent) or when typing fails; `hq sandbox restart` takes back the one of a first prompt the session never got to, as the relaunch starts without that prompt. Whenever hq cannot write the word, or took it back, the prompt is the user's: every failure errs towards a notification. An outdated agent (3.3) is sent nothing: `send` refuses it. Costs, all but the last towards a notification. A prompt hq typed for the supervisor that Claude takes up more than 3 s later (one that waits behind a closing turn begun at the same moment) is the user's. The supervisor's prompt after a turn of the user's that they interrupted is taken for one into a turn at work, and notifies at its end (spec §5); the two cannot be told apart by the hook, and the other reading would hide the end of a turn of the user's. A shell command the agent itself started is not in `ID.owe` (a subagent's is, as `~ID`, and keeps the mark while it runs), so nothing says whose it was: the turn Claude takes when it ends after the turn's end finds no mark and notifies (spec §5), also when a supervised turn started it. The gaps left: a supervised turn the user interrupted with nothing owed keeps its mark until the next prompt, so a turn Claude takes meanwhile for a shell command of an earlier turn of the user's ends without a notification; and an `ID.next` whose prompt never comes, with no hq left to take it back (an `hq mcp` ended within those 3 s, or a first prompt Claude never took, without a relaunch), makes the user's next prompt the supervisor's.
**Alternatives considered:** comparing in the hook the prompt Claude reports with the text hq typed (it would have to match Claude's own encoding of a pasted prompt byte for byte, which nothing guarantees); a variable in the settings' environment (it lasts the session, and a supervised turn is a turn's property, not an agent's); deciding on the host (no hq process takes part in a notification: ADR 0002, 0010).

Satisfies: §5 (exactly one notification per attention or done event, docked or not, kind and branch; none for the `done` and `question` of a supervised turn; the `done` of a turn an API error ended notifies about a minute late, not when a prompt comes within that minute, and maybe not while a subagent runs, documented limitations), §10, S4, S5, S5c, Phase 2; drivers 3, 5.

### 3.6 Sandboxes

**Decision:** hq resolves DIR to the main repository root (through git, so a subdirectory or one of Claude's worktrees is the same repository) and finds that repository's sandbox of the agent's setup ([ADR 0015](../adr/0015-one-sandbox-per-repository-and-setup.md)) by workspace path in `sbx ls --json`, then by name (`sbx.Find`): among the sandboxes whose primary workspace is the root, the `default` setup's is the first whose name does not start with `hq-`, whatever its name; another setup's is the one named exactly `hq-<setup>-<dir>`, `<dir>` being the root's base name cleaned as sbx cleans it for its own names (lowercased, then each byte but ASCII letters, digits, hyphens and periods a hyphen, so a letter beyond ASCII is a hyphen per byte: `My_Repo x` is `my-repo-x`, `Zażółć` is `za--------`, verified with sbx v0.47.0; `sbx.SandboxName`). With none, the first `hq new` of that setup creates it: the default's under sbx's own name, another's with `--name hq-<setup>-<dir>`; the one-time Claude login, where one is needed, happens in the docked session (S2). An agent's home window runs `sbx run --name <sandbox> -- --settings '<env + hooks>' [prompt]`, through hq's session program (3.3), whatever its setup: the setup's flags only mean something at creation. Every caller that needs a repository's sandbox (`hq new`, `hq sandbox`) goes through the same lookup, so none takes a setup's sandbox for the default, including one whose setup was removed from the preferences.
**Rationale:** lookup by workspace path cannot collide on two repositories with the same folder name and adopts sandboxes the user created by hand; `sbx ls` carries no labels and no model, so the name is the only marker of a setup sbx keeps, and the `hq-` prefix cannot be mistaken for sbx's own `<agent>-<dir>` names (a suffix would make repository `foo-local`'s default read as `foo`'s `local`, ADR 0015). The row's `setup` (3.12, `hq ls --json`) is read off the name the same way (`sbx.SetupOf`): what stands between `hq-` and `-<dir>`, `default` for any other name.
**Satisfies:** §2 (one sandbox per repository and setup), §4.1 (`hq new`, `hq sandbox`, `hq mcp`), §11 (setups), S2, S11.

- **Which sandboxes `hq sandbox` acts on** (spec §4.1, #136): REPO is a directory in the repository or its name as `hq ls` shows it (matched against the base name of each sandbox's primary workspace, each repository once), and the flags choose among its sandboxes through the same lookup as `hq new`: none, the default's (`sbx.Find` with `default`); `--setup NAME`, that setup's (`sbx.Find` with NAME, whether or not the preferences still define it, so a setup's sandbox can be removed after its setup is); `--all-setups`, every sandbox of the repository (`sbx.OfRepository`: the default's first, then each one named `hq-<setup>-<dir>` on the workspace, in sbx's order; a further sandbox made by hand on the workspace is none of them, since hq never runs an agent there). Without a flag REPO may also be a sandbox's own name as `sbx ls` shows it (#113), which means that one sandbox; the flags take a repository only, so with a sandbox's name, or together, they are a usage error. A repository that has no sandbox of the setup asked for is not found (exit 2). The agents acted on are those whose window names one of the chosen sandboxes. The confirmation names every sandbox chosen, once. An agent's hint to relaunch it (`hq send`, `hq answer` on an ended agent) names its setup when it is not the default (`hq sandbox restart app --setup local`).
- **`hq sandbox restart REPO`** (S9): after confirmation (`-y` skips it, no terminal refuses, as `hq kill`), stop and start the sandbox (every chosen one: all are stopped, then all started, so one wait covers every agent's end), then relaunch each of their agents in its own pane (`respawn-pane`, through hq's session program, 3.3), same window, same name, same id, with `--resume <last Claude session id>` taken from the agent's journal, so each conversation continues. The window is never removed, so the row stays through the restart (`ended` from the `ending` marker, then `starting`), the name stays taken, and a docked agent, whose pane is in the slot, stays docked with its frame. The window's start time moves to the relaunch, set only after the pane is respawned and the `ending` marker is gone, so no look sees the new session ended (and dates that end) as it starts (#104); the journal, kept and numbered on, holds the previous session's reports until the new one reports: a report older than the start gives the branch, worktree and last message, not the state (5.1), so the row reads `starting` with what it last said, until the resumed session reports its start (SessionStart, 3.4) and the row is `done` with the same branch, worktree and last message, taken from the report before it. Start times are kept to the millisecond so a relaunch in the same second as the last report is told apart. After `sbx stop` hq waits for the agents' panes to die (at most the kill's wait), so no hook of the old session writes after the relaunch. sbx has no start command: running anything in a stopped sandbox (`sbx exec`) starts it, which also restarts a sandbox without agents. The session id is read before the stop and passed only when it has the form of a Claude session id, since the sandbox writes the event files; an agent that never reported, or whose session never had a prompt (its latest report a SessionStart of a new session), starts fresh: Claude keeps no conversation for such a session, and `--resume` with its id fails with `No conversation found` (verified with Claude Code 2.1.283 in sbx, #124; after `/clear` it does keep one). An agent killed while the sandbox restarts is not relaunched. The relaunch writes the agent's record (3.3), with the running hq's generation. A restart is refused while the sandboxes hold an outdated agent (3.3), before any agent is marked `ending` or any sandbox stopped: it would relaunch the agent under an hq that cannot continue it; after a host restart, when tmux lists none of the sandboxes' agents, the restart restores their lost agents (3.3) once the sandboxes run again, and its confirmation names them.
- **What a sandbox is created with** (spec §11, #58, #135): `sbx create --no-progress [--name hq-<setup>-<dir>] [--template IMAGE] [--static-mcp A,B] claude WORKSPACE`, or, for a setup with a model or a provider, `sbx run --detach --name hq-<setup>-<dir> [--template IMAGE] [--static-mcp A,B] [--model M] [--provider P] claude WORKSPACE`, since `sbx create` takes neither (`unknown flag: --model`, sbx v0.47.0) and `run --detach` creates and starts the sandbox without a session. These spellings are those of sbx 0.48.0 and newer (verified with the flag parsers of 0.48.0 and 0.53.0, #172); before 0.48 they were `create --quiet` and `run --detached`, which 0.48 no longer knows. `--model` is never given to a sandbox that exists: there it recreates the container. The default setup's image and servers are the `sandbox` object of the per-user preferences file (`template`, a string; `staticMcp`, a list of names registered with `sbx mcp add`), each replaced by `HQ_SBX_TEMPLATE` or `HQ_SBX_STATIC_MCP` (comma-separated) when that is set and not blank; with neither, the command is the one without them. The other setups are the objects of `sandboxes`, by name, with `template`, `staticMcp`, `model` and `provider`, each optional, which no variable overrides; `default` among them is refused with the reason whenever a setup is read (`prefs.Setup`), and so are setups in a form hq cannot read, naming the setting, what it should be and what it is (`"sandboxes.local" should be an object of settings, not a string`, `prefs.FormError`), rather than read as no setups, both prefixed with the file's path; so is an unknown name, listing the setups there are, before anything is created; the default's own object takes no model. The user writes both and hq only reads them, so a write of the file for the list's modes or the update check keeps them as the user left them. `sbx run --name` does not change: the flags only mean something at creation, and a sandbox created by hand with them is adopted like any other. hq neither pulls nor checks the image, the model, the provider or sbx's model feature; when creation fails while a setting is in effect, the error is sbx's (`Failure`) followed by `created with sandbox.template IMAGE (WHERE), sandbox.staticMcp A,B (WHERE)`, for a setup `sandboxes.<setup>.template IMAGE, sandboxes.<setup>.model M, ... (FILE)`, WHERE being the variable or the file's path, named once for settings from the same place, since sbx's error does not say which hq setting it came from. sbx's own limits come back as its errors: a name over 63 characters, and a second repository of the same directory name on one setup (`sandbox 'hq-local-app' already exists and can't be given new workspaces`), as sbx refuses it for its default names. A first creation with a model may take minutes while sbx's `llmman` downloads its runtime; `hq new` waits for it.
- **The oldest sbx** (spec §11, #172): `sbx.MinVersion`, 0.48.0, which changed `sbx ls --json` from `{"sandboxes": [...]}` to the array itself and the flags of `sbx create` and `sbx run` (above); hq uses only the spellings 0.48 and newer accept, with no second path for older ones, as no spelling of the `create` flag suits both. The calls hq makes (`ls --json`, `create`, `run --detach`, `run --name NAME --`, `stop`, `rm --force`, `exec`, `mcp inspect NAME --json`, `mcp add NAME --command C --args A,B`, `mcp load NAME --sandbox S`, `version`) were checked against the flag parsers of sbx 0.48.0 and 0.53.0. hq asks no version up front: the object form of `sbx ls --json` is the sure sign of an older sbx, and only then does hq run `sbx version` (`sbx version v0.48.0 <commit>`, before 0.48 `sbx version: v0.47.0 <commit>`) to name it: `sbx.TooOldError`, which `sbxErr` turns into exit code 3 and one line, `sbx 0.47.0 is too old, 0.48.0 or newer needed; update Docker Sandboxes` (without the version when sbx tells none), as for a tmux too old. A supported sbx costs no process more. The commands that read `sbx ls` fail with it (`hq new`, `hq sandbox`, `hq ls`, `hq read`, `hq send` and its first lookup with `--wait`, `hq answer`, `hq restore`); those that tolerate a failed `sbx ls` (the list's looks, `hq kill`, `hq wait`'s looks and those of `hq send --wait` after its first lookup, `hq explain`, the dialog's sandbox name) take it as one more, and append no `sbx` event from it: `hq explain` shows the journal, which is on the host, and explains a lost agent whatever sbx says. The listing of agents by `hq update` across generations, and the `hq __may-update` the installer asks, are of the first kind with a code of their own: an sbx too old refuses the update with its line and exit code 1, like a failed `sbx ls`, since hq then cannot tell whether lost agents exist (3.9, ADR 0020). The installer checks no sbx version: it checks that `sbx` is there, and asks the installed hq about its agents.
- **`hq sandbox rm REPO`**: refused while agents in a sandbox it would remove run (§4.1), naming those sandboxes and agents, so `--setup local` is not held back by agents of the default sandbox, while `--all-setups` is by any agent of the repository; then hq asks and runs `sbx rm --force` for each (sbx would otherwise ask a second time). When sbx fails for one of several, hq goes on with the others, prints `removed the sandbox claude-app` for those it removed and fails (exit 3) with `could not remove hq-local-app: <sbx's error>` for the rest, each with its own error; without sbx at all it stops at the first, which says so. REPO is a directory in the repository, its name as `hq ls` shows it, matched against the base name of each sandbox's workspace, or the sandbox's own name as `sbx ls` shows it (#113), which also tells apart two repositories of the same name.

### 3.7 Keys and mouse

**Decision:** prefix-free Alt+letter chords, bound in tmux for the `hq` session only, work anywhere in the dashboard, including while typing to Claude in the docked session:

| Chord | Action | Mirrors in the list |
|---|---|---|
| `Alt+j` / `Alt+k` | dock next / previous row | `j` / `k` |
| `Alt+a` | dock the first agent needing attention, skipping the one docked now | - |
| `Alt+l` | toggle focus between list and session | - |
| `Alt+n` | New agent dialog | `n` |

Docking by chord moves the cursor to the newly docked row. Esc is deliberately no focus key: Claude uses it to interrupt, cancel dialogs and rewind (Esc Esc), so it reaches Claude unchanged; `Alt+l` and clicks move the keys (#128). Each chord runs an internal hq command that performs the swap, so it works whatever the list program is doing. Kill stays `k`, `y` (`Enter` means No, ADR 0004).
**Rationale:** walked through the triage, kill, new-agent and name-jump flows: the triage loop is one chord per hop without leaving the keyboard. Alt+Enter (Claude Code's newline), Alt+arrows (word movement in Claude's input; Windows Terminal's pane focus) and Alt+Space (Windows system menu) collide; home-row letters mirroring the list keys do not. Skipping the docked agent in `Alt+a` avoids re-docking an agent whose answer has not yet been reported (up to one refresh tick).
**Alternatives considered:** Alt+arrows and Alt+Enter (collisions above); the tmux prefix (two keystrokes, and tmux's default prefix Ctrl+B is a Claude Code key); function keys (off the home row, need Fn on Mac laptops).
**Satisfies:** §6.3, §6.5 (in-session dock previous/next/first needing attention, focus switching), S3, S4; drivers 2, 4.

- **Option as Alt on macOS.** iTerm2 sends Option as a special character by default; hq's installation adds an iTerm2 dynamic profile with Option as Esc+, and hq switches the dashboard's tab to that profile when it attaches (3.11). No user setup (spec §5, §11).
- **Mouse.** tmux mouse mode on for the `hq` session only. Clicks in the list go to the list program (row: cursor; strip item: action, §6.3, §6.4); clicks in the docked pane focus it and pass to Claude; an open popup takes all clicks (§6.6). Inside `hq` a drag selects through tmux (copy mode); the terminal's own selection stays one modifier away (Option-drag in iTerm2, Shift-drag in Windows Terminal), and other tmux sessions keep the server's setting.

### 3.8 Components of the hq binary

One binary, five roles; they share the row model and never talk to each other directly: tmux and the journals are the only shared state.

```mermaid
flowchart LR
    CLI["CLI<br/>hq new, ls, read, explain, wait, go, code, send, answer, kill, stop, sandbox, restore"]
    LIST["List program<br/>list pane; footer via status line"]
    DLG["Dialog<br/>one process per tmux popup"]
    CH["Chord commands<br/>behind Alt+j/k/a/l/n"]
    MCP["MCP server<br/>hq mcp: tools new, list, read, wait, send, answer, go, kill"]
    TM[("tmux: registry, panes, options")]
    ST[("$XDG_STATE_HOME/hq: the journals<br/>repo/.git/hq: the event files, the inbox, the records")]
    SBX["sbx"]
    CLI --> TM & ST & SBX
    LIST --> TM & ST & SBX
    DLG --> TM & SBX
    CH --> TM
    MCP -- "calls in process" --> CLI
```

- **List program.** Bubble Tea and Lip Gloss: header, rows, action strip, scroll hint (§6.1-6.4), mouse from tmux, colours degrading on terminals with fewer colours. Sets the footer through the `hq` session's status line and clears it on exit.
- **Dialog.** A short-lived hq process in a tmux popup, same library, styled as the mocks (§6.6). It performs its own action (kill, start); the list sees the result on its next tick. It stays open to show an error under a field (duplicate name). `Alt+n` opens the same New agent dialog anywhere. With setups besides `default` in the preferences the New agent dialog has its setup field (spec §6.6) and its popup is three lines taller; its note asks `sbx ls` once per dialog, in the background so typing never waits for it, and finds the sandbox as `hq new` does (`sbx.Find`, 3.6) for the setup chosen and the `dir` typed; one not created yet is named as it will be, `hq-<setup>-<dir>` or, for the default, sbx's own `claude-<dir>` (`sbx.DefaultName`, verified with sbx v0.47.0). An answer for a setup or `dir` no longer shown is dropped. The dialog starts the agent through `hq new`'s start with the setup chosen, so its errors are `hq new`'s. The popup runs a hidden hq command; tmux draws its frame and holds the client's keys, and the list, which opened it, refreshes on while it waits for it to close.
- **Row model.** One model for `hq ls` (plain columns, `--json`), `hq wait` (the rows it returns, as `hq ls` gives them) and the list program (§4.1, §6.1). `hq read` shows the same row, pending messages included, with the agent's detail, read from its journal: the latest turn end's reply with its lines kept (stripped as in 7.3, `ID.reply`), and what the open dialog asks in full (`ID.ask`). Every role reads the agents through one **look** (`agent.Look`, glossary): it reads the home windows, ingests each agent's new event files into its journal and folds it, appends what tmux, sbx's answer and the screens of the agents whose screen may show what no hook reports (captured in one tmux call, 3.4) show that the journal does not hold yet, first append winning, and folds that; it never fails (a failed capture appends nothing of the screens and what the journal holds stands, a journal that cannot be read leaves the agent as its window says, one that cannot be written gets no event), and a screen at rest asks the caller for a second look `RestDelay` later. `hq go`, `hq code`, the dock, the kill, `hq sandbox restart` and `hq restore` read the journals without a look (`agent.FromJournals`, `agent.ReadStates`): they capture no screen and ask no sbx, and of what tmux shows append only the death of an agent's pane, so an `ended` they show rests on an event as any state does. Its sources are the journals' store and tmux's screens (`agent.Sources`), `journaltest.Memory` in the command tests. The row carries the agent's own tasks (3.4, #78): `own_tasks` in the JSON of `hq ls`, `hq read` and `hq wait` (each `type` and `text` in full, `[]` when none), one `own task:` line each in `hq read`, cut as LAST is, and a prefix before LAST in `hq ls` and the list program, their count in Claude Code's footer wording and a dot (`1 shell · `, `1 shell, 1 monitor · `, `agent.OwnPrefix`), dim in the list's row; `last` in the JSON stays the message alone, and where the list drops LAST (below 100 columns) the prefix goes with it. The row's `setup` in the same JSON (#135) is read off its sandbox's name (`sbx.SetupOf`, 3.6), so a row needs no record of its own and an agent keeps its setup when the setup leaves the preferences.
- **MCP server.** `hq mcp`, started by Claude Desktop or Claude Code over its standard input and output; each tool calls the CLI command of the same name inside the process, with its output as the tool's result (3.12).
- **Platform adapter.** Every role reaches `sbx`, the editor, the browser, the notification sequence and the configuration of Claude Desktop and of Claude Code on Windows through it (3.10); nothing else knows the platform.

Satisfies: §4.1, §6.1-6.6, S2, S6, Phase 2; drivers 2, 3, 7.

### 3.9 Distribution and updates

**Decision:** on every `v*` tag the release workflow cross-compiles hq (macOS arm64/amd64, Linux amd64/arm64) and attaches the binaries to the GitHub release, beside the notes written by `scripts/release.sh`. The repository is public, so everything reads the release's public URLs over HTTPS with no login and no `gh`. First install is one command: `curl -fsSL https://github.com/rkrysinski/hq/releases/latest/download/install.sh | sh`; `install.sh` puts the binary in `~/.local/bin/hq` and, on macOS, the iTerm2 profile of 3.7. `hq update` does the same from inside hq with Go's HTTP client: latest release, download, verify, replace itself in one step. Both first apply the update rule ([ADR 0020](../adr/0020-an-update-across-generations-is-refused-while-agents-exist.md)): a release of another generation than the hq they replace is refused while any agent that hq knows exists, so no agent is ever left with an hq that cannot read it. hq looks for a newer release at most once a day and never makes a command wait for the answer (spec §4.2): the answer is cached in the per-user preferences file, and every command reads only the cache. A user command that finds the check due starts it in a detached hq and exits; the dashboard's list checks in its own background. After its output, a user command in a terminal adds the update notice on stderr when the cache holds a newer release; `hq --version` shows the hint, and the dashboard's header shows the newer release after the running version (`· v0.9.2 → v0.9.3 hq update`, spec §6.1).
**Rationale:** one command on both platforms with no tooling beyond `curl` and no login; `gh` stays what it is for the user anyway, the pull request lookup (5.2), and is optional. A command that asked GitHub itself would be as slow as GitHub, or fail with it; a detached check costs a command one process start a day. No daemon (ADR 0002).
**Alternatives considered:** `gh release download` (a login and `gh` for every user, needed only while the repository was private; the first implementation); the GitHub API for the latest tag (`api.github.com/repos/.../releases/latest`: a second base URL, and 60 unauthenticated requests an hour per address, shared behind a company's NAT); asking GitHub inline with a short timeout (still a wait on every due command, and offline a failure to hide); the next command reading what a previous one fetched in-process (a command would still wait on it); a Homebrew tap (poor on WSL); `go install` (every machine needs the Go toolchain).
**Satisfies:** §4.1 (`hq update`, `--version`), §4.2 (update notice, no command waits on GitHub), §6.1 (update hint), §7 (S15), §8 (one-command install), §11; drivers 3, 6.

- A release holds `hq-<os>-<arch>` for each platform, `install.sh`, `GENERATION` and `SHA256SUMS`, at `https://github.com/rkrysinski/hq/releases/download/<tag>/<file>`. The latest release's tag is where `.../releases/latest` redirects (`.../releases/tag/<tag>`; a repository without releases redirects to its releases page, a private or missing one answers 404). `install.sh` (with `curl`) and `hq update` read that tag first and then download both files from that release, so the binary and its checksums always come from the same release, even while another is published. `HQ_VERSION=vX.Y.Z` makes `install.sh` take that release instead. `HQ_RELEASES_URL` replaces the base URL for both `install.sh` and hq, for tests and QA against a stub server that answers the same way.
- **The update rule** (ADR 0020). `GENERATION` holds the release's generation (`version.Generation`, a number and a newline), written by `scripts/build-release.sh` from what `go run ./cmd/hq __generation` prints, and listed in `SHA256SUMS`. `hq update` reads it, checked against `SHA256SUMS`, after the latest tag and before the binary (`Releases.Generation`, at most 64 bytes; a release whose `SHA256SUMS` does not list the file publishes none, which counts as another generation; one without `SHA256SUMS` yet, or whose `SHA256SUMS` lists a `GENERATION` not attached yet, stops the update with `try again in a minute`, exit code 3, since the release workflow publishes the notes before it attaches the files; one the checksums do not vouch for refuses the update with exit code 1, as the binary's mismatch does). Within hq's generation it updates as before, agents running or not. Across generations it lists the agents in the way: the agents of its tmux server as `hq ls` shows them, in any state, `ended` ones included, then the lost agents (3.3, `hq restore`) of every repository with a sandbox, which it learns from `sbx ls` within the list's time limit, then each agent those repositories hold a record of made on another tmux server, which this hq cannot see running or lost (`x (on tmux server qa)`, `(on the default tmux server)`), once by its id. Any agent refuses the update, and so does a failed `sbx ls` (sbx missing, too old, or not answering within 5 s) or a failed tmux, as hq then cannot tell whether one exists: exit code 1, nothing replaced, one line, `hq: not updated to v0.15.0: it is of another generation (4, this hq 3) and agents exist; end them first with hq stop or hq kill NAME: 42 (working), old (ended), x (lost)` (`(it names none, this hq 3)` for a release without one; `... and hq cannot tell whether agents exist: sbx: no answer within 5s` when it cannot tell, with sbx's own line when it is too old). No option lets it through. A development build compares generations the same way.
- `install.sh` asks the hq it would replace, `~/.local/bin/hq`, before it replaces it: `hq __generation` prints its generation, and an hq that answers is asked `hq __may-update TAG GENERATION` (the release's tag and its verified `GENERATION`, empty when it has none), which is the update rule above with hq's own line and exit code 1; the installer then fails with that line, exit code 1. An hq from before generations does not know `__generation`: it is asked `hq ls --json`, and any row in it (a `"name"` line followed by its `"repo"`), or a list it cannot give, refuses the install with the agents' names. A first install asks nothing, and the checks that come before (prerequisites, download, checksums) are as they were.
- The generation stands for the forms it guards only while a change to one of them raises it, so a unit test (`internal/version`) pins a fingerprint of each beside the generation it was pinned at: the hook set and script of `state.Settings`, the fields, types and tags of `state.Record`, the journal's form (the fields, types and tags of `state.Event`, one a line, and of `state.Reply` and `state.Asked`, kept beside it, #193), and what the host takes of the hook's event files (`state.ParseEvent` on probes of every hook event, so taking a fact more or less from a payload demands a pin too). It fails when a form changes and the pin is left as it was, and when the generation moves without the pin; a pull request that pins again without raising the generation says why what agents report is unchanged.
- Requests time out: 15 s for the latest tag, 5 minutes for a download. `hq update` replaces its own executable by writing the new binary next to it and renaming it over it, so hq is never half-written.
- The per-user preferences file is `$XDG_CONFIG_HOME/hq/preferences.json` (default `~/.config`) on both platforms. Several hq processes change it at once (the list's sort, the update check, `hq update`, `hq mcp load` and `hq sandbox` with the sandboxes hq is loaded into), so every change reads, changes and writes it under an `flock` on `preferences.json.lock` (let go when the process ends, however it ends), and every write goes to a temporary file renamed over the file, so a reader never sees half a file.
- The daily check: a command reads `update_checked` from the file without the lock; when it is a day old (or later than now, the clock set back), it takes the check under the lock by storing the current time, so of the hq processes that find it due at once only one checks, and a failed check waits a day like a successful one. It then starts `hq __update-check` detached: its own session (`setsid`), no terminal, stdin, stdout and stderr on `/dev/null`, never waited for; that process asks for the latest tag and stores it as `latest_release`, silently, whatever happens. The list program does the same without the extra process, in its hourly look at the cache. Only the user's own commands start a check (not `hq mcp`, `hq update`, the dashboard's hidden commands or a mistyped one); `hq ls --json` and the like start it, but print no notice.
- The notice is `hq vX.Y.Z is available - run hq update` on stderr, printed after the command's output and error, only when stderr is a terminal and the cached release is newer than this hq; never with `--json`, in `hq mcp`, `hq update`, `hq --version`, the dashboard (`hq`, `hq dash`) or the hidden commands. A development build (version `dev`) neither checks nor tells, and `hq update` moves it to the latest release.
- `install.sh` checks the prerequisites (`git`, `curl`, `tmux` with the minimum version, `sbx`, `code`) and hq checks tmux and, where a command reads `sbx ls`, that sbx is 0.48.0 or newer (*The oldest sbx*, 3.6), and they fail with exit code 3 and the remedy (§4.2). `gh` is not one of them: without it, or logged out, only the pull request lookup (5.2) finds nothing.

### 3.10 Platform adapter

**Decision:** one component is the only code that knows the platform. hq detects it at startup, not at build time: the Linux binary is on WSL when `WSL_DISTRO_NAME` is set or `/proc/sys/kernel/osrelease` names Microsoft. The adapter covers exactly seven concerns. The first two, with the command line sbx's MCP gateway starts hq with (3.12), are the sbx side, a seam of their own put together with the desktop's: macOS and Linux always run the native sbx; on WSL, the Linux `sbx` when `sbx` is in `PATH` ([ADR 0017](../adr/0017-wsl-runs-the-linux-sbx-by-default.md)), otherwise the Windows `sbx.exe`. hq looks for `sbx` by name only and does not check that it is a Linux program: on WSL a Windows program keeps its `.exe`.

| Concern | macOS | WSL |
|---|---|---|
| sbx command | `sbx` | `sbx` when it is in `PATH` (the Linux sbx); otherwise `sbx.exe` through Windows interop. Neither there: `hq: neither sbx nor sbx.exe found; install Docker Sandboxes` |
| Paths between hq and sbx | unchanged | with the Linux `sbx` unchanged; with `sbx.exe` `wslpath -w` towards sbx, `wslpath -u` back (workspace lookup in 3.6, worktree path for `c`) |
| Editor (`c`, `hq code`) | `code PATH` | `code PATH`; the Remote-WSL shim takes Linux paths. hq collects the shim's stderr in a file, never a pipe: on WSL 1 a Windows program cannot open a pipe as its stderr, and the shim then opens nothing and still exits 0 (#7) |
| Browser (`p`) | `gh pr view --web` | the same, with `BROWSER` set to `wslview` or `explorer.exe` when unset |
| Notification sequence baked into the hook (3.5) | OSC 9 (`ESC ] 9 ; text BEL`) | BEL, shown as a taskbar flash; it carries no text. Windows Terminal flashes only with `bellStyle` including `taskbar` in its settings, which it does not have as installed; the user sets it (README, spec §11), hq never edits Windows Terminal's settings |
| Raise the window titled `hq - agents` (3.11) | `osascript` to iTerm2, selecting the session on the attached client's terminal | `powershell.exe`: find the window by its title, ask Windows to bring it to the front, then look at which window is in front. Windows lets only the process with the last input do that and answers "done" to any other while only flashing the taskbar button (the foreground lock, #9), so when another window is still in front the script taps Alt, which makes it the process with the last input, and asks again; if the other window stays in front it fails and `hq go` says so |
| The configuration of an app on the user's desktop, Claude Desktop or Claude Code on Windows, and how it starts hq (3.12) | Claude Desktop's `~/Library/Application Support/Claude/claude_desktop_config.json` (`~/.config/Claude/...` on a plain Linux); no Claude Code on Windows; command: hq's path and arguments, the environment in `env` | `claude_desktop_config.json` in the first there of: `%LOCALAPPDATA%\Claude-Data\claude_*\` (Claude Desktop from the Microsoft Store since late 2026, which gives its processes that folder with `--user-data-dir`, #154); `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude\` (the Store's install before that: Windows gives a packaged app its own `%APPDATA%` there, #25) unless it holds a `.user-data-left.*` marker, which Claude Desktop leaves when it moves to `Claude-Data` and no longer reads the file there; `%APPDATA%\Claude\` (the installer from claude.ai). Several folders of a kind: the first by name. The folders come from one `cmd.exe /d /c "echo %APPDATA%&echo %LOCALAPPDATA%"` and `wslpath -u`. A running Claude Desktop decides instead: PowerShell lists the command lines of the `claude.exe` processes (`Get-CimInstance Win32_Process`); those with a `--type=` are Claude Desktop's Electron helpers (its main process has neither flag, and Claude Code on Windows is a `claude.exe` too), and the first `--user-data-dir` among them names the folder it reads. When that is another file than the order finds, hq writes the one it reads and names both, a sign Claude Desktop moved its configuration again; running, it loads hq only once quit from the system tray. No `--user-data-dir` (the installer from claude.ai) or no answer from PowerShell: the order's file. Claude Code on Windows: `.claude.json` in the Windows user's `%CLAUDE_CONFIG_DIR%` when set, else in `%USERPROFILE%`, from one `cmd.exe /d /c "echo %USERPROFILE%&echo %CLAUDE_CONFIG_DIR%"` and `wslpath -u`; command: `wsl.exe -d DISTRO --exec /usr/bin/env K=V... HQ ARGS...` (`mcp`, or `mcp claude-code`) |

Everything else (tmux, registry, journals, keys, dialogs) is one code path.
Paths cross at the sbx client's boundary: the workspaces sbx reports come back as hq's paths, and the workspace hq gives goes out as sbx's path, so the rest of hq only ever sees its own paths. One set of contract tests (an sbx command; every path survives the trip to sbx and back; a gateway command line that carries hq and its environment) runs against both sbx sides, both adapters and the test fake, which gives sbx Windows-like paths so a test shows which paths went through the adapter.
**Rationale:** these are the only points where the platforms really differ; a narrow interface keeps the rest free of platform branches and lets both sides share one set of contract tests with a fake.
**Alternatives considered:** build-time selection (a WSL binary and a plain Linux binary would differ for no reason); platform checks at each call site (scattered, against spec §8).
**Satisfies:** §2, §4.1 (`hq code`, `hq mcp install`), §6.4 (`c`, `p`), §8 (identical behaviour, platform code isolated), §11, S13; driver 4.

### 3.11 Opening and raising the dashboard

**Decision:** hq never opens terminal windows; it uses the terminal it is run in.
- `hq` / `hq dash` first docks the cursor row when nothing is docked (S1), from what the list would show: the cursor's agent (the `@hq_cursor` session option) when it is still there, else the first row, the keys staying on the list as with the cursor's own docks (3.1). It is done by the command, not the list program, since coming back to a running dashboard starts no list program. Outside tmux it attaches there with `attach -d`, detaching any other client, so there is one dashboard at a time. Inside the `hq` session it selects the dashboard window; inside another tmux session it switches the client rather than nesting.
- On iTerm2, just before attaching, hq sends iTerm2's `SetProfile=hq` sequence, so that tab alone takes the installed profile with Option as Esc+ (3.7). Windows Terminal needs nothing.
- `q` (S8) takes the terminal off the `hq` session once the list program has ended: a client whose last session is another session of the same server is switched back there and shown the S8 hint on its status line; any other client is detached, so tmux restores the terminal (normal screen, full scroll region, mouse off) and `hq` returns, printing the S8 hint. The list pane is left without a list program, so the next `hq` starts it and attaches to the same layout and docked session.
- While attached, tmux sets the terminal's title to `hq - agents` (`set-titles`, the `hq` session only). `hq go NAME` from another shell docks the agent; if a dashboard client is attached it asks the platform adapter to raise the window titled `hq - agents` (3.10); if none is, it attaches in the current terminal as `hq` does. With no terminal to attach in (standard input not a terminal, as under `hq mcp`) it only docks the agent and says to run `hq` in a terminal: it never attaches tmux to a pipe, and never opens a window.
- **After an update to another generation** (spec §6.1). The list program outlives `hq update` and the install script, which rename a new binary over the one it runs from, and a list of an older generation would read agents the wrong way. At its start it takes the path of the hq it runs from (links resolved) and a stamp of that file: device, inode, size and modification time. Every 2 s (8 ticks, one look at a time, in the background of the list's loop) it stats the file again; only when the stamp differs does it ask the hq there `hq __generation`, within 5 s. Same generation: it keeps the new stamp and goes on, so the next look is again a stat alone. Another generation, or an hq that does not know the question (from before generations, as `install.sh` tells one, 3.9): the list program ends its Bubble Tea program and replaces itself with `HQ __list` from that path (`exec`), in the same process and pane. The pane's `@hq_list_pid` stays right, and what tmux keeps (the docked session in the slot, `@hq_cursor`, the panes' sizes) is there for the new list, which lays the window out again as any list program does at its start (3.1, 3.3). A missing file, or an hq that does not answer, decides nothing: the next look tries again. An `exec` that fails leaves the pane's shell with the S8 hint and the reason, the terminal still attached.

**Rationale:** attaching in place avoids driving terminal windows, which differs per terminal; what remains is one narrow action, "raise the window titled hq - agents", with the same shape on both platforms.
**Alternatives considered:** opening a new terminal window per `hq` (iTerm2 AppleScript and `wt.exe` differ in every detail, and the user loses the terminal they chose); several attached dashboards (tmux clients fight over the window size).
**Satisfies:** §4.1 (`hq`, `hq dash`, `hq go`), §4.2 (same from any shell), §6.1 (a dashboard left open across an update), §6.5 (Alt chords need Option as Esc+), S1, S8, S9, S15; drivers 2, 4.

### 3.12 MCP server for the supervisor's client

**Decision:** `hq mcp` is an MCP server over standard input and output, in the hq binary itself, built on the official Go SDK (`github.com/modelcontextprotocol/go-sdk`, v1.8.0). The client, Claude Desktop or Claude Code on the user's machine, starts it as a child process and ends it; it opens no port and leaves nothing running (ADR 0002). It outlives `hq update`, which renames the new binary over the one it runs from: after an update of hq's own generation it goes on as the old hq, which the update rule allows (3.9); after one to another generation it steps aside (below). Each tool is a thin layer over the CLI command of the same name, called inside the process with an empty standard input, its standard output and error as the tool's text and a failure as an error result ("hq: ..." as on stderr):

| Tool | Command | Annotation |
|---|---|---|
| `new(name, dir, prompt?)` | `hq new NAME DIR [PROMPT]`; DIR must be absolute (or `~/...`) and exist, since the server's working directory means nothing | not destructive |
| `list()` | `hq ls --json` (`{agents, next_since}`, each agent with `state_seq` and `completion_seq`; `next_since` a cursor, 3.4) | read-only |
| `read(name, offset?, since?)` | `hq read NAME --json [--offset N] [--since S]` (with `reply_size`, `next_offset`, `next_since`; a reply over 32 KiB in pages, 3.4 "Long replies") | read-only |
| `wait(names?, since, timeout?)` | `hq wait NAMES --json --timeout T --since S`, T 50 s unless given, at most 50 s for Claude Desktop and 1 h for Claude Code (below); `since` required | read-only |
| `send(name, text, now?, wait?, timeout?)` | `hq send NAME TEXT [--now] --json` (`{delivery, next_since}`); with `wait`, `--wait --timeout T`, T as for `wait` (`{delivery, outcome, message?, agents, next_since}`, a stall the tool's error); `timeout` without `wait` is refused | not destructive |
| `go(name)` | `hq go NAME` (3.11: docks; raises the dashboard when a client is attached, else says to run `hq`) | not destructive, idempotent |
| `answer(name, dialog, answers?, cancel?, confirmed)` | `hq answer NAME --dialog ID ... --json` (`{state, next_since}`) when `confirmed` is true, the answers given whole (`{options: [n, ...]}` or `{text}` each, so a text is never read as a number), for a question dialog or a dialog of Claude's own (one option); otherwise it answers nothing and returns an error telling the supervisor to ask the user | not destructive. The user's word comes with the call, as for `kill` |
| `kill(name, confirmed)` | `hq kill NAME -y` when `confirmed` is true; otherwise it ends nothing and answers with an error telling the supervisor to ask the user | destructive. Claude Desktop 2.16120 on Windows ran it without asking (#26), so the confirmation comes with the call |

`hq stop` and `hq sandbox` are not offered (PRD #132), nor is `hq explain` (#202). **The calling agent (#142).** The server cannot tell who calls it: through sbx's gateway (#141) `hq mcp` runs on the host from one registration for every sandbox, with no sandbox or session named to it, and all agents of a repository and setup share their sandbox. The agent's own session can: it carries `HQ_AGENT` in the settings hq gives Claude (3.4). So the refusal is a hook of that session, not a check of the server: a `PreToolUse` hook, matched to `^mcp__.+__(kill|answer|send)$` (Claude names hq's tools `mcp__hq__VERB`, or `mcp__mcp-gateway__VERB` through the gateway), runs the hook script's kind `refuse`, which reads only the payload, writes nothing and, for a call of hq's shape naming `HQ_AGENT`, prints a `deny` decision whose reason is the refusal (the tool's error the supervisor sees); Claude then does not make the call, whatever the permission mode. Hq's shape: every key of `tool_input` is one of that tool's (`kill`: `name`, `confirmed`; `answer`: `name`, `dialog`, `answers`, `cancel`, `confirmed`; `send`: `name`, `text`, `now`, `wait`, `timeout`) and the key hq requires besides `name` is there (`dialog`, `text`), so another server's `kill` or `send` with keys of its own is left alone (a key the hook does not know makes it refuse nothing, so a unit test holds its lists, `state.RefusedInput`, to the tools' inputs); `name` is the input's own, read by a walk of the payload's JSON, never a word inside its text, and one with an escape is not taken for the agent's, since an agent's name needs none. A client outside any agent's session has no such hook and is refused nothing; nor may an outdated agent's older hook (3.3), whose `send`, `answer` and `read` hq refuses anyway. Verified with Claude Code 2.1.317: the payload of an MCP tool's `PreToolUse` is as the fixtures `pre-tool-*.json` show, and the matcher's anchors take `mcp__hq__kill`. The walk costs the script about 600 bytes, 9,810 in all, over the 9 KiB it had been kept within, so its budget became 10 KiB. The hook script's budget now, stated here alone: 10 KiB and 512 bytes since #224 (10 KiB and 256 bytes since #209), the script 10,561 bytes, the settings 13,760 bytes with the longest name, about 13.4 KiB of their 24. `list`, `read` and `wait` give the row `hq ls --json` gives, which carries `asks` (#100): what the agent asks while it `needs input` or has a `question`, null otherwise, as `hq read` shows it, read from the detail of its report only for an agent that may ask. While the agent `needs input` the row also carries `dialog`, the open dialog's id (#90). For an MCP elicitation `asks` has `server`, `message`, and `fields` in the form's order, each with `name`, `title`, `description`, `type` (`string`, `number`, `integer` or `boolean`), `required`, `options` (each a `value` with its `title`; absent for a free field) and `default`, each omitted when empty, or, for a URL-mode form, `url`; `hq read` cuts each line of a form as `LAST` is but the URL, which it prints in full; beside AskUserQuestion's `questions`, never mapped onto them, since a form field is not a pick-one question. The server's instructions and each tool's description teach the protocol of spec Phase 2: status from `list` and `read`, never by asking an agent; ask with `send` and `read` the answer at the stop; watch with `wait` in a loop; never answer a permission prompt or any dialog but a question dialog (an MCP server's form included), tell the user, and answer a question dialog with `answer` only on the user's word, never on its own initiative (the instructions, and the descriptions of `answer` and `send`, which points to `answer` for question dialogs); and that the user is not notified when work the supervisor sent finishes or asks a question (the instructions, and the descriptions of `new` and `send`), so it waits for that work and tells them; and that an agent `done` or `question` with `own_tasks` (3.4, #78) has a shell command or watch of its own still running, for whose end Claude takes another turn, so it waits again if it needs that result, that a dev server may never end, and that the list is the turn end's own and may be stale until the next one (the instructions, shortened in the descriptions of `list`, `read` and `wait`). The commands a tool calls know that they run for the supervisor, so the PROMPT of `new` and the messages of `send` are the supervisor's, and a turn made only of them is a supervised turn (3.5); what the tools return does not change. **`since` is the watch's cursor.** Every `list`, `read`, `send`, `answer` and `wait` result carries `next_since`, a cursor (3.4, "Changes after a cursor"), which every tool that gives it and the instructions say to pass back exactly as given; the rows of `list`, `read` and `wait` carry `state_seq` and `completion_seq`. The instructions and the tools tell the supervisor to pass that of its most recent `wait` or `list` as `wait`'s `since`, naming every agent it follows in each `wait` and acting on the agents a `list` it watches from shows `done`, `question`, `needs input` or `ended` (a `wait` from there returns only later changes), and never that of `read`, `send` or `answer`, which is one agent's (#116): told before to pass the most recent result's, the owner's supervisor took a `read`'s after a `wait` had returned one of two agents whose turns ended in the same second, and the other, later than that `wait`'s point and earlier than the read's, was returned by no `wait` for 29 minutes. Found by the owner in Claude Desktop: `send` typed "No" into an agent in `question`, the agent was `done` about 1 s later, and only then did Claude call `wait` without `since`; the window started at that call, the answer was already before it, and two `wait`s returned nothing. From the `wait`'s before `send`, or `send`'s own `next_since` for a `wait` on that agent alone, the same `wait` returns it at once. So `wait` requires `since` in the tool (an empty one is refused, naming the remedy: with no result yet, call `list` first); the CLI keeps `--since` optional, since a person at a terminal starting to watch means "from now". `new`, `go` and `kill` carry no cursor: they report nothing to wait from. **What `send` says of a later turn (#173).** Of several messages waiting, a slash command is a prompt of its own and the others wait behind the first prompt (3.4, *Messages*), so `send`'s description and the instructions say that when its delivery says the message follows as a prompt of its own, the next `wait` returns the earlier prompt's turn first, with `pending` still counting the message, and a later one the answer; and that a slash command the agent's hooks deliver arrives as text and does not run, which its delivery says, so `/model NAME` is sent while the agent waits at its prompt.

Typed at a terminal, `hq mcp` refuses with the remedy (`hq mcp install`) instead of waiting for JSON.

**After an update to another generation** (spec, Phase 2). An `hq mcp` of an earlier generation would start agents whose hook the installed hq cannot read. It watches the hq it was started from as the list does (3.11): a stamp of the file taken at its start, compared with a fresh stat before each tool call (an SDK middleware on `tools/call`, so every tool and any added later is covered), and `hq __generation` asked only when the stamp changed. Once the answer is another generation it stays so for the life of the process: every tool call returns an error result, `hq: hq was updated: restart hq in this client`, before any command runs, so nothing is started or changed; the rest of the protocol (the handshake, the tool list) still answers. The server's instructions say what the line means: every call fails the same way from then on, so the supervisor stops calling and tells the user to restart hq in that client. The line and that instruction follow the client the server was started for (`mcpClient`'s `updated` and `remedy`): `hq mcp sbx` was started by sbx's MCP gateway on the host, which restarting the Claude Code in the sandbox does not replace, so its line is `hq: hq was updated: on the host, run hq sandbox restart REPO for this sandbox's repository, with --setup SETUP for a sandbox of a setup`, and its instructions tell the supervisor to have the user run `hq sandbox restart REPO` on the host, with `--setup SETUP` when the sandbox is of a setup (named `hq-SETUP-DIR`), which starts the sandbox's hq anew (#249). The line cannot name the sandbox itself: the gateway sets no environment for the server and is itself the MCP client, so nothing tells the server which sandbox it serves; and REPO alone is the repository's default sandbox (3.6, *Which sandboxes `hq sandbox` acts on*), hence `--setup`. Same generation: the new stamp is kept and the tools go on as before; a gateway's server then runs the earlier release's code until its sandbox restarts. A server started by a release before v0.14.0 has no such watch and cannot notice an update at all; the README names the one `hq sandbox restart` such a sandbox needs.

**`wait` and Claude Desktop's limit.** Verified in the Claude Desktop 2.9939.2 app bundle (its bundled MCP TypeScript SDK): a `tools/call` to a local server the user added times out after 60 s (the SDK's `DEFAULT_REQUEST_TIMEOUT_MSEC`), with no progress token sent and `resetTimeoutOnProgress` off, so progress notifications would not extend a call. The only setting is `mcpToolTimeoutSec` (60-3600 s) of an enterprise-managed configuration; neither `MCP_TOOL_TIMEOUT` nor a per-server `timeout` key is read. So `wait`'s default and maximum are 50 s (`DefaultWaitTimeout`), as are those of a `send` with `wait`, the delivery included, 10 s of margin for starting the call and reading the answer, and hq sends no progress notifications and relies on none. Not verified: the limit in the Windows app (reports in anthropics/claude-code, #44032, #65643, speak of about 4 minutes there, which 50 s is below anyway), and the timing observed from a live Claude Desktop conversation, left to the owner's acceptance.

**`wait` and Claude Code's limit (#115).** Read in the Claude Code 2.1.302 bundle: a tool call times out after the server entry's `timeout` (milliseconds; below 1000 it is ignored), else `MCP_TOOL_TIMEOUT`, else 100,000,000 ms (about 28 hours), and never after more than 2^31-1 ms; progress notifications do not extend it either. A supervisor there needs no loop of short calls: in the release that prompted #115 one under Claude Desktop spent 107 `wait` calls in 5 hours. The server learns its client from its command line, `hq mcp claude-code`, which `hq mcp install claude-code` writes, not from the client's name in the initialize request, which no client promises to keep. For Claude Code `wait`'s maximum is an hour and its default stays 50 s, so a supervisor that passes no timeout behaves as under Claude Desktop; the entry's `timeout` is 3,660,000 ms, a minute above the maximum, so an `MCP_TOOL_TIMEOUT` the user lowered for other servers does not cut a `wait` short (a Claude Code that does not know the key drops it). `hq mcp` alone, or `hq mcp claude-desktop`, keeps 50 s: an entry written by an older install or by hand is taken for Claude Desktop's, whose limit cannot be raised. The wait tool's description gives each client its numbers. The user interrupts a long `wait` with Esc, as any tool call.

**`hq mcp install`.** For Claude Desktop (the default, or `hq mcp install claude-desktop`), the platform adapter (3.10) says where the configuration is and how Claude Desktop starts hq; `internal/mcpconfig` edits the file:
- it adds or updates only `mcpServers.hq`, keeping every other key and server with its value, order and formatting of numbers and strings (members are copied as raw JSON), and writes nothing when the entry is already as it would write it, so a second run changes nothing;
- it refuses a file that is not a JSON object, gives a key twice, or has an `mcpServers` that is not an object; it follows a link to the real file, keeps its mode (0600 when it creates it, which it does only inside Claude Desktop's folder: a missing folder means Claude Desktop is not installed, was never opened, or keeps its configuration elsewhere, and hq never creates it, #10), writes a copy of the old file next to it (`claude_desktop_config.json.hq-backup-TIME`) and then the new file under a temporary name renamed over it, so the file is never half written;
- when Claude Desktop's folder is not there, or the file cannot be found or edited safely, it changes nothing, prints the entry (`{"mcpServers": {"hq": ...}}`) to stdout and exits 3 naming the file; it never prints the file itself, which holds other servers' secrets.

The entry records hq's resolved path and the environment hq needs, because Claude Desktop, a GUI app, starts servers with a minimal PATH: `PATH` always (tmux, sbx, git, gh), and `HQ_TMUX_SOCKET`, `TMUX_TMPDIR`, `XDG_CONFIG_HOME` and `XDG_STATE_HOME` when set, so the supervisor sees the tmux server, preferences and journals of the shell that ran the install. On WSL the Windows app cannot run a Linux path, so the entry is `wsl.exe -d DISTRO --exec /usr/bin/env K=V... HQ mcp` (the distribution from `WSL_DISTRO_NAME`), since `env` of the Windows side does not reach the Linux process.

`hq mcp install claude-code` sets hq up among Claude Code's user-scope servers, which every project sees: `mcpServers.hq` in `.claude.json` in `CLAUDE_CONFIG_DIR`, or in the home when that is not set, where `claude mcp add --scope user` writes it. The entry is what that command writes, with the command line and environment Claude Desktop's gets and the timeout above: `{"type": "stdio", "command": HQ, "args": ["mcp", "claude-code"], "env": {...}, "timeout": 3660000}`. This Claude Code runs on the user's machine (a Claude Code inside a sandbox reaches hq through sbx, below): beside hq, where the entry is the same on both platforms, or, on Windows, also as Windows' own `claude.exe`. On WSL the install therefore sets hq up in both, each where that Claude Code has run: the one beside hq as above, and the one on Windows through the platform adapter (3.10), in `.claude.json` in the Windows user's `%CLAUDE_CONFIG_DIR%` or `%USERPROFILE%`, with the entry Claude Desktop's would be, `wsl.exe -d DISTRO --exec /usr/bin/env K=V... HQ mcp claude-code`, plus `type` and `timeout`. Only when Claude Code has run in neither place does it fail as not found, naming both files; a Windows that cannot be asked (no interop) leaves only the one beside hq. Not verified on a real Windows: Claude Code on Windows starting `wsl.exe` as an MCP server, which Claude Desktop does (#25). `internal/mcpconfig` edits the file with the same care as Claude Desktop's (the bullets above), except that it never creates it: Claude Code writes the file at its first start, so a missing one means Claude Code was never run there or keeps it in another `CLAUDE_CONFIG_DIR`. What it prints for the user to run by hand is the command that adds the entry, `claude mcp add-json --scope user hq '...'`, rather than the JSON; for Claude Code on Windows, whose shells quote otherwise, the JSON entry, as for Claude Desktop. **No lost save (#115).** Claude Code rewrites the file often (counters, projects, its own servers). Read in the 2.1.302 bundle and seen in its debug log, it saves with proper-lockfile: it makes the directory `FILE.lock` beside the path it was given (beside a link, not its target), re-reads the file, applies its change and writes it atomically (a temporary file renamed over it), then removes the directory; a lock directory whose time is more than 10 s old is abandoned, and a holder refreshes it every 5 s. When the lock does not come within about 1.5 s (6 retries, cut short in a one-shot `claude mcp`), it logs "Failed to save config with lock" and writes without it. So `internal/mcpconfig` takes the same lock for Claude Code's file (`File.Lock`): it makes `FILE.lock`, takes one older than 10 s for abandoned, waits up to 10 s for a live one (then fails, changing nothing), and holds it for the milliseconds of its own read, merge and write, so a save of Claude Code's waits for it rather than falling back. And since that fallback writes without the lock, it also looks again just before its rename: when the file is no longer what it read, it drops its temporary file and backup and merges again (at most 5 times, then fails, leaving the file to the other writer). Claude Desktop takes no lock, so its file gets only that second look. Measured with Claude Code 2.1.302: 12 `claude mcp add-json` saves while hq rewrote the same file in a loop (about 3,000 installs per run) lost 21 of 72 saves in 6 runs with the hq before this change and none of 132 in 11 runs after it. An `hq` server added with `claude mcp add` at local or project scope takes precedence over the user-scope one in that project; the README says to remove it.

**A Claude Code inside a sandbox (#141).** It has no way to start hq over standard input and output itself; sbx's MCP gateway does it for the sandbox, on the host, and offers the tools in the sandbox as `mcp__mcp-gateway__<verb>`. `hq mcp install sbx` registers hq with sbx under the name `hq`, as `sbx mcp add hq --command CMD --args A,B,...` does, through the seam to sbx (`Sandboxes.MCPAdd`), since sbx keeps its own store and not a file hq could edit. `sbx mcp add` sets no environment for a local server, so the command line sets it: beside hq, `/usr/bin/env K=V... HQ mcp sbx`, with the variables Claude Desktop's entry records; with `sbx.exe` on Windows, the platform adapter's command line for an app, `wsl.exe -d DISTRO --exec /usr/bin/env K=V... HQ mcp sbx`, as Claude Desktop's (3.10). The command line follows where sbx runs, not the platform: the Linux `sbx` on WSL gets the first, the one a user who ran hq with `HQ_PLATFORM=native` already registered, so their next install leaves it alone (#153). `mcp sbx` is served as Claude Desktop is: the gateway gives a tool call 60 s, so `wait` is capped at 50 s. Idempotent by comparison: `sbx mcp inspect hq --json` gives the registered command line whole (`"command": [CMD, A, B, ...]`, sbx v0.47.0); the same one is left alone, any other replaced by a new `sbx mcp add`, which replaces a registration of the same name (exit 0, verified with sbx v0.47.0), so there is always one. sbx fails the inspect of a name it does not know, saying it is not found, which counts as not registered; any other failure is sbx's error, not taken for "not registered". `--args` is split at commas, so a `PATH` or hq path holding one is refused with the reason rather than registered broken. `hq mcp load REPO` runs `sbx mcp load hq --sandbox NAME` for the sandboxes REPO and the flags name, found as `hq sandbox` finds them, after checking hq is registered. sbx loses the load when it restarts the sandbox and says nowhere which sandboxes a server is loaded into (`sbx mcp ls` and `inspect` list servers only, v0.47.0), so hq records each sandbox it loaded hq into in the preferences file (`mcp_loaded`, a list of sandbox names): there, not beside the agents' files in the repository, because a sandbox can write those, and a sandbox that recorded itself would get hq's tools. `hq sandbox restart` loads hq again into each of its sandboxes on that list once they have started, before relaunching the agents; a failed load relaunches them all the same and fails naming the remedy. `hq sandbox rm` drops the sandboxes it removed from the list, failing with `hq mcp unload` as the remedy when it cannot; `hq mcp unload` forgets a listed name sbx no longer lists (a sandbox removed with `sbx rm`). `hq restore` cannot load hq again itself: the restored agents' `sbx run` start their sandboxes in their windows, after it returns, and `sbx mcp load` needs a running sandbox; so it names each such sandbox with `hq mcp load` as the remedy. Of several sandboxes, `hq mcp load` loads the others when sbx fails one, records those in one change of the file and names both. Every agent in a sandbox hq is loaded into sees its tools, so the README says to unload it after the work; sbx has no unload (`sbx mcp` has add, auth, inspect, load, ls and rm, v0.47.0), and `sbx mcp rm hq` would take hq from every sandbox, so `hq mcp unload REPO` drops the sandboxes from the list and says the tools stay until `hq sandbox restart`, which then does not load hq again. `sbx mcp load` needs a running sandbox; `hq mcp load` passes sbx's error on for one that is not. sbx's gateway keeps the `hq mcp sbx` it started for a sandbox running across `hq update`; after an update to another generation its tools fail (*After an update to another generation*) until the sandbox restarts, so `hq update`, once such an update has gone through, names the sandboxes on `mcp_loaded` with `hq sandbox restart` as the remedy, in one line after `updated hq OLD -> NEW`, and adds nothing with an empty list or after an update within the generation (#249). It restarts nothing itself.

**Rationale:** the official SDK follows the protocol as it moves, infers each tool's input schema from a Go struct and has an in-memory transport for tests; calling the commands in process rather than as a subprocess keeps one code path, one set of results and errors, and nothing to find on PATH.
**Alternatives considered:** `mark3labs/mcp-go` (the older community SDK, now overtaken by the official one); a hand-written JSON-RPC loop (the protocol's handshake and schema rules for no gain); running `hq` as a subprocess per tool (a second process, and output parsing, per call); an HTTP server (a port and a daemon, against ADR 0002; parked again for Claude Code on 2026-10-18, #115); progress notifications to hold `wait` open longer (neither client resets its timer on them); running `claude mcp add --scope user` for Claude Code (it refuses an entry that is there, so an update is a remove and an add, and it needs `claude` on hq's PATH; the file edit keeps one way for both clients, with its backup and refusals); one `wait` maximum for every client, Claude Desktop's limit left to its documentation (a supervisor there that asks for more fails instead of hearing "nothing yet").
**Satisfies:** §4.1 (`hq mcp`, `hq mcp install`), §11, S15, Phase 2; drivers 3, 4, 7.

## 5. Key algorithms & data structures

### 5.1 Look loop

Problem: state visible within 1 s (§5), CLI changes within 1 s (§4), an externally stopped sandbox `ended` within 2 s of its having stopped (§10), with no daemon.

**Decision:** a look every 250 ms, no file watching: ingest, append, fold (3.4, *Events and journals*). Every 250 ms the list program makes one tmux query (home windows, their options, pane liveness), and a second only in a look that found an agent's journal gone (3.4, *Changes after a cursor*), with one more for each piece of evidence it appends to a journal that is not there, under the store's lock, so the journal of an agent killed meanwhile is not written back (3.4, *Lifetime*), ingests each agent's new event files into its journal, appends what the screens, tmux and sbx show that the journal does not hold yet, and folds the events appended since its last look: it keeps each agent's fold (`agent.Folds`) and reads its journal on from where it stopped (`journal.Store.ReadFrom`), so a look at journals of 50,000 events reads and folds only the new ones, and an append reads on from the append before (`ID.read`). Every 1 s it runs `sbx ls` once. `hq ls` takes one look, folding each journal from its start. `hq wait` takes a look every 250 ms until it returns, keeping its folds as the list does, with `sbx ls` once a second in the background as the list does (its first look waits for sbx's answer), so it sees what the list sees when the list sees it; its default timeout, 50 s, is a little below the 60 s MCP clients commonly allow a tool call (the MCP SDKs' default request timeout), so a wait called as a tool returns "nothing yet" before its caller gives up; `hq mcp` (#136) sets it from Claude Desktop's measured limit (`cli.DefaultWaitTimeout`).
**Rationale:** at A3's scale a tick is one tmux call (two in a look that found a journal gone), about 15 directory reads for event files and 15 reads of what was appended since; a look on a timer gives one code path on both platforms and bounded latency (250 ms for tmux and hooks, 1 s for sbx). Every process folds the same journal, so the list, `hq ls` and `hq wait` show the same state and age.
**Alternatives considered:** OS file watching (FSEvents, inotify): platform-specific, and tmux and sbx would still need polling.
**Satisfies:** §4 (dashboard reflects CLI within 1 s), §5 (1 s), §10 (2 s), S4, S7; drivers 3, 5.

```
every 250 ms:
    counter <- the journals' counter, under the lock (hq ls --json, hq wait: the cursor's floor, 3.4)
    windows <- tmux: home windows with options, pane dead?
    for each agent: ingest its new event files into its journal; fold the events since the last look, noting the counter of each read
    every 4th tick: running <- sbx ls
    for each agent whose pane is dead: append PaneDied (dated by tmux) unless the journal holds it
    for agents reported, not since sbx was asked, and sandbox not in running: append NotRunning (asked at)
    for agents working or needing input for 500 ms+: screen <- tmux capture-pane (one call); turn the user ended -> append TurnEnded; screen at rest -> AtRest, unchanged for 2 s -> Rewound (3.4)
    for agents needing input at a dialog the hooks reported (not a subagent's): Claude at work on the screen -> append AtWork (3.4)
    for agents done, with a question or working only on background work, for 500 ms+: screen <- the same call; a dialog of Claude's own -> append OwnDialog, gone -> OwnDialogGone (3.4)
    fold what was appended -> state, since, last, branch, dialog verdict, state_seq, completion_seq; ended since the event that ended it (3.4)
    for agents whose journal the look found gone (holding nothing when read, or removed while it looked): windows <- tmux again, once; leave out those whose window has gone (hq kill, 3.4)
    hq ls --json, hq wait: cursor <- the lowest counter of the last reads; the counter above when no journal was read, one could not be, or windows listed again show a new agent (3.4)
    for agents at their prompt with a message waiting 6 s+, one round at a time beside the loop: box empty and at rest -> type the messages in (3.4, Messages)
    rows <- sort(agents, mode)                  # every agent (ADR 0016)
    redraw list and footer if anything changed
```

`ended` has three sources, first one wins: the pane's process died (Claude exited, launch failed, or `sbx run` returned because its sandbox stopped), the session-end hook, or `sbx ls` no longer listing the sandbox as running. sbx's answer counts only for an agent that has reported: before its first report the session may still be waiting for `sbx run` to start a stopped or just created sandbox, which takes seconds, and the agent is `starting` (S2); should the sandbox stop before then, `sbx run` returns and the pane's death ends it. Nor does it count for an agent whose latest report is newer than the moment hq asked sbx (#48): hq keeps an answer for up to a second, and `hq ls` reads the agents after it has one, so an answer taken while a sandbox was starting ("stopped") can be older than the first report of a session in it. A report after the question proves the sandbox ran after it, so the reported state stands and the next answer decides. Every answer carries the moment it was asked for (`agent.Sandboxes`), taken before `sbx ls` starts; both it and a report's time are host times (7.1). A sandbox that has stopped ends its agents as before: their last reports are older than every answer asked after the stop. The answer that ends an agent is appended to its journal (`NotRunning`, with the moment sbx was asked), so the agent stays `ended` for every process, also for a look that cannot ask sbx; an answer sbx did not give (failed, slow, or an sbx too old, *The oldest sbx* in 3.6) ends nobody and is no event.

### 5.2 Pull request lookup

Problem: the strip shows `p pr` only when the branch has a pull request (§6.4), without the network in the 250 ms tick.

**Decision:** the list program keeps an in-memory map branch -> pull request (number, state, URL) per repository shown, filled in the background by one `gh pr list --state all --json number,headRefName,state,url` per repository; with several pull requests on one branch the newest wins. It refreshes a repository at list start, every 60 s, and at once when one of its agents turns `done`. `p` opens the URL from the map through the platform adapter's browser (3.10); if the map was stale, the footer says `no pull request for BRANCH`. When `gh` is missing, logged out or offline, the strip leaves out `pr` and the list shows no error.
**Rationale:** one call per repository per minute is far below GitHub's limits at A3's scale; refreshing on `done` catches the moment a pull request usually appears (S5).
**Alternatives considered:** `gh pr view BRANCH` per agent per tick (network in the loop, one call per agent); lookup only when `p` is pressed (the strip could not know whether to show `pr`).
**Satisfies:** §6.4 (`pr` shown only with a pull request, `p`), S5; drivers 5, 7 (the same map can feed the Phase 2 pull request status column, spec §9).

## 6. Conceptual data model

No database; each entity lives where its source of truth is.

    AGENT ||--|| HOME_WINDOW : "exists while"
    AGENT ||--o| STATE_FILE : "reported through"

## 7. Cross-cutting concerns

### 7.1 Failure handling

The CLI follows spec §4.2 (exit codes 0-4, one `hq:` line naming the remedy). Underneath the dashboard and the hooks:

- **Hooks never get in the way.** The injected hook always exits 0 and never blocks Claude, with one exception ([ADR 0012](../adr/0012-hq-send-messages-cross-into-the-sandbox.md)): the Stop hook blocks the stop while a message from `hq send` is unread, taking it as it delivers it, so a stop is held back once per batch of messages and never loops. The hook that holds on a question dialog for hq's answer ([ADR 0013](../adr/0013-question-dialogs-are-answered-through-their-own-hook.md)) blocks nothing: Claude draws the dialog and takes an answer at the terminal while it holds, and it ends by itself once the dialog closes, or at its timeout of a day. If it cannot write its event file, the agent keeps working and the row keeps its last state; the pane's death still gives `ended`. If it cannot move a message, the message waits for the next hook.
- **sbx down is not a missing sandbox.** A failed or timed-out `sbx ls` (no answer within 5 s; it usually answers in under a second), or an sbx too old (*The oldest sbx*, 3.6), changes no row and appends nothing; sbx contributes `ended` only when `sbx ls` succeeds without listing the sandbox as running (5.1), and that answer, once appended to the agent's journal, stands. While sbx is unreachable the header shows `sbx ?` after the clock, in the clock's dim style: once its last successful answer, or the start while it has not answered, is more than 8 s old. An `sbx ls` starts at most 1 s after the last answer and may take up to its 5 s timeout, so an sbx that answers, however slowly, leaves at most 6 s between answers; past 8 s at least one call failed or timed out. A hung sbx is seen about 2 s after its first call times out, one that fails at once within 8 s. The next successful answer removes it. While sbx answers, the header's right side is the clock and the version only; like the clock and the version, `sbx ?` keeps its place in a narrow terminal (S12); `gh` failures only hide `pr` (5.2).
- **A crashed list program leaves the window intact.** Its pane falls back to a shell as after `q` (S8), with one `hq:` line, and the terminal stays attached so the line is seen; the docked session is untouched and `hq` brings the list back. Diagnostics go to a small, size-capped per-user log in the XDG state directory, never into the list.
- **Times are host times.** `AGE` and `since` come from the events of the agent's journal: an event of the hook is dated by the host's modification time of its event file, not by a timestamp written inside the sandbox, whose clock can lag after the host sleeps, and an event of hq's own by the clock of the process that appends it; after a sleep `AGE` shows real elapsed time, and `hq ls` agrees with the dashboard. The events are ordered by their numbers, never by a clock (ADR 0018), so a host clock moved back and forward again changes no state, but for the two comparisons with a launch below: the moment a state counts from is an event's time, kept in the journal, and only the age, counted to the moment of the look, moves with the clock. Two times are compared all the same, both with the time of the agent's latest launch or relaunch (ADR 0018, amended; the operator's decision on #191, [S4](https://github.com/rkrysinski/hq/issues/191#issuecomment-6913577968)): a report counts for the agent's state only when its time is not before that launch (`Fold.session`), so a report of the session before it, whose event file is ingested only after the launch's event (`hq sandbox restart` takes the agent down and relaunches it with no look in between, and the old session's SessionEnd lands after `Relaunched`), does not end or move the relaunched agent; and a pane's death that tmux dates more than a second before that launch ends nobody (`Fold.DiedBeforeLaunch`), so a look that listed the windows before a relaunch respawned the pane does not end the relaunched agent for good. The cost, accepted: a host clock set back after a launch shows that agent `starting` until a report is dated after the launch, and while the clock is behind, a death of its pane dated before the launch is not counted as its end either.
- **GitHub slow or unreachable.** No command waits on it: the update check runs detached (3.9), gives up after 15 s and fails silently, and the next one comes a day later. `hq update` alone waits for GitHub, since that is its job, and names the URL when it fails.
- **Concurrent `hq new NAME`.** tmux has no atomic create-if-absent, so uniqueness (§4.2) is checked again after the home window is created; of two windows with one name, the later removes itself and exits `1`. No lock file.

**Satisfies:** §4.2 (exit codes, errors, name uniqueness), §5 (states truthful), §10 (externally stopped sandbox `ended` within 2 s, without false `ended`), S7, S8, S9; drivers 3, 5.

### 7.2 Testability

**Decision:** six seams, each an interface with an in-memory fake: tmux, sbx, gh, the platform adapter (3.10), the clock and the journal's store (`journal.Store`: ingest, append, read on from a position, remove; `journal.Files` the real one, `journaltest.Memory` its fake, which the command tests fill with the hook's payloads, `journaltest.Contract` run against both), which took the state-file reader's place (#198); nothing else touches a process or a file, but for the MCP clients' configuration files (Claude Desktop's, Claude Code's `.claude.json`), edited by `internal/mcpconfig` (3.12), and the per-user files beside the preferences file, the preferences (`internal/prefs`) and the trace of kills (`internal/kills`, 3.3), and the hq on disk the list and `hq mcp` watch (its stamp, its generation, and the list run from it in place of the old one, 3.11, 3.12), each behind a function in the command's dependencies and tested on temporary directories. The pyramid of `docs/agents/testing.md` maps to Go as:

### 7.3 Security

The one boundary hq opens is files written inside the sandbox and read and shown on the host. The threat is Claude, or content it read from a repository or the web, pushing something harmful across it. A spoofed state is harmless: the user's own agent misreporting itself.

- **Output is stripped.** `last_assistant_message` and every other field from a hook's report lose control characters and escape sequences before they reach the list, `hq ls` or `hq read` (which keeps a reply's lines, tabs as spaces), so a message cannot retitle the terminal, redraw the screen or fake a notification.
- **Event files are data only.** Of what the sandbox writes for an agent hq reads only `events/ID/` for ids it issued, and none of the hook's working files in `agents/`; it checks with `lstat` and opens without following links, rejecting anything but a regular file, so a symlink planted in the repository cannot make the host read `~/.ssh/...` and show it in `LAST`; it caps the size at 16 MiB and parses defensively. The cap bounds what a planted file costs, not what an agent may say: a regular file over it is shown as a report too large to read, with its size, never ignored (3.4, "Long replies"). An event file it cannot read (a link, a pipe, over the cap, no payload) is appended as an event of kind `unreadable` with its size, and removed (a link, not its target).
- **The journal is out of the sandbox's reach.** It lives in the user's state directory, so an agent cannot rewrite what hq learned of it; an event holds less than the file it came from, so the sandbox gains no way to fill the user's disk that the mounted repository does not already give it.
- **A record names only what the sandbox could reach anyway.** The sandbox can write `ID.hq` too, so hq reads a record as it reads an event file (a regular file, not followed, capped at 4 KiB), checks its name as `hq new` checks one, takes the repository from where the record lies, never from its content, and launches only in a sandbox of that repository: a planted record can at most start an agent of a made-up name in the repository's own sandbox, which the sandbox can already run.
- **The trace of kills is out of the sandbox's reach.** It lives in the user's configuration directory, not beside the agents' files in the repository, so an agent that kills another (with hq loaded into its sandbox) cannot erase or forge the line that says so. What a line says of an MCP client (its name and version) is the client's own word. `hq killed` strips every field it shows, as the list strips a hook's report, since the client names itself.
- **No shell in between.** hq starts processes as argument lists, tmux's `new-window` in its multi-argument form that executes directly; names are restricted by §4.2; prompts and paths are always one argument, never pasted into a command string. The injected hook never uses the branch or the message as a `printf` format or in `eval`.
- **The supervisor gets what a shell gets, less.** `hq mcp` listens on nothing: it is a child of Claude Desktop or Claude Code, spoken to over a pipe. Its tools are the CLI's own commands, without `stop` and `sandbox`, and a message it sends goes through `hq send`'s stripping and caps. `hq mcp install` never prints the client's configuration, which holds other servers' secrets (Claude Code's also the user's projects and account), and its copy of the file keeps the file's mode.
- **Updates are verified.** Releases come over HTTPS from GitHub; every release publishes `SHA256SUMS`, and `install.sh` and `hq update` check the downloaded binary, and the release's `GENERATION` before they act on it, against it before replacing anything (3.9); a `GENERATION` an attacker removed only makes the update refuse more often. `HQ_RELEASES_URL` can point both elsewhere, which only whoever already controls the user's environment (and so `PATH`) can set.
- **Nothing new crosses the sandbox boundary, but messages and answers.** The hook writes only into `.git/hq/` of the already mounted repository; hq passes nothing into the sandbox beyond what `sbx run` receives at launch, with one exception ([ADR 0012](../adr/0012-hq-send-messages-cross-into-the-sandbox.md)): the text the user gives `hq send`, which reaches Claude as a prompt the user could have typed into the session. hq strips it of escape sequences and control characters but newlines and tabs, caps it at 8 KiB and encodes it as JSON on the host; the hook only moves and copies it, never evaluates it or uses it as a format; typed in, it is one bracketed paste, or, for a slash command Claude Code would collapse, its command word typed literally (`send-keys -l`) and the rest pasted (3.4), so no key in it acts. hq reads an inbox's files as it reads event files (no links, capped size), and drops one that is not a message; an agent's events directory or inbox (with its `held/`) that is a link, or lies under a directory of `.git/hq` that is one, is refused for listing, reading, writing and removing alike (`state.LinkedAt`, #193, #215), and one that is itself a link loses the link alone when its agent is removed. Besides the text, one bit crosses: whether a prompt or a message is the supervisor's (`ID.next`, an empty file, and a message's name; 3.5). The sandbox can write those itself, as it can every file under `.git/hq/`: all it gains is more or fewer of its own notifications. hq writes `ID.next` as a file of a new name renamed into place, as it does a message, so a link the sandbox plants at that name is replaced, never written through. The answer to a question dialog ([ADR 0013](../adr/0013-question-dialogs-are-answered-through-their-own-hook.md)) crosses the same way: a PermissionRequest decision hq encodes on the host from the dialog's own tool input and the user's choice, labels taken from the dialog or free text stripped and capped at 8 KiB as a message is, written aside and linked into place under a name of its own; the hook only renames and copies it. An option of a dialog of Claude's own ([ADR 0014](../adr/0014-dialogs-of-claudes-own-are-answered-with-keys.md)) crosses as keys, `Down`, `Up` and `Enter` by their tmux names, pressed in the agent's pane as a person would: nothing of the user's text.

**Satisfies:** §2 (sandboxes as isolation), §5 (last message shown), §8; drivers 1, 6.

## 8. Risks & open questions

- **Repositories on the WSL file system (closed, #153).** The team runs the Linux `sbx` inside WSL, which mounts the WSL file system as its own, and hq uses it by default ([ADR 0017](../adr/0017-wsl-runs-the-linux-sbx-by-default.md)); the question stays open only for `sbx.exe`, and is not pursued. As it was: Whether `sbx.exe` can mount a repository that lives in the WSL file system (`\\wsl.localhost\...`) at usable speed for Claude's work. Unknown until the team runs hq on WSL. Rule fixed in advance:
  - it works: nothing changes;
  - it does not: spec §11 states that on Windows repositories live on the Windows file system (`/mnt/<drive>/...`); `hq new` refuses a DIR outside it with exit 3 and the remedy; the platform adapter (3.10) opens the editor with Windows VS Code on the Windows path instead of the Remote-WSL shim.
