# Testing hq

hq's own testing rules, beside the template's `docs/agents/testing.md`; where the two differ, this file holds for hq. hq is written in Go (ADR 0011). The seams and levels are designed in `docs/design/hq.md` §7.2.

## Where a test goes

| Level | Selected by | Use it for |
|---|---|---|
| Unit | no build tag; `_test.go` next to the code | Pure logic: parsing, state and attention rules, sorting and filtering, what a dashboard row or a command's output contains, mapping the answer of `sbx`, tmux or a hook with a fake. No processes, sockets, terminals or real `sbx`/tmux |
| Integration | `//go:build integration`; `_integration_test.go` next to the code | The contract of a command or an adapter: what it runs against tmux (on a private socket per test, `tmux -L`), a stub `sbx`, `gh` or `wslpath` (`testutil.WSLStubs` runs the WSL side on any machine, with the stubs listed in `internal/testutil/wsl-stubs`, which `scripts/local-dev.sh --stub` puts in place for QA too; `testutil.FakeClaude` puts `tools/fakeclaude` behind the stub `sbx run`, firing hq's injected hooks with Claude's payloads as it is prompted, and running a question dialog's hooks side by side, so it takes an answer from a hook's decision as from a typed line; a package whose tests call it runs them from its `TestMain` with `os.Exit(testutil.Main(m))`, which removes the fake once they end, and `FakeClaude` fails a test of a package that does not), or the file system, and what it reports. Flows that need a real process, file or socket |
| End-to-end | `//go:build e2e`; in `e2e/` only | A few critical journeys a person drives in a terminal (start an agent, see it, enter it, kill it; install and update), in real tmux with the stub `sbx` and `gh` |

Rules of thumb, beside the template's:

- **External tools sit behind an interface** (tmux, `sbx`, `gh`, the platform adapter, the clock, the journal's store) with a fake for tests, so unit tests never call the real tool. Platform-specific adapters (macOS, WSL) get the same contract tests.
- **Wait for tmux to reap an ended pane before looking at it.** On WSL 1 tmux now and then misses that a pane's program exited: the pane is dead, but without its time, status and "Pane is dead" line until another child of the server exits (#22). A tmux test that asserts any of those calls `reaped(t, socket)` after the pane is dead.
- **Run tmux with `-u`.** hq passes it to every tmux command (design 3.2); a test that runs tmux itself does too, or what it reads depends on the machine's locale (#41).
- **Never touch the user's tmux server or sandboxes from a test.** Integration and end-to-end tests use a private tmux socket and the stub `sbx`. A test that starts hq says which platform it runs as, so the suite behaves the same on macOS, Linux and WSL: `testutil.SbxStub` sets `HQ_PLATFORM=native` (hq runs `sbx`, the stub, never the `sbx.exe` of a WSL machine) and `testutil.WSLStubs` sets `HQ_PLATFORM=wsl` (hq runs the stub as `sbx.exe`, whatever `sbx` is in `PATH`); a test that uses neither and starts the hq binary sets it itself.
- **A reducer rule that depends on the screen is tested through the screen.** Pass the capture through `ScreenMayTell` and `Sees`, the way the reducer meets it, never append the event the screen would give: a unit case that skips `ScreenMayTell` lets a rule through that never fires on a real screen (#232).

## Commands

The template's *Wiring the checks* is done: `scripts/check.sh` is hq's, `.github/workflows/tests.yml` sets up Go at `go.mod`'s version and tmux, and `scripts/local-dev.project.sh` is not used (hq runs with its own `scripts/local-dev.sh`, `docs/hq/agents.md`, *Local run*).

`scripts/check.sh` is the full build: every step the test workflows run, in their order (vet for every build tag, formatting, the pyramid gate, the platform gate, the time-bound gate, unit tests, integration tests with coverage, the coverage gate, the end-to-end journeys), and they run nothing else (`.github/workflows/private.yml`, below, checks private details apart). Run it, from any directory, before you hand work over. It prints `check: ok   <step>` per passed step and stops at the first failure with `check: FAIL <step>`, that step's output and `check: stopped at <step> on <commit>` (exit 1). Its last line, `check: all <N> steps passed on <commit>` (exit 0), is the test evidence: `<commit>` is HEAD's full sha, followed by ` with uncommitted changes` when the tree is not clean, so only a clean tree's line vouches for a commit. Every temporary file of the run, the tests' among them, goes to a directory of the checkout's own outside the tree, `hq-check-<n>` in the caller's `TMPDIR` or `/tmp`, exported as `TMPDIR` (#226); a run that ends leaves it empty, and one that is killed leaves its files there. Remove such leftovers from that directory only, never by a pattern in the shared temporary directory, where other checkouts' tests are running. A passed step's output is not printed: CI puts the pyramid and coverage figures in the job summary, and locally the single commands below print them. The single steps, to run one at a time:

```bash
go test ./...                                          # unit
go test -tags integration ./...                        # unit + integration
go test -tags e2e ./e2e/...                            # end-to-end journeys
go run ./tools/testgate pyramid                        # counts per level, checks the shape
go run ./tools/testgate private [PATH...]              # no private details (needs the pattern list)
go run ./tools/testgate prepost < HOOK_INPUT            # no private details in what a gh command posts (Claude Code's hook)
go run ./tools/testgate platform                       # platform-specific names only in internal/platform
go run ./tools/testgate timebound                      # no test bounds real elapsed time under 1s
go test -count=1 -tags integration -coverpkg=./internal/... -coverprofile=cover.out ./... \
  && go run ./tools/testgate coverage cover.out        # coverage threshold
go run ./tools/testgate mutation BASE [PATH...]        # mutation tests of the lines changed against BASE, part by part with PATHs (not in the full build)
```

## Mutation tests

Coverage says a line ran under a test, not that a test would fail if the line were wrong; a mutation run checks the second (#204). A mutant is one small change to the code, for example `<` into `<=`. It is killed when a unit test then fails, alive when every unit test still passes, timed out when the tests did not finish within the limit, and not covered when no unit test runs its line.

**The rule.** Every pull request that runs the full build also runs `go run ./tools/testgate mutation BASE`, each time the full build is run for it: after implementing, after review fixes, and after the rebase before the merge. It runs after the full build, on the same tree, and is not a step of it: CI does not run it, and its block in the pull request's `## QA` section is the evidence (`docs/hq/qa-evidence.md`).

- **BASE** is the branch the pull request goes into: `origin/dev` for a single issue, the release branch for a ticket of a supervised release. In a spec built on one integration branch, each ticket's implementer runs it against the integration branch before reporting, and the orchestrator runs it once on the integration branch against `origin/dev`, after the review fixes and before the pull request is ready.
- **What passes**: no mutant left alive in the changed lines. For each survivor, write a unit test that kills it, or give a one-line reason of equivalence in `## QA` next to its line: a mutant that does not change behaviour (an equivalent mutant, such as `<` into `<=` where the two values are never equal) cannot be killed by any test. A mutant is equivalent only when no input tells it from the original. A difference a test can see is a change of behaviour, however small: a result that comes later (one look later), one call more or fewer, or another step a test can see on the way to the same end result. Such a mutant gets a test, so try to write the killing test before writing a reason. Every run whose block is in `## QA` follows this rule, whatever its base and whichever commit of it the run was made on; another run that covers the same line, such as a run over the whole release, is not a reason. A timed-out mutant fails the run the same way, until a rerun kills it or it is explained (why the tests hang under it). An accepted survivor stays in the command's output; the reason next to it is what makes it pass. Not covered is a count, never a failure. There is no minimum share and no figure for the whole module.
- **In parts**: a block covers a pull request's change when its last line counts 0 changed files in no part, or when another block of the same `## QA` covers the files it lists in no part (*In parts*, below).
- **Exempt** are only the master pull request of a release (each of its tickets had a run) and a revert. No kind of change is exempt: where there is nothing to mutate (documents, CI files, shell scripts, tests only, Go lines with nothing to change), the command says so, and that line is the evidence.
- **Shell scripts get no mutation check**: the tool changes Go code only. Their Go integration tests stay their check.

**What it does.** It makes mutants only in the lines of Go code, not tests, that the working tree changes against its merge base with BASE, uncommitted and untracked files included: a branch behind BASE is not charged for what BASE gained meanwhile; every changed line, also one that follows unchanged lines in its hunk, since the staging repository diffs with no context lines (`diff.context` 0), where the tool reads a hunk as one run of added lines. The mutants are the five kinds the tool makes by default: arithmetic operators (`arithmetic base`), comparison boundaries (`conditionals boundary`), negated conditions (`conditionals negation`), increments and decrements (`increment decrement`) and negated numbers (`invert negatives`). Each mutant is judged by the unit tests of the whole module (`go test ./...`, no build tag), so a line counts as covered when a unit test of any package runs it, and a mutant in a `package main` directory gets a real test run. The tool is go-gremlins, pinned in `tools/testgate/mutation.go` (nothing in `go.mod`) and installed fresh for each run. A run copies the files git tracks or would track into a temporary directory (git's objects are borrowed, not copied; other worktrees and ignored directories stay out), uses a build cache of its own there and removes the directory when it ends, also when it fails or is interrupted (Ctrl-C, SIGTERM): the shared Go build cache does not grow from it. It needs the module cache to hold the tool, or the network once. The tool counts every failing run of the unit tests as a kill and never sees why, so a mutant counts as killed only when what failed with it passes without it: the gate puts a `go` of its own (its own binary) before the real one in the tool's `PATH`, and when a mutant's run fails it runs, uncached and in the staged tree without the mutant, the top-level tests that failed, the build of a package that did not build, a package's tests when the output names none, or the whole unit suite when it names no package, and that run has to be over two seconds before the mutant's time limit ends, so a healthy machine's verdict stays what it was; when it fails, the run ends with exit 2 (#234). That go tells the gate by removing a file of the run, which needs no free disk, beside a record of the run again when one can be written.

**In parts.** `go run ./tools/testgate mutation BASE PATH...` runs the same mutants part by part, one part per PATH, for a change too large for one run's build cache (the run over the whole of release v0.14.0 took the sandbox's disk under 2 GB twice). A PATH is a package's directory, which names the Go files directly in it and not those of the directories below, or one Go file; only files git tracks or would track count. The parts run one after another, in the order given; each makes mutants only in the changed lines of its own files and has a build cache of its own, removed before the next part starts, so the disk a run needs is that of its largest part. A mutant is judged as in a run without PATH, by the unit tests of the whole module, so a part's verdict on a line is the whole tree's; a part's file that git, over the whole tree, pairs as the rename of a deleted file is paired with it in the part too, and any other new file counts as new in its part as it does over the whole tree, so the part gets mutants in the same lines. A part whose files change no production file runs nothing and is no error: name every package without looking first. A PATH that does not exist, lies outside the repository or names no Go file of it, and a file two PATHs cover (a file and its directory, or the same PATH twice), end the run with exit 2 before any part runs; a part that fails, or an interruption, ends the whole run as it ends a run without PATH. Without a PATH the command is the one run above.

**Its output.** One line per alive and per timed-out mutant, in file and line order: the verdict, the file, the line and column, the kind. The last line gives the counts, BASE and HEAD's full sha, followed by ` with uncommitted changes` when the tree is not clean, as the full build's last line does; only a clean tree's line vouches for a commit. Progress goes to stderr.

```text
alive      tools/testgate/push.go:94:14 conditionals boundary
timed out  internal/dash/dash.go:120:9 arithmetic base
mutation: 23 killed, 1 alive, 1 timed out, 0 not covered against origin/dev on <commit>
```

When the changed lines hold no mutant, the last line is `mutation: no mutants in the lines changed against <BASE> on <commit>`.

With PATHs, the mutants' lines come from every part, in one file and line order. After them stands one line for each changed production file that no part covers (a Go file, not a test, that the tree changes against its merge base with BASE; a deleted one has no line to mutate and is not listed), in path order, and the last line sums the parts and counts those files, also when there are none (`1 changed file in no part` for one, `<n> changed files in no part` otherwise). Files in no part never fail the run: the exit code follows the mutants alone.

```text
alive      internal/cli/cursor.go:87:14 conditionals boundary
no part    internal/state/hook.go
no part    internal/state/read.go
mutation: 23 killed, 1 alive, 0 timed out, 4 not covered, 2 changed files in no part against origin/dev on <commit>
```

When no part holds a mutant, the last line is `mutation: no mutants in the lines changed, <n> changed files in no part against <BASE> on <commit>`. It exits 0 when no mutant is alive or timed out, 1 when one is, and 2 on an error of its own, with no mutant's line and no last line: no BASE, a BASE git does not know (`git fetch origin dev` first), a PATH that does not exist, lies outside the repository or names no Go file of it, a file two PATHs cover, unit tests that fail before any mutation, unit tests that failed with a mutant and fail without it too (`the unit tests that failed with a mutant fail without it too`, with how many of the mutants' runs left a record and one such run's output, or that no record could be written: the machine failed them, a full disk for one, or a test that fails now and then, not the mutant, so no mutant is judged; #234), the tool failing, or an interruption. In parts, an error of a part starts with `the part <PATH>: `.

**Cost.** The tool runs the unit tests once with coverage, then once per mutant, in parallel on every core; a mutant's run rebuilds the packages it touches and runs the unit tests the test cache cannot answer. On 10 cores the changes of pull request #148 (292 added lines of Go, 66 mutants) took 35 s in all, those of #151 (7 mutants) 20 s. A mutant times out when its run takes ten times as long as that first run, which builds the whole module from an empty cache. A killed mutant's run also runs what failed once more without the mutant, inside the mutant's time limit: one `go test -count=1` per package that failed, one after another, each linking that package's test binary; the first in a run or a part also builds the module once more without coverage, in the run's cache, and when the output names no package the whole unit suite runs. On pull request #213's change (54 kills, nearly all in one package) that took a few seconds in all; a mutant in a package that many packages use costs more. On that change (94 mutants, 62 of them run) load did not change the verdict: runs with every core kept busy by a busy loop each took 1.2 times as long as runs on an idle machine and printed the same lines and counts (#234). In parts, every part that has something to run makes that first run again with an empty cache of its own: a run in parts takes longer than one run over the same change, and needs at once only the disk of its largest part.

**Known limits of the tool.** A mutant that does not compile is counted as killed (the tool's issue 321); for these five kinds it is rare. A machine that fails a mutant's run and passes again by the time what failed runs once more, a moment later, is not seen, nor is one whose run again is not over two seconds before the mutant's time limit: that mutant counts as killed. A unit test that passes only after another test of its package has run fails in the run again too, which runs it by name (`-run`) without that other test, and so can end a healthy run with exit 2. A mutant whose run comes near the time limit, ten times the first run (one in a package that most tests depend on, while every worker runs the whole suite), can still turn `timed out` under heavier load than #234 measured, or under pressure on the disk or the memory: the coefficient was not changed. The tool cannot tell an equivalent mutant from a weak test: that judgement is the reason in `## QA`, and in a supervised release the integration reviewer tries the killing test for each such reason (`docs/agents/integration-review.md`, *Reasons of equivalence*).

## CI

A pull request into `dev` or into a release branch (`release-vX.Y.Z`, `docs/agents/issue-tracker.md`, *Working a release*) gets a run, unlike the template's *Merging* says: `.github/workflows/pull-request-tests.yml` runs `scripts/check.sh` on macOS and Ubuntu, for every change but one of only the paths its header lists as skipped. For a ticket of a supervised release it is the only run of the full build in CI before its squash, since the release branch gets no `Tests` run. Every push to `dev` runs it once more on Ubuntu (`.github/workflows/tests.yml`), for every change but one of only the paths its `paths-ignore` lists. A pull request into any other branch gets no run. A PR with a red CI job is not merged.

## Thresholds

`tools/testgate` holds the minimum unit share of unit + integration tests and the minimum statement coverage of `internal/`. Unlike the template's `docs/agents/testing.md` and `docs/agents/implementer.md` say, a pull request moves them, by these rules. Both thresholds only go up. The unit share's minimum follows the figure: a PR that raises the share raises the minimum in the same PR. The coverage minimum stays 0.5 points under CI's figure, rounded down to a tenth, so a PR that changes nothing about tests cannot fall under it: a PR that lifts the figure more than 0.5 points above the minimum raises the minimum to the figure less 0.5 (#42). Never lower one to get a PR through.

## Platform code

Both platforms behave the same, and the code that tells them apart lives in `internal/platform` only (`docs/hq/agents.md`, *Rules*; design §3.10). `testgate platform` fails on a Go file, not a test, that names a program or variable of one platform outside it: `cmd.exe`, `powershell.exe`, `wsl.exe`, `wslpath`, `sbx.exe`, `WSL_DISTRO_NAME` or `osascript` in a string (ignoring case), or `runtime.GOOS` in code (ask `platform.OS` instead). It prints the file, the line and the name. Comments are not checked, and no other word is looked for: a message to the user about the system tray passes. The list and its exemptions (`internal/platform`, the stubs in `internal/testutil`, the gate itself), each with its reason, are in `tools/testgate/platform.go`; a new exemption needs a reason there and a line in the PR.

## Time bounds

A test that fails when real time runs past a tight bound fails at random on a busy runner (two did in release v0.14.0, #219). `testgate timebound` reads every `*_test.go` of the repository, whatever its build tag and under `tools/` too (leaving out hidden directories and `testdata`), and fails on an upper bound under one second on real elapsed time: a comparison that holds when `time.Since(x)` or `time.Now().Sub(x)` is greater than (`>`, `>=`, or `<` and `<=` written the other way round) a constant duration under 1 s, the elapsed time compared directly or through a variable it was assigned to (`d := time.Since(start); d > 300*time.Millisecond`) and never given anything else. The constant may be a literal, arithmetic on the `time` package's units, a conversion to `time.Duration` or a constant of the package, declared in any of its files. It does not follow a helper function that returns the elapsed time, nor the elapsed time turned into a number (`.Milliseconds()`, `.Seconds()`). It prints the file, the line and the bound per finding (#232). Not findings: a bound of 1 s or more, a lower bound, time from anything but the real clock (a fake clock's `now.Sub`), timers and timeouts (`time.After`, a context's deadline). It has no way to exempt a line: a test that has to show something happens at once shows it by the order of events (the program waits for a file the test creates only afterwards), and one that needs a bound on real time takes 1 s or more.

## Private details

The repository is public. Names of private organisations and repositories, agent and repository names taken from them, a local user's paths, host names and Claude session ids stay out of the code, the docs, the fixtures and the QA evidence: use a placeholder (`<org>`, `~/work/app`, `agent-17`, `/w/app`), and when a capture carries such a detail, edit it and say so in its fixture README (#127). `testgate private` fails on a line that matches one of the patterns in the list (one regular expression per line, matched ignoring case, `#` comments); it checks the tracked files, or the PATHs given. The list itself is not in the repository: the gate reads it from `HQ_PRIVATE_PATTERNS` or, without the variable, from the file `.git/info/hq-private-patterns` of the repository it runs in (in the common git directory, `git rev-parse --git-common-dir`, so every worktree shares it; never tracked, never pushed). CI takes it from the repository secret `HQ_PRIVATE_PATTERNS` (`.github/workflows/private.yml`, on every pull request, every push to `dev` and once a day; each run also checks the tip of `qa-artifacts`), and a local run without a list passes with a notice. Ask the owner for the list to run it locally; the gate prints the file, the line and the pattern's number (counting patterns, not comment or blank lines), never the text, since CI logs are public. It reads text only: look at images yourself.

That workflow sees a commit only once it is public, and a commit that a later one cleans up stays reachable by its sha. So a push is checked before it leaves the machine (#185): the pre-push hook `scripts/git-hooks/pre-push` (enabled once per clone, `docs/hq/agents.md`, *Pushing*) runs `testgate prepush`, which checks what the push sends: the name of every branch or tag it updates, an annotated tag's message, and the message, the added lines and the added paths of every commit the remote does not have yet (when its tip there is unknown locally, of every commit no remote-tracking branch has), a merge as its change to the first parent. The names and addresses of author, committer and tagger are not checked: they are the pusher's own. It prints `private: N patterns, C commits, M matching lines` and, on a match, each commit, file and line with the pattern's number, and refuses the push. Without a list it refuses the push too, saying where the list goes: forgetting the list must not mean pushing unchecked. `git push --no-verify` skips the hook, for a push that has to go out anyway; the workflow stays the last line.

A pull request's body, an issue or a comment is public the moment it is posted, and the workflow never sees it. So it is checked before it is posted (#231): `.claude/settings.json` runs Claude Code's PreToolUse hook `scripts/claude-hooks/prepost` before every Bash command of a session, and for a command that may post through `gh` (also with `-R` before the subcommand: `gh pr create`, `edit`, `comment`, `review`, `merge` and `close`, `gh issue create`, `edit`, `comment` and `close`, `gh release create` and `edit`, and `gh api` but with `-X GET`) it runs `testgate prepost`. The gate reads the command without running it and checks, against the same list, the text it posts: the values of `--title`, `--body`, `--subject`, `--comment` and `--notes` and of `gh api`'s `-f` and `-F`, a heredoc or here-string it reads (Claude Code's `--body "$(cat <<'EOF' ... EOF)"` included, and standard input by any of its names, `-` or `/dev/stdin`) and the files it reads (`--body-file`, `--notes-file`, `-F body=@<file>`, `--input`, `< <file>`), also inside `$(...)`, a shell's `-c` or heredoc and `eval`. It refuses the command on a match, and also when it cannot see the text: a value with `$VAR`, `$(...)` or a backtick, standard input from a pipe, a file that is not a regular file, does not exist yet or that the same command writes (with a redirection, `tee`, `cp`, `mv` or `sed -i`, for example); the agent then writes the file in one command and posts it in the next. Without a list, or without Go, such a command is refused too, as a push is. A refused command does not run, and the agent sees `prepost: N patterns, T texts, M matching lines` and each finding with the pattern's number, never the text. There is no counterpart of `--no-verify`: a text that has to go out anyway is posted by the operator outside Claude Code. The gate stops an accident, not someone set on getting around it: a `gh` command hidden in a variable or a script file is not seen. Claude Code reads its hooks when a session starts, so a session started before the hook came in runs without it.
