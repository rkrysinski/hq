# hq - one console for many Claude Code agents

This document is the requirements specification for the whole product, to be implemented from scratch in the milestones of section 12. It describes WHAT hq does, as observable behaviour, and the givens it must live with. It deliberately says nothing about HOW (languages, libraries, file formats, internal mechanics); that is the implementer's design. Design reference for the look: `docs/requirements/look-and-feel.pen`, one frame per scenario (section 13).

## 1. Goal

The user runs several Claude Code agents in parallel, in different repositories, and today has no consolidated view of them. hq gives one terminal window that shows every agent regardless of project, tells at a glance which ones need the user, lets the user enter any agent's session with one action, and start, stop and inspect agents from the same place or from any shell.

## 2. Givens (the platform hq is built for)

These are facts about the environment, not design choices. hq is designed with them, not against them.

- Each agent is a Claude Code session running inside a Docker Sandboxes (`sbx`) microVM. One sandbox per repository and setup, shared by all agents of that repository on that setup (ADR 0015); without setups, that is one sandbox per repository, shared by all its agents.
- From inside the sandbox nothing on the host is reachable: no host binaries, no host sockets, no host home directory. The only channel out is the repository directory mounted into the sandbox.
- Agent sessions live in tmux. On macOS the user works in iTerm2; on Windows the team works in Windows Terminal with WSL (Ubuntu). In both, hq's dashboard is plain tmux inside the terminal. Both must be supported with identical behaviour.
- Claude Code creates git worktrees and branches itself. hq never creates or manages worktrees, branches or pull requests.
- Claude Code can run user-provided hooks on its lifecycle events (prompt submitted, turn finished, waiting for input, session ended); this is how an agent's state can be observed from outside.
- Both terminals can show a desktop notification triggered by the terminal output stream.

## 3. Concepts

- **Agent**: one Claude Code session started through hq, identified by a short **name** (typically the issue number or a slug, e.g. `42`, `agent-17`). A name is taken while its agent exists, running or `ended`, until the agent is killed. A **lost agent** is one whose place in tmux went with the tmux server (a host restart) while hq keeps what it needs to bring it back (`hq restore`); it too holds its name until it is restored or killed.
- **Repo**: the repository the agent works in. **Worktree/branch**: where the agent actually works; the branch is the primary identifier in status output.
- **State**: `starting`, `working`, `question`, `needs input`, `done`, `ended`, `outdated` (definitions in 5).
- **Attention state**: `question` or `needs input` - the agent is waiting for the user.
- **Generation**: the number a release of hq carries for the form of what agents report and of how hq keeps it; it changes exactly when one of the two changes. An agent has the generation of the hq that last launched it. An **outdated agent** is one whose generation is not the running hq's: hq cannot read its state, lists it as `outdated` (5) and can only open or kill it.
- **Event** and **journal**: an event is one thing hq learned about an agent, what it was, when, and its source (the agent's hook, its screen, tmux, sbx, or hq itself), with a number from one count for the whole host, never used twice; an event hq recorded but did not act on (another hq process recorded the same first, or a later report overtook it) is set aside. An agent's journal is its events in the order hq learned them, kept on the host, out of the sandbox's reach, for as long as the agent exists; its state is worked out from its journal alone, and `hq explain` shows the events it rests on (4.1). An agent's **state number** is the number of the event at which its state, or the dialog it is at, last changed (an event that leaves both as they were moves it not), and its **completion number** the number of the event that ended its last completed turn: one whose end its hook reported as `done` or `question`, a supervised turn and a turn Claude started itself included, or the turn Claude owed after such an end, kept `working` for background work, that it did not take (the screen's event that decides so); not a stop blocked to deliver a message, a session that just started, a resumed or restarted conversation, or a turn the user ended at the agent. An agent with no event behind its state (an `outdated` agent, one `starting` before its journal holds an event, one `ended` whose journal cannot be read) has neither. A **cursor** is the opaque text hq gives in `next_since` for a number of that count such that the look that gave it saw every change numbered up to it; passed back as given, it misses no change and repeats none (ADR 0019).
- **Dashboard**: the hq window with the agent list and the docked session.
- **Setup**: a named configuration a sandbox is created with (an image, MCP servers, a model and where it is served from). `default` is the one an agent gets when none is chosen; the user defines the others once (11).
- **Docked session**: the one agent session currently shown live and interactive below the list. **Cursor row**: the row currently selected in the list. They are the same row: the session slot follows the cursor (6.3).

## 4. Command line

All operations are available from any shell; the dashboard reflects them within a second.

### 4.1 Commands

- `hq` / `hq dash` - open the dashboard (create it if needed, otherwise return to it, with the previously docked session).
- `hq new NAME [DIR] [PROMPT] [--setup SETUP]` - start an agent for the repository in DIR with an optional first prompt (at most about 16 KiB; a longer one is refused, saying by how much). The second argument is DIR when it is an existing directory, otherwise it is the PROMPT (so `hq new 42 "work on issue #42"` works from inside the repo). DIR defaults to the current directory and must be a git repository. The agent runs in the repository's sandbox of SETUP (`default` without `--setup`, exactly as without setups): reused if it exists, created otherwise, with that setup's settings; another setup's sandbox, and every agent in it, is left as it is. A freshly created sandbox may need a one-time Claude login, which the user does in the docked session. An unknown SETUP is refused before anything is created, listing the setups there are (`unknown setup 'locl'; setups: default, local`). Fails if an agent named NAME already exists (running or `ended`, until killed), or a lost agent holds the name, naming both remedies (`agent 'sup' was lost with tmux (hq restore brings it back; hq kill sup forgets it)`).
- `hq ls` - list agents, one per line, columns `NAME REPO BRANCH STATE AGE LAST`, in attention order (see 6.2). `--json` gives the same as a machine-readable list, with how many messages wait for each agent (`hq send`), its own tasks (5), what it asks (as `hq read --json` gives it) and, while it is `needs input`, the open dialog's id (`hq answer`); its state number and completion number (3), `null` where it has none; and the cursor of `hq ls --json` to pass to `hq wait --since` (see `hq wait`).
- `hq read NAME` - show that agent in full, without docking it: its name, repository, branch, worktree, state and age as `hq ls` shows them; its own tasks (5); how many messages wait for it (`hq send`); its complete last reply; while it is `needs input` or `question`, what it asks (each question with its options, the tool and command a permission is for, or an MCP server's form: the server and its message, `elicit asks: Which color should I use?`, then each field in the form's order with its title, whether it is required, its options (or its type when it has none), its default and its description, `color (Color, required): red | blue - Pick one`, each line cut as `LAST` is; for a form that sends the user to a page, the server, its message and the page's URL, the URL in full however long, since cut it would hide where it sends the user), and at a dialog the dialog's id, with the `hq answer` command for it while hq can answer it. `--json` gives the `hq ls --json` fields plus these, and the read's cursor, which is that one agent's (see `hq wait`). An unknown NAME fails as `hq go` does. A reply longer than 32 KiB comes in pages of 32 KiB, never cut short: the read says the whole reply's size and where the next page starts, and `--offset N --since SINCE` (N where a page starts, SINCE the cursor of the read that gave it) gives that page; if the agent has replied anew since that read (its latest turn end is numbered above the cursor), the page is refused, saying so, rather than mixing two replies. A moment as an older hq printed it is still taken for SINCE and ties the page to the reply by its time, as before. However long the reply, the agent's turn ends as any other (`done` or `question`, notification, `hq wait`, `hq send`) and `LAST` is one line of it. A report too large for hq to read at all (over 16 MiB) is never silent: the agent counts as `done`, and `LAST` and the reply say the report was too large, with its size. An outdated agent (5) is refused: `hq: 42 was started by an older hq: kill it and start it again`, exit code `1`.
- `hq wait [NAME...] [--since SINCE] [--timeout DURATION] [--json]` - wait until one of the named agents (every agent when none is named) changes into `done`, `question`, `needs input` or `ended` after SINCE, then return its row as `hq ls` shows it, with the row of every other that does so by the look after it, so agents that finish together come back together; while agents only work, it keeps waiting. It returns within a second of the change (an agent whose session was cut off, as when its sandbox stopped, within 2 s as in 10). Without SINCE it starts from its first look, so an agent already in such a state then is not returned. The output carries a cursor (3) to pass as the next call's `--since`: a change that happened between two calls is returned by the next call, and none is returned twice, however many hq processes look at once and whatever the clocks do (the host's after the laptop sleeps); a change overtaken by a later one between two looks is not returned. SINCE is such a cursor, which is exact; or a moment (RFC 3339, as an older hq printed the field, so a supervisor started before the upgrade keeps working) or a duration back from now (`10m`), both compared with the time of the change and so approximate; the result always carries a cursor, so the calls that follow are exact. A cursor hq did not give (above every number hq has given, as after a lost state directory) is refused, saying to take a new one from `hq ls --json`. A new dialog while an agent still needs input is a change; a report that changes neither its state nor its dialog is not. `hq ls --json` carries its cursor in the same field: a supervisor watching passes the cursor of its most recent `hq wait` or `hq ls --json` as `--since`, so a change after that result is returned even when it happened before `hq wait` was called (after `hq send`, the agent's reply, however quickly it came). The cursor of a `hq wait` stands for the agents it waited on. `hq read --json`, `hq send --json` and `hq answer --json` carry a cursor in the same field that is that one agent's: `hq wait NAME --since` from it returns that agent's next change (after `hq send`, its reply; when the message follows as a prompt of its own behind an earlier one (5.1), the end of the earlier prompt's turn first, then the reply), but a change of another agent before it may be lost, so a watch never takes its `--since` from them. After DURATION (default 50 s, suited to MCP clients; `0` waits with no limit) it returns "nothing yet" (an empty list with `--json`), which is not an error. A NAME that does not exist fails as `hq go` does, and one of an outdated agent is refused as `hq read` refuses it (5); waiting on every agent leaves outdated agents out. An agent killed while waited on is returned as `ended`, as is one whose journal can no longer be read once its pane is dead, both with no numbers. It agrees with `hq ls` and the dashboard, however many hq processes look at once, and leaves nothing running when it returns or is interrupted (Ctrl-C).
- `hq go NAME` - dock that agent's session and bring the dashboard to front, opening the dashboard if it is not open. Called with no terminal (as by the supervisor) and no dashboard open anywhere, it docks the agent and says to run `hq` in a terminal to see it.
- `hq code NAME` - open the editor (VS Code) on the agent's worktree, so the editor shows the agent's branch. Before the worktree is known, opens the repository; an outdated agent (5) is refused as by `hq read`. Works on macOS and from WSL. The agent keeps running; editor and agent see the same files.
- `hq send NAME TEXT [--now] [--wait [--timeout DURATION]] [--json]` - leave a message for that agent (TEXT one argument, at most 8 KiB), delivered when the agent is ready, never pulling it away from its work (5.1); `--now` asks for it within the running turn. Prints how the message goes (`queued: 42 is working, delivered when it stops`, `delivered: typed into 42 as its next prompt`); for a message that starts with a slash command and that it leaves to the agent's hooks the line adds that the command then arrives as text and does not run (5.1); `--json` gives it with the agent's cursor from before the message was left, for `hq wait NAME --since`, so the agent's reply always counts as after it. Refused for an `ended` agent, naming the remedy (relaunching it), and for an outdated agent (5). With `--wait` the message is left, delivered and refused as without, the line is printed as without, and the call then waits until the turn that took the message ends and prints that agent's row and cursor as `hq wait` does, or returns at once with a line saying why that turn will not come by itself; it fails as stalled, exit code `4`, when the agent sits at its prompt and does not take the message (5.1, *Waiting for the answer*). `--timeout` is `hq wait`'s (default 50 s, `0` waits with no limit, `nothing yet` at the end, exit code `0`), counted from the start of the call, the delivery included; without `--wait` it is a usage error. `--json` then gives the line (`delivery`), how the call ended (`outcome`: `turn_ended`, `not_taken` with where the message is in `message`, `waiting`, `kept` or `gone`, `no_turn`, `timeout`), the agent's row as `hq wait --json` gives it (`agents`, empty at the timeout) and a cursor taken after what the call returned: still that one agent's, so `hq wait NAME --since` from it returns that agent's next change and never the one returned, and a watch never takes its `--since` from it. Without `--wait`, `hq send` prints and does what it did before.
- `hq answer NAME --dialog ID ANSWER... [--json]`, `hq answer NAME --dialog ID --cancel [--json]` - answer that agent's question dialog (AskUserQuestion) on the user's word, with the same effect as picking the answer at the agent, while the dialog stays open and answerable there the whole time; or cancel it as Esc does, which ends the turn (`done`, `User declined to answer questions`). ID is the open dialog's id, six hex characters, as `hq read` shows it: an answer can never land on a dialog that opened after the user read. One ANSWER per question, in the dialog's order: an option's number as `hq read` lists it, numbers joined with commas where the question allows several, or any other text as an answer in the user's own words. The whole answer is checked against the dialog before anything reaches the agent and refused whole on any fault (a wrong count, an unknown option, several options where one is allowed, empty text). It returns once the agent has left the dialog and prints its state then (`answered: 42 is working`, `cancelled: 42 is done`); `--json` gives the state with the agent's cursor from before the answer was left, for `hq wait NAME --since`. Refused, with the reason and nothing reaching the agent: a dialog no longer open (answered at the agent first), with the agent's state; a missing or wrong ID, naming the open dialog's id; a permission prompt and an MCP elicitation, which are answered at the agent; an agent at no dialog, or in `question` (answered with `hq send`); an `ended` agent; an outdated agent (5); and an agent whose sandbox template answers AskUserQuestion by itself, which would keep the agent from taking any answer from hq, naming the template's hook and the remedy (answer it at the agent; recreate the sandbox from a template whose hooks leave AskUserQuestion alone). Fails, naming the agent's state: when the agent does not take the answer within 3 s; when it has taken it but not left the dialog within 5 s, naming the likely cause, another permission hook that answered AskUserQuestion first (the repository's settings, a plugin, or the template where hq could not check it); and when what the agent reports it got differs from what was sent, saying what it got. hq types nothing into a question dialog. The `needs input` notification, whose turn it is (5) and a message waiting for the dialog to close (5.1) are as when the dialog is answered at the agent. A dialog Claude Code itself shows in place of its prompt box (5: when a session starts, or after a turn, such as `Change effort level?` after `/effort` or `Switch model?` after `/model NAME`) is answered the same way, with one ANSWER, an option's number, with the same effect as picking it at the agent, and only while the agent's screen shows the dialog the user read: nothing is picked on another. It returns once the agent has left the dialog, as it was before it (`answered: 42 is done`). Refused for it, nothing picked: text, several options and `--cancel`; and a list that scrolls past what the screen shows (the model picker of `/model` with no name; `/model NAME` asks `Switch model?` instead), which is answered at the agent, as is the question whether to trust the folder, asked before the session starts (the agent is `starting` then). Fails, naming the agent's state, when the dialog does not come to the option within 2 s (nothing is picked) or the agent has not left it within 5 s of the pick.
- `hq kill NAME` - end that agent's Claude session after confirmation (`-y` skips it). The sandbox stays. A lost agent is killed the same way: hq forgets it, ending its session where it still runs in its sandbox, and its name is free.
- `hq stop` - end all agents after confirmation (`-y` skips it). Sandboxes stay.
- `hq killed [NAME]` - show the trace of kills: every agent hq killed, by `hq kill`, `hq stop`, the dashboard's Kill dialog or the supervisor's `kill`, one line each, oldest first, with when, the agent's repository and sandbox, and who asked for it: `2026-11-03 14:02:11  coolify in app (sandbox claude-app), by hq kill` (or `by hq stop`, `by the dashboard`, `by MCP: client sbx (claude-code 2.1.30), agent sup`). For the supervisor's `kill`, the client is the one `hq mcp` serves (`claude-desktop`, `claude-code`, `sbx`) with the name and version the client gives itself, and the calling agent when hq knows it (a client running inside an agent's own session); an agent calling through `sbx`'s gateway is not known. With NAME, only the kills of agents of that name. With no kill to show it says `no kills in the trace` (`no kill of 'NAME' in the trace`), exit `0`. The trace is the user's own, kept where no agent can write it, and survives tmux and host restarts; its oldest kills go once it holds a few hundred. A kill the trace cannot take still ends every agent, then fails saying so (`killed a, but could not add it to the trace of kills (REASON)`); an agent whose window was removed is in the trace even when removing the next one fails. It is how an agent gone from `hq ls` is explained: a kill, or not (#147).
- `hq explain NAME [--all] [--json]` - show why the agent's state is what it is: the events of its journal (3) its present state and its dialog verdict rest on, oldest first, as `hq ls` shows them now; each with its number, its time, its source (`hook`, `screen`, `tmux`, `sbx`, `hq`), what it was and the state after it. It says whether the agent is at a dialog, whose it is (its hooks', a subagent's, Claude's own) and which events opened and closed it, or that it never was at one. For an agent `working` on background work these are the prompt, the end of the tool that started the task and the turn end that left it working. `--all` gives every event of the journal since the agent started, an event hq set aside marked with the reason (another hq process appended it first, or a later report overtook it). `--json` gives the same as data: the state, its age, the events it and the dialog verdict rest on, and the events, each with its facts. It shows no text of the conversation, in any form: no prompt, no reply, nothing a dialog asks, no text of a message, nor the session id, branch or worktree; where a rule depends on text it shows the fact (`turn end, the reply ends with ?`), and no option adds the text (`hq read` shows the reply). So its output can go into a public issue as it is. It explains an agent that has `ended` and is still listed and a lost agent before `hq restore`, since the journal is kept on the host; it delivers no message. An unknown NAME fails as `hq read` does (`hq: no agent 'x' (see hq ls)`, exit code `2`); an outdated agent (5), a lost one of another generation included, is refused as `hq read` refuses it, exit code `1`. A command only: the supervisor has no tool for it and the dashboard no key.
- `hq sandbox rm REPO` / `hq sandbox restart REPO` - remove or restart a repository's sandbox after confirmation (`-y` skips it; restart is the remedy after laptop sleep, S9). REPO means the repository's default sandbox; with `--setup SETUP`, that setup's sandbox of the repository; with `--all-setups`, every sandbox of the repository, which the one confirmation lists by name. REPO may also be a sandbox's own name as `sbx ls` shows it, which means that one sandbox, whatever its setup. `--setup` and `--all-setups` together, or either with a sandbox's name, is a usage error; a setup the repository has no sandbox of is not found. `rm` refuses while agents in the sandboxes it would remove are running; when one of several cannot be removed, `rm` still removes the others and says which it removed and which not, with `sbx`'s error; `restart` ends every session in them and relaunches each of their agents, continuing its conversation; it is refused while they hold an outdated agent (5), naming it and the remedy (kill it and start it again), and stops nothing; after a host restart, when tmux lists none of them, it relaunches the same agents `hq restore` would for those sandboxes (each lost agent of theirs, or the reason it cannot), and its confirmation names them. A sandbox hq was loaded into with `hq mcp load` gets it again once restarted, before its agents are relaunched (`restarted the sandbox claude-app; loaded hq into it again; relaunched sup`); when that fails, the agents are relaunched all the same and the command fails naming the sandbox, `sbx`'s error and `hq mcp load` as the remedy. A sandbox `rm` removes is no longer one hq was loaded into, so a new sandbox of its name does not get hq; when that cannot be recorded, `rm` fails after removing it, naming `hq mcp unload` as the remedy.
- `hq restore [REPO]` - bring back the lost agents (3) of the repository (REPO as for `hq sandbox`: a directory in it or its name as `hq ls` shows it), or, without REPO, of every repository hq knows (each repository with a sandbox): each agent hq started or relaunched on this tmux server whose place in tmux is gone, after a host restart or any loss of the tmux server. Each is relaunched under its name, in its repository, worktree and sandbox (setup included), continuing its conversation, as `hq sandbox restart` relaunches an agent (5: `done` once the resumed session has started, messages waiting for it still delivered), and shows in `hq ls` and the dashboard as any other agent. A session of it still running in its sandbox (the tmux server alone went) is ended first, so the conversation is never continued twice. One line per agent: `restored sup in app (sandbox claude-app)`, or `not restored 42 in app: REASON (hq kill 42 forgets it)` for an agent it cannot bring back, which stays lost: its worktree is gone, its sandbox is gone, it has no conversation to continue (it never had a prompt), its journal is gone (`its journal is gone`), or it was started by an hq of another generation (its record says none, or another: `it was started by an older hq`). Running it when nothing is lost changes nothing and says `nothing to restore`. An agent that runs, or has ended and is still listed, is never touched, nor one of another tmux server (another hq of the same user on its own tmux server, as in development). Not being able to restore an agent is no error (exit `0`); REPO that is no repository hq knows is not found. For each sandbox of the restored agents that `hq mcp load` loaded hq into, it adds `hq was loaded into the sandbox claude-app; if it restarted, hq mcp load claude-app loads it again`.
- `hq mcp [claude-desktop|claude-code|sbx]` - serve `new`, `list`, `read`, `wait`, `send`, `answer`, `go` and `kill` as tools to an MCP client over its standard input and output (Phase 2 below); the client, Claude Desktop (the default), Claude Code, or `sbx`'s MCP gateway for a Claude Code inside a sandbox, starts it and ends it, the user never types it. Each tool gives what the command of the same name gives, with the same errors; `list` is `hq ls`, `wait` requires its `since` (the cursor of the supervisor's most recent `wait` or `list`, passed back as given, see `hq wait`), and `wait`'s timeout is at most 50 s for Claude Desktop and for `sbx`'s gateway, which give up on a tool call after 60 s, and at most an hour for Claude Code; `new` takes an optional `setup`, as `--setup`, with the same meaning and errors; `list`, `read` and `wait` carry each agent's `setup`, as `hq ls --json`, `hq read --json` and `hq wait --json` do (`default`, or the setup its sandbox was created for; nothing new on screen, where the docked session's title already names the sandbox); `kill` takes the user's confirmation with the call (`confirmed`) in place of `-y`: without it nothing ends and the supervisor is told to ask the user. `send` takes `wait` and `timeout` as `--wait` and `--timeout`, its timeout at most `wait`'s for the client and its `next_since` at that limit to go on with a `wait` that names that agent alone (whose `next_since` is that agent's too: the supervisor's watch keeps its own), and a stalled message is the tool's error. `answer` takes the dialog's id, one answer per question (option numbers, or text) or a cancel, and the user's word the same way (`confirmed`): without it nothing is answered and the supervisor is told to ask the user, naming the agent and its question. When the client runs inside an agent's own session (a Claude Code of an agent in a sandbox, with hq loaded there), `kill`, `answer` and `send` naming that agent are refused, whatever `confirmed` says: nothing ends, nothing is answered or sent, and the tool's error names the agent and the tool, `hq: kill refuses sup, the calling agent: an agent does not end itself; the user ends it (hq kill sup)`, `hq: answer refuses sup, the calling agent: an agent does not answer its own dialog`, `hq: send refuses sup, the calling agent: an agent does not send to itself`; the same calls naming any other agent, and `new`, `list`, `read`, `wait` and `go` naming that one, behave as ever. A client hq cannot place in an agent's session (Claude Desktop, Claude Code on the user's machine) is refused nothing. An outdated agent (5) is refused as the command of the same name refuses it. `hq stop`, `hq killed`, `hq explain`, `hq sandbox` and `hq restore` are not offered.
- `hq mcp install [claude-desktop|claude-code|sbx]` - add hq as an MCP server to Claude Desktop's configuration (the default) or to Claude Code's user configuration (the servers `claude mcp add --scope user` adds, there for every project), or register it with `sbx` under the name `hq` (the servers `sbx mcp add` registers), for a Claude Code inside a sandbox, on macOS and on Windows (where Claude Desktop starts hq in WSL, and Claude Code is set up both in WSL beside hq and on Windows, wherever it has run). Running it again changes nothing; every other setting and server in the configuration stays as it was, and a copy of the file as it was is kept next to it. When the configuration cannot be found or edited safely, or Claude Code was never run there, it changes nothing and prints the entry to add by hand (for Claude Code, the `claude` command that adds it). A save Claude Code makes to its configuration while hq edits it is never lost. The client is restarted by the user to load it. With `sbx`, the registration records hq's path and the user's `PATH` as the Claude Desktop entry does; running it again changes nothing, and with hq moved or `PATH` changed it replaces the registration, leaving one; a `PATH` or hq path holding a comma, which `sbx mcp add` cannot pass, is refused with the reason, registering nothing; the output names the command that loads hq into a sandbox (`hq mcp load`).
- `hq mcp load REPO [--setup SETUP|--all-setups]` - load hq, registered with `sbx` by `hq mcp install sbx`, into the repository's sandbox (REPO and the flags as for `hq sandbox`), so the Claude Code of every agent in that sandbox has hq's tools, and remember it for `hq sandbox restart`, which loads it again (`sbx` loses it when it restarts the sandbox). Prints `loaded hq into the sandbox claude-app: every agent in it sees hq's tools`. The sandbox must be running (`sbx` loads into a running sandbox only). Refused when hq is not registered with `sbx`, naming `hq mcp install sbx`; a repository without such a sandbox is not found; `sbx`'s error when it cannot load it, remembering nothing; of several sandboxes (`--all-setups`), those it loaded hq into are named and remembered, and the others named with `sbx`'s error.
- `hq mcp unload REPO [--setup SETUP|--all-setups]` - forget that hq was loaded into the repository's sandbox, so `hq sandbox restart` no longer loads it again. `sbx` cannot unload a server from a sandbox, and removing hq's registration would take it from every sandbox, so the tools stay until the sandbox restarts, which it says: `hq stays loaded into the sandbox claude-app until it restarts (sbx cannot unload it): hq sandbox restart claude-app takes its tools away`. A sandbox `hq mcp load` did not load hq into is named, with nothing to unload. A sandbox it loaded hq into that is gone (removed with `sbx` itself) is forgotten by its name, `hq mcp unload claude-app`, so a new sandbox of that name does not get hq.
- `hq update` - replace hq with the latest released version, printing the version before and after. Needs no GitHub login. Every release carries its generation (3), published with it and checked like the binary; a release that carries none (any from before generations) counts as another generation. An update to a release of hq's own generation goes through with agents running, which carry on untouched. An update to a release of another generation is refused while any agent hq knows exists: running, `ended` and still listed, or lost (3), and one hq started on another tmux server, which its repository's record of it names (`x (on tmux server qa)`). It then replaces nothing and exits with code `1`, with one line that names the release, the reason, the remedy and every agent in the way with its state: `hq: not updated to v0.15.0: it is of another generation (4, this hq 3) and agents exist; end them first with hq stop or hq kill NAME: 42 (working), old (ended), x (lost)`. When hq cannot tell whether agents exist, because `sbx` does not answer, is too old or is missing (so the lost agents are unknown), or tmux fails, it is refused the same way, exit code `1`, with that reason: `hq: not updated to v0.15.0: it is of another generation (4, this hq 3) and hq cannot tell whether agents exist: sbx 0.47.0 is too old, 0.48.0 or newer needed; update Docker Sandboxes`. No option updates anyway. A development build compares generations the same way. A dashboard and an `hq mcp` still running from the hq replaced step aside after an update to another generation (6.1, Phase 2), and go on as before after one of hq's own. After an update to another generation has gone through, while sandboxes are on the list of those hq was loaded into (`hq mcp load`), one more line names them and the remedy, since hq's tools in them fail until each restarts: `hq's tools in the sandboxes claude-app, claude-lib fail until each restarts: hq sandbox restart claude-app, hq sandbox restart claude-lib`. With no sandbox on that list, or after an update within the generation, nothing more is printed.
- `hq help`, `hq --version` (also says when a newer version is released).

### 4.2 Conventions

- Names: letters, digits, `-`, `_`, `.`, at least one letter or digit, at most 32 characters (`42`, `agent-17`, `rel-1.10.5-213`); unique among existing agents, running or `ended`. Reusable once the previous agent with that name is gone (killed). A name over the limit is refused with an error naming the limit.
- Exit codes: `0` success, `1` usage or refused (duplicate name, `sandbox rm` with running agents), `2` not found (agent, repo, sandbox), `3` environment (tmux or sbx unavailable), `4` stalled (`hq send --wait`: the agent did not take the message, 5.1). Declining a confirmation is not an error: nothing changes and the exit code is `0`; with no terminal to confirm on and no `-y`, the command is refused (`1`).
- Errors are one line on stderr, prefixed `hq:`, and name the remedy where there is one (`hq: no agent 'x' (see hq ls)`).
- Every command works the same from inside the dashboard's own terminal and from any other shell.
- When a newer version of hq is released, a command the user runs in a terminal ends, after its own output, with one line on stderr: `hq v0.4.0 is available - run hq update`. Not with `--json`, not when stderr is not a terminal, not in `hq mcp` (its output is for the MCP client), not in `hq update` or `hq --version` (which says so in its own output), and not in the dashboard, whose header shows the hint beside the running version (6.1). A development build never says it.
- hq looks for new releases at most once a day and in the background: no command waits for the answer, and none is slowed down, fails or prints anything because GitHub is slow or unreachable; what a check finds shows from the next command on.

## 5. Agent state

Observable definitions; the mechanism is the implementer's choice, within the givens.

- `starting` - agent launched, its session not started yet (Claude still starting in the sandbox); an agent launched with a first prompt stays `starting` until it reports taking that prompt, however late. A first prompt that is a command of Claude Code's own that starts no turn, which Claude Code reports nowhere (such as `/model NAME`, or `/effort` and the model picker closed with nothing picked; verified with Claude Code 2.1.329), makes it `done` once its screen shows the command taken (see `done`). Should it never report taking any other first prompt (one Claude drops at its start, a plugin's command whose hooks report nothing), it stays `starting` until it next reports anything, or until `hq kill`. A first prompt that is only late (behind a slow SessionStart hook) never makes it `done`.
- `working` - the agent is processing a prompt, or its turn has ended while subagents it started in the background still run: Claude then goes on by itself when they finish, so the agent is not finished yet (see *Background work* below).
- `question` - the agent finished a turn with a direct question to the user.
- `needs input` - the agent is waiting for a permission or an input dialog, or for a dialog Claude Code itself shows in place of its prompt box: when a session starts, before it takes any prompt (such as its question about the default permission mode), or after a turn (such as its confirmation of an effort change, or the model picker). Once such a dialog of Claude's own is answered, the agent is again as it was before it.
- `done` - the agent finished a turn without asking anything and with no background subagent still running, or the user ended its turn at the agent: interrupted it (Esc), cancelled its dialog or refused a permission. The last message then says so (`Interrupted`, `User declined to answer questions`). Also a turn an API error ended, whatever the error (an expired login, a rate limit, an overloaded or unreachable service, ...): its last message is the line Claude Code ends the turn with (`Login expired · Please run /login`), its time counts from that end, and it leaves the state with its next prompt, as from any `done`; while the error lasts, that prompt's turn ends `done` the same way. Also a session that has started and waits at its prompt for the user's first prompt: an agent started without a PROMPT (last message `-`), one whose first prompt was a command of Claude Code's own that starts no turn (last message `-`, no notification, and no completed turn: `completion_seq` stays as it was), a session resumed or started over (`/clear`), which keep their last message.
- `ended` - the session is gone (exited, crashed, sandbox stopped).
- `outdated` - the agent is an outdated agent (3): it was last launched by an hq of another generation, so this hq cannot read its state. It stays `outdated` whatever its session does, its pane dead included, until it is killed: no age, branch `-`, and the last message `started by an older hq: kill it and start it again` (`started by a newer hq: ...` after a downgrade). It can be opened (`hq go`, docking in the dashboard, typing in it) and killed (`hq kill`, `hq stop`, the Kill dialog), the kill removing everything of it, the files its older hook wrote included, and recording it in the trace of kills as for any agent. Every other command that names it (`hq read`, `hq send`, `hq answer`, `hq code`, `hq explain`, a `hq wait` that names it) is refused with `hq: 42 was started by an older hq: kill it and start it again`, exit code `1`; `hq sandbox restart` of a sandbox that holds one is refused (4.1); a `hq wait` on every agent leaves it out. hq raises no notification of its own for it and continues none of its conversation; its own hook may still notify as it did. A lost agent whose record has no generation, or another, is reported by `hq restore` and not relaunched, and `hq kill NAME` forgets it.

Requirements:

- A state change is visible in the dashboard within 1 second.
- Each state carries the time since it was entered (`3s`, `2m`, `1h`) and the agent's last message, one line, truncated.
- Entering `question`, `needs input` or `done` triggers exactly one desktop notification per event, whether or not that agent is docked, while the dashboard is open in a terminal (S8); the `done` and `question` of a supervised turn trigger none (*Supervised turns* below). Notifications name the kind and the branch (`Question: feat/42-...`, `Needs input: ...`, `Done: ...`). `working`, `starting` and `ended` never notify, and neither does a turn the user ended at the agent (interrupted, a dialog cancelled or a permission refused) or a session that has just started: the user is already there, or has just started it. The `done` of a turn an API error ended notifies once, as `Done: ...`, unless the turn is a supervised turn. Documented limitations: that notification comes about a minute after the end, and none comes when the agent gets a prompt within that minute, nor, it may be, while a background subagent still runs (*Background work* below).
- **Background work.** `done` means "come and look". A turn that ends by itself while subagents the agent started in the background still run leaves the agent `working`: no notification, `hq wait` does not return, the time keeps counting from the user's prompt, and the last message is that turn's. Each subagent that finishes may wake the agent for a turn of its own; every such turn that ends with subagents still running leaves it `working` (only the last message changes), and the turn that ends with none running makes it `done`, with exactly one notification. Every running background task Claude reports at the turn's end counts (subagents, workflows, and shell commands and watches its subagents started), except shell commands and watches (monitors) the agent itself started, including the artifact watch Claude arms when the agent publishes an artifact: an agent that left a dev server running would never be `done`, and neither would one that published an artifact, whose watch runs until its session ends; so an agent waiting only on a background shell command of its own is `done`, and `working` then `done` again when Claude takes a turn at the command's end, and an agent whose own watch alone runs is `done`, as is every later turn of its session that leaves only the watch running. It is plain `working` everywhere: no state of its own, no marker in the row, nothing extra in `hq ls`, `hq read` or the supervisor's tools. The agent's own tasks show, without changing its state (below). hq sets no time limit while background work runs: the agent stays `working` until its next turn ends or its session is gone. In detail:
  - A turn that ends with a direct question to the user is `question`, and notifies, even with subagents running; afterwards the state follows the latest turn end, so the closing turn may replace it with `done`.
  - A turn the user ended at the agent (interrupted, a dialog cancelled, a permission refused) is `done` without a notification, whatever still runs; when the subagents finish, the closing turn shows `working`, its time counting from when Claude took it up (from the interrupted prompt when no hq was looking during that turn), then `done` with a notification.
  - A turn an API error ended (5, `done`) is `done` as well, whatever still runs: background subagents, or a subagent's open dialog; its last message is the error line. When the subagents finish, the closing turn shows `working`, then ends as any turn does. Documented limitation: the notification of that `done` waits for Claude Code to report the agent idle, which it does not do while a subagent runs, so it may come only with the closing turn's end.
  - A session that starts, is resumed or started over (`/clear`), or relaunched by `hq sandbox restart` or `hq restore`, is `done` as always: the subagents of the session before are forgotten. One that outlives `/clear` and wakes the new session shows as it happens: `working`, then `done` with a notification.
  - Subagents that finish at almost the same moment are no exception: Claude takes a turn for each, and the agent is `done`, with its one notification, at the end of the last of those turns, although nothing runs any more at the end of the earlier ones.
  - Should Claude not take the turn it owes for finished background work, the agent is `done` a few seconds after its turn's end, with that turn's message and without a notification, so it never stays `working` with nothing running.
  - A shell command a subagent started in the background is background work while it runs. A subagent that started one and stopped is reported finished, with an interim report, and Claude wakes it again when the command ends: the agent stays `working` through that report, with its message, and is `done`, with one notification, at the end of the turn after the subagent's final report, once nothing of it runs. Nothing tells whether a subagent waits on its command or left it running (a dev server): an agent whose subagent left a server running stays `working`, with the subagent's last message, until the server ends. Chosen over a `done` while the work goes on, which would recur at every wait for CI. A watch a subagent keeps on a command or an event counts the same.
  - **Own tasks.** The background shell commands and the watches (Monitor tool) the agent itself started that still run at the turn end its `done` or `question` comes from are its own tasks: not background work, so its state, its notification (text included) and `hq wait` are as above, but shown beside the state, since Claude takes another turn when each ends. A shell shows by its command, a watch by its description. A command or watch a subagent started is never one (it is background work), nor is the artifact watch Claude arms when the agent publishes an artifact. `hq read` lists them one per line after the state (`own task: shell  sleep 120`, on one line, cut as `LAST` is); `hq ls --json`, `hq read --json`, `hq wait --json` and the supervisor's `list`, `read` and `wait` carry them in `own_tasks`, each with its type (`shell` or `monitor`) and its command or description in full, `[]` when none; the dashboard row and `hq ls` start `LAST` with their count in Claude Code's words, dim in the row (`1 shell · Waiting for the background task...`, `2 shells · ...`, `1 shell, 1 monitor · ...`), while `last` in the JSON stays the message alone, and where the row drops `LAST` (S12) the count goes with it. They show only while the agent is `done` or `question` from that turn end: nothing is listed while it works on a new prompt, at a dialog, `ended`, after a turn the user ended at the agent (Esc), or at a session's start (new, resumed, `/clear`, relaunched), whatever still runs. Documented limitations: the list is that turn end's, refreshed by the turn Claude takes when a task ends, so a task that ended without a turn (stopped by the user) stays listed until the next turn end; and a dev server may never end.
- **MCP elicitations.** An MCP server's form (an elicitation, a question dialog of the agent's own or of a background subagent's) makes the agent `needs input` as soon as Claude Code draws it, with one notification, and its message as the last message; `hq read`, `hq ls --json` and the supervisor's tools say what it asks (4.1). The form is drawn at the agent exactly as without hq, and is answered there: hq answers no elicitation. Accepting, declining or cancelling it at the agent (Esc included) leaves the agent `working` at once, unlike cancelling another question dialog, which ends the turn (`done`, above): the MCP tool gets the answer and Claude goes on, so the turn then ends as usual (`done` or `question`, one notification). A form that sends the user to a page (a URL) is the same, and shows its message and the URL. A subagent's form reported after the agent's turn ended with that subagent running is the subagent's, as any subagent's dialog. Documented limitations: a background subagent's elicitation while the agent is still in its own turn shows as the agent's own; another hook in the user's own settings that answers an elicitation before Claude Code draws it leaves hq having notified for a form never drawn, which the end of the MCP tool closes; answering an elicitation from hq waits for Claude Code to draw the form while its hooks run ([anthropics/claude-code#103115](https://github.com/anthropics/claude-code/issues/103115)).
- **Supervised turns.** A turn whose every prompt came from the supervisor, that is through `hq mcp` (`new` with a prompt, or `send`; Phase 2), is a supervised turn. Its `done` and `question` trigger no desktop notification: they are for the supervisor, which reads the reply and answers, and tells the user. Its `needs input` (a permission prompt, a question dialog) notifies as ever: dialogs are the user's, answered at the agent or, a question dialog or a dialog of Claude Code's own, through hq on their word. Only the desktop notification differs: state, colour, attention sort, `hq ls`, `hq read`, `hq wait` and the supervisor's tools are the same, and nothing marks a supervised turn. In detail:
  - It is the turn's, by where its prompts came from, not the agent's: a turn the user prompts on an agent the supervisor started notifies, and a turn the supervisor sends to an agent the user started is a supervised turn.
  - Only `hq mcp` counts: `hq new` and `hq send` from a shell are the user's and notify. Every MCP client is the supervisor; several are not told apart.
  - Any prompt of the user's in the turn makes its end notify, once: a message of the supervisor's that reaches a turn the user started (5.1, with or without `--now`), a prompt the user types or a message they send (`hq send`) during a supervised turn, and a message of the supervisor's that goes along with a prompt the user was typing (5.1).
  - Answering, refusing or cancelling a dialog on a supervised turn, at the agent or through hq (`hq answer`, the supervisor's `answer`), does not change whose turn it is: `needs input` notified, the later `done` does not.
  - The closing turns of background work are of the turn that started the work: after a supervised turn they notify nobody, after the user's they notify as above. When work of both is owed, the end notifies. A background shell command or watch the agent itself started is no background work (above): the turn Claude takes at its end, after the turn that started it has ended, notifies, whoever sent that turn.
  - After a turn of the user's that they interrupted at the agent (Esc), the next turn the supervisor sends notifies at its end like a turn of theirs. Documented limitation.
  - It is forgotten with the session: background work that outlives `/clear`, a resume or a relaunch and wakes the new session ends `done` with a notification, as above.
  - Whether the supervisor waits for the agent (`wait`) makes no difference: a supervised turn ends without a notification even when nobody is listening. The row shows the state, and the user asks the supervisor. No setting turns this off.
- Two agents on the same branch are allowed; their states may then be indistinguishable. Documented limitation.
- Every agent started by hq reports its state with no setup: nothing is installed, configured or committed in the repository, and nothing per machine beyond installing hq.
- In the prompt box of an agent started by hq, Claude Code suggests no next prompt after a turn: nothing waits there that the user did not type.

### 5.1 Messages

A message left with `hq send` reaches the agent when it is ready, depending on its state:

- `working`: when the agent would finish its turn, it goes on with the message instead, and finishes after that. It stays `working` meanwhile; only the turn's final end notifies (once; not at all when the turn is a supervised turn and the message the supervisor's, 5). With `--now`, the message comes after the agent's next tool call, within the running turn, and the agent may change course; when no tool call comes, it goes when the agent would finish, as without. A turn an API error ends goes on with nothing: the agent is `done` (5), and the message is entered as its next prompt, as below.
- `done` or `question`, nothing typed in its prompt box: it is entered as the agent's next prompt, once the agent has taken in what it was given last: messages sent one right after the other, such as `/model NAME` then `/effort LEVEL`, are entered one after the other. With something typed there (the user writing), it waits and goes along with the next prompt sent from there.
- `working` only on background subagents (5, *Background work*): the agent sits at its prompt, so the message is entered as its next prompt at once, as for `done`, or waits for the next prompt sent from a box the user is typing in. The agent stays `working` if subagents still run when that turn ends.
- `needs input`: it waits until the dialog is closed, then goes as above. A message never answers a dialog: a question dialog is answered with `hq answer` (4.1), and the message then goes as promised. At a dialog Claude Code itself shows in place of its prompt box (when a session starts, or after a turn), the message waits for the agent's next prompt after the user has answered the dialog, and `hq send` says so.
- `starting`: it waits for the session to start, then goes as above; for an agent launched with a first prompt, it goes along with that prompt as the agent takes it; once the agent took that prompt as a command of Claude Code's own that starts no turn, it is `done` and the message goes as to any agent at its prompt; while the agent never reports taking any other first prompt, the message waits.
- `ended`: refused.

A message whose first line starts with `/` is a slash command. Entered as the agent's prompt, it runs: Claude Code runs the command with the rest of the message, its other lines included, as its arguments, whatever the message's length. Claude Code collapses a paste of more than 3 lines, or of more than 800 characters, into `[Pasted text #1 +3 lines]` and does not take a prompt that begins with one for a command (verified with Claude Code 2.1.325); hq enters such a command so that it runs all the same. Delivered by the agent's hooks instead (`working`, `needs input`, `starting`, or riding along with a prompt the user sends), a message reaches the agent as text, so a command in it does not run: wherever `hq send` leaves such a message to the hooks, its line says so (`queued: 42 is working, delivered when it stops; if its hooks deliver it, the slash command arrives as text and does not run`, `delivered: 42 took it with its hooks, as text, so the slash command did not run`). It says "if": an agent back at its prompt before the hooks deliver the message gets it entered as its prompt (below). A message that does not start with `/` is entered as one prompt as ever, which Claude Code may collapse so and gives the model whole.

A message that still waits for an agent at its prompt with nothing typed there (the user emptied the box without sending it, or Claude Code was still busy with a command entered just before) is entered as its next prompt the next time hq looks at the agents: the dashboard while it runs, `hq ls`, `hq read`, `hq wait`, and the supervisor's `list`, `read` and `wait`.

Whose turn it is afterwards (5, *Supervised turns*): a message of the supervisor's entered as the agent's next prompt starts a supervised turn, unless a message of the user's is entered with it; one that reaches a running turn, or goes along with a prompt the user sends, leaves the turn whose it was; a message of the user's makes the turn it reaches theirs.

Several messages waiting are delivered oldest first, each exactly once, and together as far as they make one prompt. A slash command among them is never joined behind another message's text, where it would be text: each command is a prompt of its own, and the messages between commands are one prompt. The first prompt is entered at once; the others are held for the agent, where its hooks do not deliver them, and each is entered as its next prompt once it is back at its prompt (the looks above), in the order sent (`hq send` prints `queued: typed an earlier message into 42 as its next prompt; this one follows as a prompt of its own once 42 is back at its prompt`). A message sent while others are held may still reach the agent through its hooks before them. Messages still waiting when the agent is killed go with it; a relaunched agent (`hq sandbox restart`, `hq restore`) still receives them. The user docked on the agent sees a message delivered when the agent would finish, or entered as its prompt, in the session.

**Waiting for the answer** (`hq send --wait`, the supervisor's `send` with `wait`). A message is taken once it has left the agent's inbox for Claude: handed over by its hooks, or entered by hq as its prompt; a message held behind an earlier prompt is not taken until hq enters it. The call waits, looking at the agents as `hq wait` does (so a message waiting at an empty box is entered by this call), and ends in one of five ways:

1. The agent stops after taking the message: it is `done`, `question`, `needs input` or `ended`, exactly as `hq wait` returns them (a turn that leaves background subagents running, at the agent's final `done`; a turn the user ended at the agent, as `done`), and the call returns its row. A change from before the message was taken is never returned: not the end of the turn the message was left in, nor of an earlier prompt's turn, nor of a turn Claude takes by itself for background work before the turn the entered message starts. Messages taken together, in one prompt or one handing over, are answered by the same turn end, for every call waiting for one of them.
2. The agent needs input (any dialog, one of Claude Code's own included) or ends before it took the message, already when the call is made or meanwhile: the call returns at once with the row and a line that says where the message is: still waiting, delivered once the dialog is closed as above (`not taken: 42 needs input before it took the message, which still waits for it`); kept for a relaunch; gone with a killed agent.
3. A slash command hq entered has left the prompt box and started no turn within 5 s (a command of Claude Code's own, such as `/model NAME` before the first turn): the call returns normally, with the row and `no turn: the slash command left 42's prompt box and started no turn`. One that opens a dialog of Claude Code's own returns as `needs input` (1), one that starts a turn at that turn's end.
4. The message stalled: the agent sits at its prompt, where hq enters messages, and no turn started within 5 s: its prompt box did not come free that long (the user typing there), or Claude reported no prompt within 5 s of hq entering it. The call fails with one line, `hq: stalled: 42 did not take the message: ` and where the message is (still waiting in its inbox, nothing entered; no longer in its inbox, and no event of its journal says it was delivered; entered in its prompt box and not sent; gone from the box with no turn started), exit code `4`. hq enters nothing again and takes nothing back, so a waiting message still goes as above. The 5 s never run while the agent works, is starting or is at a dialog; they have passed once the condition has held for exactly 5 s; and a prompt Claude reports, one it queues included, is a turn started. A stall does not prove that nothing reached the agent: read it before sending again.
5. The timeout: `nothing yet`, which is not an error, with the message where it is. `hq wait NAME --since` from its cursor returns the agent's next change, which cannot tell which turn took the message: the agent's count of waiting messages says whether it has taken it yet.

## 6. Dashboard

### 6.1 Layout

One terminal window, split horizontally:

- **List** (top, fixed height: header + 6 rows + footer; scrolls beyond 6 agents with a `6 of 8  ▾ 2 more` hint).
- **Docked session** (bottom, the rest of the window): the live, fully interactive session of one agent. The user talks to Claude there directly. Nothing is copied or previewed; it is the real session. With nothing docked, the area shows a hint only; it is not a terminal and takes no input, and keys typed there go back to the list. The session is framed on all four sides by the surround (`#16181D`): the margins beside and below it and the footer; its title `▸ name · branch · sandbox` (or `▸ placeholder`) is at the frame's top-left.

The dashboard shows where the keys are. The side that has them, the list or the docked session, sits on the terminal's own background; the other side takes the surround's colour, and an unfocused session's text is also dimmed a little, so it reads as greyed out (cells Claude draws with its own background, such as its input box or a diff, may keep it). The session's title is in the accent (lavender) while the session has the keys and dim otherwise. The look flips whenever the keys move: `Alt+l`, a click, `⏎` docking into the session, a new agent taking the keys, returning from a dialog. The placeholder never holds the keys (they go back to the list), so it always shows as the unfocused side. Esc does not move the keys: Claude uses it to interrupt, cancel dialogs and rewind.

The terminal window is titled `hq - agents`.

Resizing the terminal window keeps the 6 list rows and gives the rest to the session. Below 24 rows the list shows 3 rows. Minimum width 80 columns; narrower terminals drop `LAST`, then `REPO`.

Header: `hq` + summary `N agents · X need you · Y done · Z working` + clock, `need you` counting the agents in an attention state and the outdated ones; while `sbx` has not answered for a few seconds, a quiet `sbx ?` beside the clock says that `ended` states may be stale, and it goes as soon as `sbx` answers again. The right corner ends with the running version after the clock, as quiet as the clock: `Wed 14:32 · v0.9.2` (`Wed 14:32  sbx ? · v0.9.2` while `sbx` does not answer); a development build shows `dev`, as `hq --version` names it (`hq dev`). When a newer version of hq is released, the same place shows it after the running version, `Wed 14:32 · v0.9.2 → v0.9.3 hq update`, and the left side carries no update hint; hq looks for new releases at most once a day (4.2). In a narrow terminal the left side gives up the counts from the last; the clock, `sbx ?` and the version stay, and only once the left is down to `hq  N agents` does the right give up ` hq update`, then `→ v0.9.3` (S12).

Columns: `TAB` (name), `REPO`, `BRANCH`, `STATE` (colored dot + word), `AGE`, `LAST`. No row numbers: under attention sort rows reshuffle on every state change, so positional shortcuts would point at the wrong agent. Colors: attention amber (an `outdated` row too: it needs the user), done green, working blue, ended grey, dark background; degrade gracefully on terminals with few colors.

The docked row is marked with an outline, the cursor row with a background. Both marks are on the same row, except while the slot shows the placeholder (S6), when only the cursor row is marked.

A dashboard left open across an update steps aside for an hq of another generation. Every few seconds the list looks at the hq it was started from; once that has been replaced (`hq update`, the install script) by an hq of another generation, the list runs from the new hq within 5 s, by itself, with the docked session, the cursor row and the layout as they were, as across `q` and `hq`; the header then shows the new version. A list of an older generation would read agents the wrong way. After an update of hq's own generation the list goes on as it was. While hq is not replaced, watching for a replacement takes nothing the user notices from the list.

### 6.2 Sorting

Sort, cycled with `s`, current mode marked in the column header, remembered between runs:

- `attention` (default): `outdated`, `needs input`, `question`, `done`, `working`, `starting`, `ended`; ties by age, newest first.
- `repo`: repo name, then attention order inside a repo.
- `state`: attention order, stable by name inside a state (no reshuffling by age).

The list always shows every agent, in all states (ADR 0016); the attention sort keeps those needing the user on top. All row actions work on any row; an agent needs no pending question to be docked.

### 6.3 Selecting

- `↑/↓` move the cursor.
- `/` then a name selects by prefix match, case-insensitive, shown in the footer as `/ag · 1 match: agent-17`; `Enter` docks the match, `Esc` clears. The `/` prefix keeps names from colliding with single-letter keys. Same names as `hq go NAME`, so the shortcut is stable across re-sorts.
- Mouse: a click on a row moves the cursor there. A click on the row that is already the cursor row does nothing.

The session slot follows the cursor: the row the cursor stops on is docked, and the keys stay in the list, so the user can look through the sessions row by row; `Enter` or `open` then moves the keys into the docked session. Holding `↓` docks only the row where the cursor stops, not every row it passes.

The cursor row is always the docked row, and only the user's own moves change them: `↑/↓`, a click on a row, `/name`, `Enter`/`open`, the dock shortcuts from inside the session (6.5), `hq go NAME`, and `n` in the dashboard (S2). Nothing else moves either: a re-sort, a refresh or a state change moves the row, and the cursor stays on it; an agent started from outside the dashboard (`hq new` from a shell, or another tool) takes neither the slot nor the cursor while an agent is docked (S2). When the docked agent goes (killed, S6), the slot shows the placeholder and the cursor moves to a neighbouring row without docking it; the user's next move docks again.

### 6.4 Row actions

The cursor row, and only the cursor row, shows a right-aligned action strip drawn over the tail of its content: `⏎ open`, `c code`, `p pr`, `k kill`. `pr` appears only when the branch has a pull request. Below 100 columns the strip shrinks to glyphs `⏎ c p ✕` and covers the tail of `AGE`/`STATE`; the footer keeps the labels. Columns never move to make room for the strip. Nothing appears on hover; the strip follows the cursor.

- `open` / `Enter`: dock this agent's session below the list, if the cursor has not docked it already, and move keyboard focus into it.
- `code` / `c`: open the editor on this agent's worktree (as `hq code`).
- `pr` / `p`: open this branch's pull request in the browser.
- `kill` / `k`: end this agent, always after the Kill dialog.

A click on a strip item fires that action at once (kill still asks).

### 6.5 Other keys

- `n`: New agent dialog.
- `s`: cycle sort. `r`: force refresh.
- `q`: quit the dashboard and give the terminal back to the shell it had before `hq`, full height; agents keep running, `hq` brings the dashboard back with the same docked session.
- From inside the docked session, without leaving it: dock previous/next row, and dock the first row needing attention (bound to modifier-key shortcuts that do not clash with Claude Code's own keys). Switching keyboard focus between list and session uses the terminal's / tmux's own pane switching.

### 6.6 Dialogs

Every question and input in the dashboard is a centered modal dialog drawn over the list and session, never an inline prompt (the look of `sbx`'s own TUI dialogs is the reference). Common behaviour:

- Centered title, `×` top-right, buttons centered below the content; the default button is highlighted and carries `⏎`.
- `Enter` = default button, `Esc` = cancel, `Tab`/`←`/`→` move between fields and buttons, `y`/`n` also answer yes/no dialogs.
- Mouse: click a button to fire it, click `×` to close; clicks outside the dialog do nothing.
- While a dialog is open the list keeps refreshing underneath but receives no keys or clicks.

Dialogs in v1:

- **New agent** (`n`): fields `name`, `dir` (prefilled with the cursor row's repo, else the directory hq was started from), `prompt`; `Start ⏎` / `Cancel`. A duplicate name keeps the dialog open with the error under the field. When the user has defined setups besides `default` (§11), a `setup` field stands between `dir` and `prompt`: the setups in one line (`○ default  ● local`), `default` chosen when the dialog opens, changed with `↑`/`↓` while the field has focus or by a click on a setup (`Tab`, `←`/`→` move on to the next or previous field there); at its right, dim, the sandbox the agent will run in (`sandbox hq-local-shop-portal`), followed by ` (new)` while it does not exist yet, following the setup chosen and the `dir` typed (none while `dir` is not in a repository). The hint line then reads `dir defaults to the cursor row's repo · ↑↓ setup · Tab next · Esc cancel`. The agent starts in the chosen setup's sandbox exactly as `hq new --setup SETUP` does, and when `sbx` refuses the setup the dialog stays open with the error `hq new` prints. Without setups besides `default` the dialog has no setup field and is as above.
- **Kill agent** (`k`, strip `kill`): `Kill NAME (branch)?`, note "Ends the Claude session; the sandbox stays.", `No ⏎` (default) / `Yes`.
- **Stop everything** (if bound inside the dashboard): same shape, states the number of agents.

The `/name` search is the one exception and stays in the footer, because it filters the list while typing and must not cover it.

## 7. Scenarios

Trigger, what the user sees, what must be true afterwards. These are the acceptance narrative for the implementation and the manual test.

**S0. Default view** - `hq` with agents running: the list shows every agent, those needing the user on top in amber (attention sort, 6.2), the docked one with its outline; the header counts them.

**S1. Start of day** - `hq` with nothing running: the dashboard opens with an empty list ("no agents yet - press n to start one, or run: hq new NAME [DIR] [PROMPT]") and an empty session slot. With agents already running: the dashboard opens showing them, with the previously docked session still docked. When nothing is docked (e.g. the docked agent was killed before the user left, S6), the dashboard opens with the cursor row (6.3) docked and focus in the list; an empty list keeps the empty slot. This happens only on entering hq (`hq`, `hq dash`, including coming back to a running dashboard); after that, the placeholder stays until the user moves the cursor (6.3).

**S2. New agent** - `n` in the dashboard or `hq new NAME [DIR] [PROMPT]` from any shell: the row appears at once as `starting` and becomes `working` when the agent reports taking its PROMPT, or `done` (last message `-`, no notification) once Claude shows it took a PROMPT that is a command of its own that starts no turn (`/model NAME`); without a PROMPT it becomes `done` (last message `-`, no notification) once Claude waits at its prompt, within seconds. A new agent gets a `new` marker while it is `starting`. The cursor is always the docked agent, and only the user's own moves change them (6.3): an agent started with `n` in the dashboard is docked, gets the cursor, and focus moves to it (so a fresh sandbox can be logged in). An agent started from outside the dashboard (`hq new` from a shell, or another tool) takes neither the slot nor the cursor while an agent is docked; if nothing is docked, it is docked, gets the cursor and focus moves to it, as with `n`. With a setup (`hq new NAME --setup SETUP`, the New agent dialog's `setup` field, 6.6, the supervisor's `new` with `setup`) the agent starts in the repository's sandbox of that setup, created first when the repository has none for it (S11); without one, in its `default` sandbox. Duplicate name or unknown setup: error, nothing created.

**S3. Select and work** - `↑↓`, a click or `/name`: the live session of the row the cursor stops on is docked below, the keys staying in the list, so the user can look from session to session. `Enter`: keyboard focus moves into the docked session. The user types to Claude directly; the list only updates that row's state and last message. Previous/next/first-needing-attention can be docked from inside the session without leaving it.

**S3b. Name search** - `/ag` shows the matches in the footer and moves the cursor to the first match, which the slot follows; `Enter` moves the keys into it.

**S4. Agent needs the user** - within 1s the row turns amber and moves up (attention sort), and one desktop notification fires whether the agent is docked or not (none for the `question` of a supervised turn, S5c). The user docks it, answers, the state returns to `working`.

**S5. Agent done** - the row turns green `done` with the last message (e.g. "PR #58 opened"). Review happens on GitHub; the row stays until killed.

**S5b. Agent waits for its subagents** - an agent told to start subagents in the background and end its turn stays blue `working`, its time counting from the user's prompt and its last message that turn's, with no notification; the user docked on it sees Claude at its prompt, and Esc there changes nothing. As the subagents finish, Claude takes a turn for each (only the last message changes while others still run). When the turn after the last one ends, the row turns green `done` and one notification fires.

**S5c. Agent done for the supervisor** - an agent the supervisor gave a prompt (through `hq mcp`: `new` with a prompt, or `send`) ends its turn: the row turns green `done`, or amber `question`, exactly as in S4 and S5, and no desktop notification fires; the supervisor reads the reply and tells the user. If the agent opens a permission prompt on that turn, one notification fires (S4); after the user approves, its `done` fires none. When the user prompts the agent themselves, or their prompt or message reaches a turn of the supervisor's, or the supervisor's message reaches a turn of theirs, one notification fires at the turn's final end.

**S5d. Agent done with its own task left running** - an agent told to start a command in the background itself (`sleep 120`, a dev server) and end its turn turns green `done` at once, with one notification, as in S5; its row reads `1 shell · ` dim before its last message, and `hq read` shows `own task: shell  sleep 120`, so the user and the supervisor know Claude will take another turn. When the command ends, the row turns blue `working`, then green `done` with one notification; once that turn ends with nothing of its own running, the count is gone. A watch the agent keeps itself shows the same way, by its description (`1 monitor · `); an artifact's watch shows nothing.

**S6. Kill** - `k`, strip `kill`, or `hq kill NAME`: Kill dialog, `No` default. On `Yes` the Claude session ends cleanly, the sandbox stays. If the killed agent was docked, the session slot becomes an empty placeholder with a hint, focus stays in the list, and the cursor moves to a neighbouring row without docking it (6.3). The same name may be reused afterwards.

**S7. Agent ends by itself** (Claude exited, sandbox stopped, launch failed): the row turns grey `ended` with the last known message, `[session ended]` when it had none, in the list and in `hq ls` alike; its output stays readable when docked; `k` removes the row.

**S8. Quit** - `q`: the dashboard closes and the terminal is back at the shell it had before `hq`, full height and scrolling normally, with nothing of hq left on screen; a hint there says how to bring the dashboard back. The docked session stays where it is and keeps working. `hq` restores the dashboard with the list and the same docked session. While the dashboard is closed (after `q`, or with the terminal detached or closed), desktop notifications are not shown.

**S9. Detach / close / sleep** - closing the terminal window or detaching leaves everything running; `hq` reattaches with the same layout. After laptop sleep, if agents fail with clock drift, `hq sandbox restart REPO` fixes it (`hq sandbox restart REPO --all-setups` for a repository with several sandboxes, one per setup, which it restarts after one confirmation); affected rows go `ended` then `starting` and stay listed throughout (their names stay taken), a docked agent stays docked, and each keeps its branch and last message (`[session ended]` while ended when it had none, S7) until its next prompt; once its session is resumed and waits at its prompt it is `done`, without a notification.

**S9b. Host restart** - the host restarts (or the tmux server goes) while agents run: `hq` opens with an empty list and `hq ls` shows nothing, but the agents' work and conversations are kept. `hq restore` (or `hq sandbox restart REPO`, which also restarts the sandbox) brings every lost agent back under its name, each in its own sandbox and worktree, continuing its conversation: the rows come back `starting` with what each last said, then `done`, and a message (`hq send`) reaches the continued session. An agent whose worktree was removed meanwhile is reported with the reason and stays lost until `hq kill NAME` forgets it; running `hq restore` again restores nothing more.

**S10. Stop everything** - `hq stop`: one confirmation, then every agent ends; sandboxes stay.

**S11. Several agents in one repo** - same sandbox, different worktrees/branches; rows differ by branch. Same-branch agents are a documented limitation (see 5). Agents started on different setups run side by side in the repository's sandbox of each setup, at the same time (one on a local model, another on Claude); each docked session's title names its sandbox. Starting an agent on one setup ends no session and recreates no sandbox of another. A conversation stays in the sandbox it started in.

**S12. Narrow terminal** - at 80 columns `LAST` is dropped, the action strip is glyphs only; below 24 rows the list shows 3 rows. Everything remains operable.

**S13. Windows/WSL** - identical flows in Windows Terminal; notifications, editor opening and sandbox handling work from WSL.

**S14. Outdated agent** - after an update to an hq of another generation, an agent the earlier hq started is still running: its row is on top, amber, `outdated`, with no age, branch `-` and `started by an older hq: kill it and start it again`, counted under `need you`. `Enter` docks it, and the user finishes or saves its work by hand; `k` kills it, and the user starts it again with `n` (or `hq new`).

**S15. Update across generations** - the user runs `hq update` while two agents work and one sits `ended` in the list, and the latest release is of another generation: hq refuses, names the release, the three agents with their states and the remedy, and stays as it was. The user lets the agents finish, `hq stop` ends them, and `hq update` goes through. Had the release been of hq's own generation, the update would have gone through at once with the agents untouched. The install script, run over an installed hq with an agent, refuses the same way. Once the update has gone through, the dashboard the user left open shows the new version within 5 s, its list running from the new hq with the docked session kept, and the supervisor's `hq mcp` answers every call with `hq was updated: restart hq in this client` until the user restarts hq in that client. A supervisor inside a sandbox, whose `hq mcp` sbx's gateway started on the host, gets `hq was updated: on the host, run hq sandbox restart REPO for this sandbox's repository, with --setup SETUP for a sandbox of a setup` instead, and `hq update` named that sandbox; after `hq sandbox restart` of that sandbox (its repository, with `--setup` for a sandbox of a setup) its tools work again.

## 8. Constraints

- No background daemon: the dashboard alone observes and refreshes; nothing runs when it is closed except the agents themselves.
- Dependencies limited to what the team can install with one command on macOS and in WSL.
- Repositories need no hq files or configuration; any hq state kept inside a repository is never tracked by git and needs no ignore rule.
- Everything platform-specific (macOS vs WSL) is isolated, not scattered; behaviour is identical.

## 9. Out of scope (v1)

Creating worktrees or branches, managing pull requests, PR status per branch (leave room for a column), several sessions side by side, multiple tmux sessions, anything workmux-like beyond control and visual.

## 11. Setup

- Prerequisites on the host: git, curl, tmux 3.4 or newer, Docker Sandboxes (`sbx`) 0.48.0 or newer, VS Code with `code` on PATH. macOS: iTerm2. Windows: Windows Terminal, WSL (Ubuntu 24.04 or newer) with the same tools; `sbx` is the Linux binary inside WSL, or the Windows binary reachable from WSL, the Linux one used when both are there. Each `sbx` has its own sandboxes, and those of the one hq does not use, with their agents, are not visible to hq. Windows Terminal's bell is set by the user to flash the taskbar (`bellStyle` including `taskbar`): as installed it does not, and the flash is the desktop notification on Windows (5).
- `sbx` is set up by the user before hq can start an agent: signed in (`sbx login`) and with its network policy chosen (`sbx policy init`), once per machine. Until then `hq new` fails with `sbx`'s error and its remedy (4.2).
- The user may choose what hq creates a repository's sandbox with: an image (an `sbx` template) and MCP servers registered with `sbx`, set once per user and overridable for one command. Unset, a sandbox is created with `sbx`'s defaults. They apply only at creation; an existing sandbox is used as it is. hq does not fetch or check the image: when `sbx` refuses the image or a server, `hq new` fails with `sbx`'s error and names the settings it used and where they were set.
- Setups: those settings are the `default` setup. The user may define other setups once per user, each by name, with an image, MCP servers, and a model with where it is served from (a provider registered with `sbx`, such as LM Studio on the host), each optional; setups do not inherit from each other, and the overrides for one command apply to the default only. A repository gets one sandbox per setup it is used with, created on the first `hq new` that asks for it; every existing sandbox, hq's or made by hand, is the `default` one without migration, and the sandbox of a setup the user later removed is never taken for the default. A setup applies only at creation, as above: a changed setup takes effect once its sandbox is removed and created again. `default` cannot be defined a second time among the other setups: hq refuses that with the reason, and setups written in a form it cannot read the same way, naming the file and the setting. hq checks none of a setup's values: when `sbx` refuses one (an image it cannot find, a model while its model feature is off, an unknown provider), `hq new` fails with `sbx`'s error and names the setup's settings and where they were set. `sbx`'s own limits are passed on as its errors: a sandbox name over 63 characters, and two repositories of the same directory name on one setup. Running a local model (enabling `sbx`'s model feature, registering the provider, loading the model) is the user's, once per machine; hq neither starts nor checks it. Windows: hq adds nothing per platform; whether `sbx` serves a model there is `sbx`'s support.
- Windows: the Linux `sbx` is installed inside WSL; the Windows `sbx` is installed on Windows and is seen from WSL sessions opened after it was installed. Without either, hq and its installer say that neither was found, naming both. The Windows `sbx` needs an x86-64 machine with the Windows Hypervisor Platform; hq itself runs on WSL 1 and WSL 2, and also where `sbx` cannot start a sandbox (ARM64 Windows, a virtual machine without nested virtualization); there `hq new` fails with `sbx`'s error and `sbx diagnose` says why.
- Optional: GitHub CLI (`gh`, logged in), only for the dashboard's pull requests (`pr`, 6.4). Without it, or logged out, hq works the same and simply shows no pull request.
- hq is installed once per machine with one command, from the public releases and without a GitHub login, and is available on PATH as `hq`; there is no service to start. `hq update` brings it to the latest release. The same command run over an installed hq is an update by another way and follows the rule of `hq update` (4.1): before it replaces anything it asks the installed hq whether it may, and a release of another generation is refused while any agent that hq knows exists, or while it cannot tell, with that hq's line and exit code `1`. An installed hq from before generations cannot answer: it is asked for its agents instead, and any agent it lists refuses the install. A first install asks nothing. The installer checks that `sbx` is there, not its version.
- Repositories need no preparation: any repository with a sandbox can host agents as it is.
- The supervisor (Phase 2) needs Claude Desktop or Claude Code on the same machine (on Windows, Claude Desktop's Windows app or Claude Code, in WSL or on Windows, with hq in WSL) and one command, `hq mcp install` for Claude Desktop or `hq mcp install claude-code` for Claude Code, then a restart of the client. Running it again after moving hq keeps the entry right.

## Phase 2: supervisor over MCP

A supervisor is a conversation in an MCP client, Claude Desktop or Claude Code, that the user tells "do this and that": it starts agents for it in the right repositories, follows their progress and gives them feedback that each agent takes into account when it is ready. It drives hq through `hq mcp` (4.1), set up once with `hq mcp install` (11); both clients behave alike, but for how long one `wait` may last. This replaces the earlier idea of a long-lived `sup-<project>` agent per project.

- **The supervisor is an MCP client, not an agent.** It has no row, no state and no session in hq; the agents it starts are ordinary agents, listed, docked and killed as any other, and always directly reachable by the user. Only the notifications of the work it sends them differ (below).
- **Status comes from hq, never from the agent.** The supervisor learns an agent's state, branch, last reply, what it asks (a dialog's questions with their options, or an MCP server's form with its fields, 4.1), the messages waiting for it and its own tasks (5) with `list` and `read`, live and without taking the agent's time; agents are never told to write a status on a timer. A long reply comes in pages as with `hq read` (4.1): `read` takes `offset` and `since`, and gives `reply_size` and `next_offset` (null on the last page).
- **Asking an agent is a message.** The supervisor asks with `send` and reads the answer when the agent stops (5.1): its next `wait` watches from a cursor taken before `send`, so an answer that comes before the `wait` is not lost; a message that follows as a prompt of its own behind an earlier one is answered a turn later, and `send`'s description and the server's instructions say so, as they say that a slash command its hooks deliver arrives as text and does not run; `--now` is a course correction inside the running turn. To wait for that one answer in the same call, the supervisor passes `wait` (with an optional `timeout`) to `send`: it ends as `hq send --wait` does (5.1, *Waiting for the answer*), within the client's limit on a tool call (that of `wait`: 50 s for Claude Desktop and `sbx`'s gateway, an hour for Claude Code), returning `next_since` at that limit to go on with a `wait` that names that agent alone; a stall is the tool's error. That `next_since`, and the one such a `wait` returns, are still that one agent's: the supervisor's watch keeps taking its `since` from its own last `wait` or `list`, so it returns that same change once more. The server's instructions and the `wait` tool say both: the watch never takes its `since` from `read`, `send` or `answer`, while a `wait` that names that one agent alone may start from the `next_since` of its `send` or `answer`. The description of `send` and the server's instructions say when to wait in `send`, its five ends, to go on with `wait` after a timeout, that the watch returns the change again, and to read the agent before sending again after a stall. Notifications do not change: a supervised turn ends without one whether or not the supervisor waits.
- **Watching is waiting.** `wait` returns as soon as an agent is `done`, `question`, `needs input` or `ended`, with every other that is within a moment of it; called in a loop, each call passing the cursor of the supervisor's most recent `wait` or `list` and naming every agent it follows, the supervisor sees every change once, including one that happened between that result and the call; what a `list` already showed, it is told to act on there, since a `wait` from the cursor of `list` returns only what changes after it. The cursor `read`, `send` and `answer` give is that one agent's, and the supervisor is told never to watch from it: a change of another agent before it could be lost. `list`, `read` and `wait` carry each agent's state number and completion number as `hq ls --json` does, and every tool that gives `next_since`, and the server's instructions, say to pass it back exactly as given. A call returns "nothing yet" before the client gives up on a tool call: Claude Desktop gives one 60 s, so its supervisor waits at most 50 s per call and loops; Claude Code's may wait up to an hour in one call. An agent returned `done` or `question` with own tasks (5) takes another turn when they end, so the supervisor waits again for that result: it is told so in its instructions and in the `wait` and `read` descriptions, with that a dev server may never end and that the list is the turn end's own.
- **Question dialogs and Claude Code's own are answered on the user's word; other dialogs stay the user's.** The supervisor answers an agent's question dialog, or a dialog of Claude Code's own (such as the one that confirms an effort or model change it sent with `send`, `/effort LEVEL` or `/model NAME`, after the agent's first turn), with `answer` only for the user: when they have said in the conversation what to pick, or told it to choose for them (whether it may then pick its own recommendation is part of what they said), passing their word with the call (`confirmed`); never on its own initiative. Permission prompts, MCP elicitations and a list of Claude Code's own that scrolls (the model picker of `/model` with no name) stay the user's, at the agent: the supervisor never answers them and never asks the user to let it; it tells the user which agent waits. `read` and `list` give the dialog's id, and `send`'s description points to `answer` for question dialogs and Claude Code's own. A message sent meanwhile waits until the dialog is closed.
- **What the supervisor sent reports to the supervisor.** A turn whose prompts all came from it (`new` with a prompt, `send`) is a supervised turn (5): its `done` and `question` raise no desktop notification, on any agent, whoever started it. The supervisor is told: its instructions and its `new` and `send` tools say that the user is not notified when work it sent finishes or asks a question, so it waits for that work and tells the user. What its tools return, and `wait`, do not change. Whatever the user prompts, or sends a message into, notifies them as ever.
- **An outdated agent is the user's to clear.** `list` shows an outdated agent (5) with the state `outdated`, and the server's instructions say what that means: hq cannot read its state, so the supervisor tells the user rather than waiting on it. `read`, `send`, `answer` and a `wait` that names it fail with the line the commands give; a `wait` on every agent leaves it out; `go` and `kill` work on it as on any agent.
- **`hq mcp` steps aside after an update to another generation.** The client keeps the `hq mcp` it started running across `hq update`; one left from an earlier generation would start agents with a hook the installed hq cannot read. Before each tool call it looks at the hq it was started from, and once that has been replaced by an hq of another generation every call fails with `hq was updated: restart hq in this client`, starting no agent and changing nothing; the server's instructions say what the line means and that the supervisor tells the user to restart hq in the client. Inside a sandbox, restarting Claude Code does not replace the `hq mcp` sbx's gateway started on the host, so there the line is `hq was updated: on the host, run hq sandbox restart REPO for this sandbox's repository, with --setup SETUP for a sandbox of a setup`, and the instructions say the supervisor tells the user to run `hq sandbox restart REPO` on the host, with `--setup SETUP` for a sandbox of a setup (REPO alone being the repository's default sandbox), which starts the sandbox's hq anew. After an update of hq's own generation its tools work as before; in a sandbox they run the earlier release's code until it restarts. While hq is not replaced, watching for a replacement takes nothing a tool call notices.
- **No push into the client.** A tool call is a request and its answer; the supervisor acts only on a turn of its own. Without a `wait` running, the user is the clock, and nothing prompts them: a supervised turn ends without a notification even then. They see in the agent's row that it is `done` or asks a question, and ask the supervisor.
- **Ending an agent is the user's call.** `kill` ends nothing unless the supervisor passes the user's confirmation: it asks the user first, naming the agent, unless the user has just said to end it. `kill` is also marked destructive, so a client that asks before destructive tools does; hq does not rely on that. A supervisor that is itself an agent (its Claude Code runs in one of hq's sessions) cannot end, answer or message itself: `kill`, `answer` and `send` naming it are refused (4.1), so a confirmed "end every agent of the release" that matches its own name ends the others only. `stop` and `sandbox` are not offered.
- **Out of scope for now:** agents messaging each other (they report up in their replies and the supervisor passes on what matters), grouping the list under supervisors, dashboard changes for the supervisor, MCP clients other than Claude Desktop and Claude Code (any client that starts a server over standard input and output works the same, untested, with Claude Desktop's limit on `wait`), and a supervisor that does not run on the user's machine beside hq, such as Claude Code inside a sandbox: it would need a transport other than standard input and output.
- **Acceptance:** from Claude Desktop on macOS, start two agents in two repositories with prompts, watch them with `wait`, read one agent mid-turn, send it a question answered at its next stop and a `--now` correction it follows within the running turn; the supervisor answers an agent's question dialog only after the user said what to pick (or told it to choose), and the agent goes on as if it had been picked at the agent; likewise it confirms an effort change it sent an agent after its first turn (`/effort`); it never asks the user to let it answer a permission prompt; the agents it gave work to reach `done` or ask a question without a desktop notification, a permission prompt of theirs fires one, and the supervisor tells the user what they said. The same on Windows 11 with WSL. The same from Claude Code on the same machine (on Windows, in WSL and on Windows), set up with `hq mcp install claude-code`, where one `wait` may last longer than 50 s and returns as soon as an agent it waits for is done.
